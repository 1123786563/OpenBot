## 5. 验收逐条证据映射（Issue #55 四条）

1. **受限角色下跨公司 SELECT/UPDATE/DELETE 与跨公司外键关联被数据库拒绝**：SELECT——operator 对全部 9 张核心表（tenants 按 id、其余按 tenant_id）跨公司 0 行；data 角色 6 表 0 行 + 全局表 principals 的 B 公司主体行不可见。UPDATE——operator 跨公司 `update memberships/resources ... returning` 0 行且行存活（受限读复核）。DELETE——operator 跨公司 `delete grants ... returning` 0 行且行存活；data 角色 DELETE 42501。FK 关联——`(tenant A, B 公司 team)` / `(tenant A, B 公司 resource)` / 反向三例全部 **23503**（复合 FK 内嵌 tenant_id，配对结构不存在，跨公司关联结构性不可能）；重指 FK 列（`workspace_id`/`tenant_id`）42501（列级授权缺失）；data/directory 任意写 42501。存在性不泄露：跨公司现存 id 与不存在 id 的 SELECT 结果逐字节同形。
2. **团队公共、个人所有权与显式分享的数据库策略与应用层规则一致（两侧对照）**：`dbSideRead` = 受限 data 角色事务内、在真实 RLS 过滤的行/事实上直接计算的应用规则等价谓词（own grant ∨ (visibility='workspace' ∧ 资源所属团队有效成员) ∧ 同团队 ∧ 活跃）；与 `decide()` 两个已发布版本 + 生产 reader 逐例对照：**db 判定 == workspace-v1 判定（9 个矩阵例全等）**；tenancy-v1 只能更窄（allow ⟹ db allow）；reader 跟 tenancy-v1（200 仅授权路径）。覆盖：显式分享 / 个人所有权 / 团队公共无授权成员 / 同公司跨团队 / 停用成员（两侧同步失去团队公共路径、恢复后同步放行）/ private 不放宽 / 未标记不自动放宽 / 跨公司（行不可见 = db deny，与不存在同形）/ 多公司身份双 scope。另钉死事实私有性：grants 只见自己的（restrictive 策略）、workspace memberships 只见自己的。
3. **事务结束后上下文被清除；连接复用不带上一次范围**：三角色各自提交后——同 backend PID 复用证明 + 全部 7 个 `app.*` 键为空 + 无上下文 0 行；带活跃 scope 回滚后下一事务干净；**MT012 清理函数**：会话级残留（模拟应用错误写 session 级上下文）经 `ob_ent_reset_business_context()` 清空（清理前 1 行可见 → 清理后键空 + 0 行）。
4. **不用可绕过 RLS 的角色做普通数据访问；机器读权限单独登记且不可用于普通业务接口**：app 配置的 3 capability + 3 login 角色 `rolsuper`/`rolbypassrls` 全 false + 能力校验 seam 全程在岗；9 表 `relrowsecurity`/`relforcerowsecurity` 全 true（属主不可绕过）；`ob_ent_identity_operator` 存在、NOLOGIN、对 9 表 SELECT/INSERT/UPDATE/DELETE 全 false、无清理函数 EXECUTE、无运行时登录 URL（`ROLE_DATABASE_VARIABLES` 键 = 三业务角色，静态单一来源）；index.ts 静态装配核验：企业数据访问只经三个已验证受限 URL（`createDatabase` 调用点白名单 + verifyXxxDatabase 存在性）。

## 7. 策略模板（下游业务闭环 Ticket 复用；票面备注要求）

下游表（凭据、账务、会话、知识、任务等）在各自 Ticket 启用 RLS 时，**复用以下模板与测试写法**，不再重新设计：

1. **表定义三要素**：业务归属列 `tenant_id`（+ 需要时 `workspace_id`）参与主键/唯一键；子记录用**复合 FK 内嵌 tenant_id**（如 `(tenant_id, resource_id) → parent(tenant_id, id)` ON DELETE cascade）——跨公司引用因配对不存在被结构性拒绝（23503），无需额外策略；drizzle 侧同文件既有模式。
2. **迁移步骤模板**（migrate-test.ts 注册新任务，expand-only）：① `REVOKE ALL PRIVILEGES ON TABLE <t> FROM PUBLIC, ob_ent_directory, ob_ent_data, ob_ent_operator, ob_ent_identity_operator;` → ② `ENABLE` + `FORCE ROW LEVEL SECURITY`（FORCE 一并约束表主）→ ③ 按需最小策略（下）→ ④ 最小列级 GRANT（SELECT 给读角色；INSERT/UPDATE(具体列)/DELETE 只给 operator；**identity_operator 永不授予**）。
3. **策略谓词模板**（与 app 规则同一语义，`nullif(current_setting(...))` 习惯）：
   - data 读（业务读角色）：`tenant_id = nullif(current_setting('app.tenant_id', true), '')`，凡属个人/分享事实的表再加 **restrictive** 策略 `principal_id = nullif(current_setting('app.principal_id', true), '')`（grants 表先例）；
   - directory 读（自助目录）：EXISTS 经 principals 关联 `user_id = nullif(current_setting('app.user_id', true), '')`；
   - operator（离线运维/装配）：tenant 范围读 + `WITH CHECK (tenant_id = ...)` 的插入；更新加 `id = nullif(current_setting('app.resource_id', true), '')` 与/或 `principal_id = nullif(current_setting('app.operator_principal_id', true), '')` 逐行钉住；审计表加 `id = nullif(current_setting('app.operation_id', true), '')`。
   - **不收紧 data 角色的租户范围行可见性**（fixtures.test.ts 已钉基线：data 角色事务租户内可见、app 层负责收窄到授权/团队公共）——两侧一致性用「受限角色事务内计算应用规则等价谓词 vs 注册表判定」的对照测试表达（本票 `dbSideRead` 写法）。
4. **测试写法模板**（rls-core.test.ts）：跨公司 SELECT/UPDATE/DELETE（`returning` 观察 0 行 + 行存活复核）+ FK 三例（23503/42501）+ 存在性不泄露（与不存在 id 同形）+ 两侧对照矩阵 + 提交/回滚上下文清除 + 会话残留经 `ob_ent_reset_business_context()` 兜底 + 角色非 bypass/表 FORCE/identity_operator 零权限核验。
5. **上下文键清单**（7 个，与清理函数单一来源）：`app.{tenant_id, principal_id, user_id, workspace_id, operation_id, resource_id, operator_principal_id}`——新增键时同步扩清理函数并在本模板登记。
