## 1. 设计要点

Spec §6 顺序不可逆：**先定允许集合 → 检索端限制 →（命中才有）重排 →（引用才进）模型上下文**。「检索后过滤」不是隔离机制，只是纵深防御；候选集合断言是验收形态。

### 新文件（3，全部新建；主库零迁移——复用 enterprise 注册 + KB 库既有内容表）

1. **`server/src/kb/application/service/kb-restricted-retrieval.ts`（受限检索入口，kb 域，消费 tenancy 权威）**：
   - `createRestrictedRetrievalService({authority, kbDb, search})`；`search` 缝隙与 KbHandlerDeps.search 同形（`SearchRequest → {results, count}`），生产装配接 hybridSearch（本票测试接真实 hybridSearch + 真实 qdrant 检索引擎，仅 QdrantClient 为内存替身）。
   - `retrieve(requester, request)` 五步：
     a. **信任门**：assertRequester（结构检查——内部 API-Key Identity 与一切无 scope 形状 → `KB_REQUESTER_INVALID`；+ assertTrustedScope——伪造 scope → `UNVERIFIED_SCOPE`）。与 MT036 入口同款，双门冗余的第一道。
     b. **候选集合构造先于一切内容访问**：经 MT036 `narrowRetrievalScope` 收窄到「授权 + 跨库一致」（去重、首现序、输入卫生 >100/非串/空串 `KB_RETRIEVAL_INPUT_INVALID`——语义在 MT036 钉死，本入口继承）。
     c. **空候选 = 检索端零调用**：embedder/向量引擎/重排器一次都不被调用，返回空结果（跨范围检索返回空而不是他人内容；测试以三端调用计数断言）。
     d. **检索端限制**：唯一一次 search 调用，`kbIds = 候选集合`、`tenantId = scope.tenantId`（服务端身份，非客户端输入）。向量引擎 wire 层 filter = tenant_id match + kb_id any(候选) + enabled——**向量命名空间按归属隔离的检索端实现**（A8 单 collection 架构下，命名空间 = payload filter 的授权投影；候选集合即命名空间的可达边界）。
     e. **纵深防御（非主机制）**：组装后丢弃 kbId ∉ 候选集合的结果行（MUT-D 变异如实验证其非主机制地位，见 §4）。
   - **引用面（AC3）**：`restrictedCitationOf` 纯函数投影——citations 与受限结果行 1:1，snippet = 该行内容的 rune 有界前缀（`DEFAULT_CITATION_SNIPPET_RUNES=280`，冻结测试钉死）。无权内容根本不进结果行（b/d 两道），引用无从泄漏；snippet 截断保证引用文本不携带超界片段。
   - **`candidateKbIds` 随结果返回**：实际进入检索端的候选集合，可观测审计面。
2. **`server/tests/multitenancy/support/retrieval-restriction.ts`（测试支撑）**：内存向量库（QdrantClient 替身——按真实引擎同语义逐字段过滤 must: tenant_id/kb_id any/enabled、余弦相似度、limit、with_payload；**逐次捕获 collection+body = 候选集合断言的引擎边界探针**）；记录型 embedder/reranker（零调用计数 + 重排文本捕获）；`seedRetrievalContent`（knowledges+chunks 行、文档内 pre/next 链自动连接、enabled=false 反例、向量点镜像真实 index-writer payload 键形）。
3. **`server/tests/multitenancy/retrieval-restriction.test.ts`**（票面 Verification 指定路径，20 用例）。

## 5. 诚实披露

- **D1（主库零迁移；无任务注册）**：检索/引用面纯消费既有对象（enterprise_resources 注册表判定 + KB 库 knowledges/chunks 既有表 + MT036 narrowRetrievalScope），无新表无新列 → migrate-test.ts / migration-tool.test.ts 零改动（无第十五任务、无 allowlist 窄例外）；测试 beforeAll 落账的是 brief 依赖序全链十四任务的既有迁移。
- **D2（检索后过滤存活的语义）**：MUT-D（纵深防御过滤移除）存活是有意的设计验证而非缺口——票面明确「检索后过滤不算隔离」；本票的隔离机制是候选收窄（b）+ 检索端限制（d），e 步过滤只是防御纵深（例如未来上游实现回归时的兜底）。若 e 是唯一机制，MUT-A/MUT-D 会呈现相反的捕获结果。
- **D3（GREEN-1 的 2 个测试侧缺陷）**：① 邻块扩展用例以 content.includes(MARK.pub2) 定位「中间块行」，误命中 c3 命中行（其 pre 恰为 c2 内容）——改按 seedRetrievalContent 返回的 chunkId 精确定位；② company-admin 无团队成员资格，`scopeFor` 在真实 seam 签发时即 WORKSPACE_FORBIDDEN——比原设想的「签发成功但检索空集」更强的 AC4 语义，改断言签发拒绝。**生产代码在该轮零回改**；REFACTOR 轮生产改动仅一处导入路径修正（企业 Db → KB 域 Db，类型面修正，语义零变化）。
- **D4（三信任门结构）**：信任边界实际有三道（本入口、MT036 查询入口、MT036 权威模块）。单门/双门移除被余下门兜住（MUT-Ca 存活），三门同移捕获（MUT-C-full）。MT036 报告的「双门」是其票内两道门的全移；本票口径按全部信任门同移检验，已在 runner 注释钉死。
- **D5（基线环境特性与同库单次性）**：MT069 计费回归用全局唯一固定幂等键（credit_grants.idempotency_key 唯一索引），同库第二次运行必失败——非本票缺陷且非本票可修（既有验证交付）；本票门槛运行前以 `reset-testdb.sh` 重建库保证确定性（03/09 存档）。另观察同库并行 29 文件偶发锁竞争瞬态（2s lock_timeout；一次 762/8，复跑 770/0 自愈）——门槛以 0 fail 干净运行存档为准。
- **D6（生产装配不接线）**：`createRestrictedRetrievalService` 交付入口语义与验证；HTTP 路由/现有 kb handler 接线属下游消费票（与 MT009/MT011/MT015/MT036 D 同判例：接口冻结，生产装配不接无人消费的死代码）。测试内接的是**真实 hybridSearch + 真实 qdrant 检索引擎**（仅 QdrantClient 为内存替身），检索管线代码路径全真。
- **D7（向量命名空间的实现口径）**：现架构为 A8 单维度单 collection + payload filter 隔离（部署级基础设施共享，Spec「路径前缀/ID 编码只用于寻址」）。本票的「命名空间按归属隔离」落在 filter 的授权投影上：候选集合是命名空间的可达边界（wire 层断言钉死）；MT015 `scopedVectorNamespace`（vn-<40hex>）是物理集合/命名空间命名原语，若未来拆分物理命名空间，其键由同一归属事实派生——本票不预接（无消费者，不接死代码）。
- **D8（凭据与容器）**：`ent_mt037_kb` 与三个 `ent_mt037_*` 登录口令仅存 0600 临时 env 文件（/tmp/mt037-env.sh），报告与 checkpoint 零口令落盘；受限登录可由 enterprise-test-db.ts migrate + provision-db.sh 在新容器确定性重建。**容器按 brief 纪律真实删除**（见 §6 回显存档）。
