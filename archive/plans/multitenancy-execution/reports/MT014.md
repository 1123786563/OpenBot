## 1. 设计要点

### 1.1 解析 seam（新文件 `server/src/enterprise/tenancy/runtime-config.ts`）

四件事，全部纯新增（无既有文件被改动到此文件外）：

1. **公司运行配置模型**（`CompanyRuntimeConfigDocument`）：`model`（provider / credentialRef / defaultModel / allowedModels 能力面）、`botDefaults`（availableAgentIds / defaultAgentId）、`credentials`（引用登记表，`access: "company" | "personal"`，**只有引用没有值**）、`planMapping`（billingExternalCustomerId + plan，公司级，团队不可覆盖——一家公司一个余额，ADR 0004）。线程标识不是可声明字段：`threadIdentitySeed` 由入参归属 `(tenantId, workspaceId)` 确定性派生（`JSON.stringify([tenantId, workspaceId])`）——两家公司声明同一个种子也不能让线程串门；下游把种子交给既有 `createThreadIdentity`（channels/thread-identity.ts，未改动）。
2. **文档解析**（`parseCompanyRuntimeConfigDocument` / `parseTeamRuntimeOverridesDocument`）：严格形状；未知键一律拒绝（把误放进配置的机密挡在门外）；能力面内部一致性（默认模型 ∈ 开放面；model.credentialRef 必须指向 `access="company"` 的登记条目——公司模型调用永不骑在个人凭据上）。**所有拒绝消息只含代码、字段路径与索引，绝不回显任何值。**
3. **纯解析函数**（`resolveRuntimeConfig`）：只依赖入参；团队覆盖只能收窄——allowlist 覆盖必须是公司 allowlist 子集（`OVERRIDE_WIDENS_POLICY`，含索引不含值）、默认模型必须落在有效（收窄后）allowlist 内、默认 Bot 必须是公司已发布 Bot；空 allowlist 覆盖拒绝（`OVERRIDE_MODEL_ALLOWLIST_EMPTY`——收窄到空等于把团队运行时关掉，那是公司管理动作）；覆盖条目解析后固定 `access: "team"`（覆盖文档里没有 access 字段可声明）；引用公司 `personal` 条目 → `PERSONAL_CREDENTIAL_NOT_UPGRADABLE`（个人凭据绝不因覆盖升级）；遮蔽公司条目 → `OVERRIDE_REDECLARES_COMPANY_CREDENTIAL`。输出深冻结（调用方拿到不可变快照，缓存键 `runtime-config/v1/t=…/w=…/c=<companyRevision>/o=<overrideRevision|->` 含实际归属及配置版本，Spec §6）。
4. **受限角色读取服务**（`createRuntimeConfigService`）：`assertDataDatabase` 拒绝未验证通道（`UNVERIFIED_DATABASE_CAPABILITY`）；每次 resolve 一个数据事务（read committed + lock/statement timeout + 事务本地 `app.tenant_id`，与 store.ts / resource-policy.ts 同款事务形状），经 RLS 读公司配置行与覆盖行；**缺行 = `RUNTIME_CONFIG_NOT_FOUND`——多租户模式没有旧默认回退**（RLS 让「别的公司的配置行」与「不存在的行」同为 0 行，不存在与跨公司不可见对外不可区分）。缺 selector → `TENANT_REQUIRED` / `WORKSPACE_REQUIRED`（与 MT005 语义同源）。

### 1.2 存储面（新文件 `server/src/db/schema/enterprise-runtime-config.ts` + MT014 迁移）

- 两张新表（expand-only）：`enterprise_runtime_configs`（一行 = 一家公司，FK → `enterprise_tenants` cascade，`document jsonb` + `revision` CHECK > 0）与 `enterprise_runtime_config_overrides`（一行 = 一个团队，复合 FK → `enterprise_workspaces` cascade）。`enterprise-tenancy.ts` 本体零改动（brief 冻结遵守）。
- 最小 RLS：REVOKE PUBLIC + 四角色、ENABLE + FORCE、data 角色租户范围 SELECT（override 的 operator UPDATE 另要求 `app.workspace_id` 上下文）、operator 租户范围读 + INSERT/UPDATE、列级 `GRANT UPDATE (document, revision, updated_at)`；**目录角色无任何策略与授权**（配置不是逐主体目录数据）。经 migrate-test 的 **MT014 任务**真实执行（0001 建表 4 语句、0002 RLS 20 语句，manifest digest 见 `checkpoints/MT014/generated/`）。

## 6. 诚实披露

- **D1（index.ts / config.ts 零改动，决策而非遗漏）**：票面是「按公司/团队解析，**而不是**启动时装配一份全局配置」——解析是按调用装配，进程级装配段正是本票要移除的形态；下游业务闭环在各自票里通过 `createRuntimeConfigService(data)` 取配置（接口即本票冻结面），现在 index.ts 没有真实的消费者，追加一个未被读取的服务实例是死代码，且与验收 4「无进程级全局状态」背向。成本：MT013 启动段与遗留租户包装配的替换本身不在本票范围（brief 可写清单只授权「装配段纯追加」而非替换），接口已就绪。
- **D2（窄例外，brief 预授权第 4 次先例）**：`migration-tool.test.ts:352` 穷举断言按裁决 #5 同一先例追加 `"MT014"` + 裁决注释；pristine 重建副本哈希证明文件其余字节未动（`changes.diff` 0 删除）。
- **D3（写路径经 operator 角色，读路径是生产面）**：公司配置/覆盖的写 API（公司管理设置流）属后续 Ticket；本票测试写入经受限 operator 角色走真实 RLS INSERT/UPDATE 策略（非 superuser 旁路；套件收尾 `current_user` 断言覆盖每一条写入）。
- **D4（夹具脚手架）**：两家公司 + 三团队经真实 `provisionDeployment`（operator 通道）创建；公司/团队实体行本身由该既有工厂路径落库，非本票新引入的旁路。
- **D5（MUT2 假跑）**：变异脚本首次运行漏 `source` 测试库 env，产生一次全 skip 假跑（skip ≠ 通过，exit 0 无意义）；已用带 env 的有效运行覆盖存档（exit 1），README 有记录——与 MT112 §7.5 同款操作事故，如实留档。
- **D6（空 allowlist 语义）**：空团队 allowlist 被拒绝（`OVERRIDE_MODEL_ALLOWLIST_EMPTY`）而不是解析成「无模型可用」：解析产物必须始终携带可用默认模型，把团队运行时整体关掉属于公司管理动作而非团队覆盖的表达范围；该语义在测试与模块头注均有钉死。
- **D7（afterAll 关闭顺序）**：套件 `extraClosables`（验收 4 的第二 data 通道）在 fixture dispose 后关闭； dispose 失败会聚合抛出（不吞错）。
