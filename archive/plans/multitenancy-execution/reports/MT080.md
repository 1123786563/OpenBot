## 1. 设计要点（详见 `checkpoints/MT080/design.md`）

### 1.1 数据契约与状态机（新文件 `app/src/lib/enterprise/tenant/selection.ts`，纯新增）

- **选择器数据契约来源（披露 D1）**：唯一事实源 = MT006 的 **`GET /api/enterprise/workspace-scope`**（`server/src/enterprise/tenancy/workspace-scope-routes.ts`，挂载 `server/src/app.ts`），响应形状 = `WorkspaceScopeListing { companies: [{ tenantId, name, role, memberEpoch, teams: [{ workspaceId, name }] }] }`。服务端钉死：无 current/default/selected 字段（MT006 review AC2 反射断言）；资格 = tenant+principal+membership 三个 active；suspended 公司整公司隐藏、suspended 团队单团队消失（MT006 review AC1）。该端点**没有 shared schema 文件**（`shared/enterprise/mobile-schemas.ts` 是旧移动端 chooser 契约，不含 teams），故 wire 类型在客户端模块本地声明，漂移由测试钉住 fixture 形状兜底；列表读对 200 但非列表形状的回答抛 `WORKSPACE_SCOPE_MALFORMED` 拒绝——**坏响应体绝不读成"你没有公司"**（本仓测试反复狙杀的 empty-state 谎言）。
- **选择头（MT005 裁决 #1）**：`x-openbot-tenant` + `x-openbot-workspace` 只做选择、成员资格数据库判定。`client.ts` 原只有 `tenantId`；本票**新增 `workspaceId` 选项**，与 `tenantId` 完全同一同源纪律（仅相对 `/api/enterprise/` 路径附加；绝对 URL/`//`/非企业路径一律丢弃），由测试钉死（含 cross-origin 拒绝）。本票页面自身消费的唯一端点是列表（不读选择头）；`workspaceId` 头是选择对后续范围读消费方的交付接口。
- **撤权态判定依据（披露 D2）**：**判定 = 所选 (tenantId, workspaceId) 是否仍出现在新拉取的列表中**（`findSelection` 纯函数），不解析业务读错误码。依据：server lister 本身就是实时资格事实且无存在性泄露（RLS 自读）；撤权在公司级 = 整公司消失、团队级 = 单团队消失。列表读失败（401/500/503/网络）是**失败态**（可重试），绝不伪造成授权事实——基础设施故障与撤权是两种状态、两张脸。撤权界面：明确标题 + 说明 + 「重新核查」（重拉列表复核）+ 选择器保留供显式改选；**绝不静默清除选择、绝不自动改选其他范围**。
- **状态机**：`selectionState(listingRead, selection)` 纯函数，六种 `kind`：`loading`（列表 in flight）→ `error`（明确文案 + Retry）→ `empty`（companies 为空：无资格空状态 + 联系管理员引导，**不渲染选择器**）→ `ready`（有资格但未选择：双选择器全占位，**绝不自动选第一项/默认团队**，A6）→ `selected`（选择两半均命中列表：选择器 + 「当前工作范围」摘要含公司/团队/角色）→ `revoked`（如上）。公司选了但该公司无团队时另有 `selection.team.none` 引导文案。
- **选择来源**：URL 参数 `company`/`team` 为权威（深链、新标签页同规则，A10）；`selectionFromSources` 规定：URL 任一参数在场则 localStorage 不参与；仅 `company` 无 `team` 是**不完整范围**（= 无选择），绝不用存储的一半拼补。localStorage 按 userId 隔离（`openbot.workspace-scope.v1:<userId>`），只记录用户显式完成的选择，损坏/变形一律读作 null，绝不发明选择。

### 1.2 切换纪律（延续既有 chooser + generation 设计）

- **共用同一 generation**：`selectWorkspaceScope` 推进与 `selectTenant` **同一个** `tenantKeys.generation(userId)`。跨公司切换（含与"无选择"互转）直接复用 `selectTenant`（推进 generation + 丢弃旧公司整棵 scope 子树——连带既有 channels 面缓存）；同公司换团队推进 generation 并仅丢弃旧团队 `:workspace` 子树（保留仍属用户的兄弟团队缓存）。任何切换先推 generation 再删缓存，旧范围在途响应按既有 `TenantSelectionChangedError` 语义被拒——用**既有** `channelsQueryOptions` 作守卫消费方在测试里钉死跨面行为（A10）。
- **缓存键**：`selectionKeys.workspaceScope(u,t,w) = [...tenantKeys.scope(u,t), ":workspace", w]`——挂在既有 tenant scope 前缀之下（公司切换的既有删除自然覆盖它），保留 token 带前导冒号（与 tenantId 字符集不可能碰撞），同一键树、一个删除纪律。
- **页面**（`app/src/routes/_authed/tenant/selection.tsx`）：URL 权威 + storage 兜底 → 纯状态机 → 按脸渲染。切换 commit 顺序：`selectWorkspaceScope`（generation++ + 缓存删除）→ `storeSelection`（显式选择才写）→ `navigate`（URL 更新，TanStack 客户端导航，无整页刷新）；选择器选项即列表原文（跨公司用户看到各自条目与各自团队）；关闭态触发器标签由已解析名称渲染（Widget 关闭时选项不存在，原始 id 仅在撤权态如实可见——不静默替换成其他范围）。

## 6. 诚实披露

- **D1（选择器数据契约来源）**：如 §1.1——事实源 = MT006 `GET /api/enterprise/workspace-scope` 及 `workspace-admin.ts` 的 `WorkspaceScopeListing` 接口；该契约无 shared schema，客户端 wire 类型本地声明 + 测试钉 fixture 形状 + 运行时形状守卫（malformed → 拒绝）三层兜底。若后续票为该端点补 shared schema，应以此处类型对齐收敛。
- **D2（撤权态判定依据）**：如 §1.1——判定 = 选择对在新列表中的在场性（server lister = 实时资格事实，MT006 review AC1/AC2 钉死的行为），不解析业务读错误码。服务端既有契约中，范围业务读的撤权对应 `SCOPE_REVOKED`/`WORKSPACE_REVOKED`（事务层）→ conversations 路由映射为 403 "forbidden"；workspace-scope 管理路由保留 `TENANT_FORBIDDEN`/`WORKSPACE_FORBIDDEN` 等码 403。本页面未消费这些端点，故未依赖其错误码形状；后续范围读票若需在请求粒度细分撤权与越权，应扩展 `WorkspaceScopeRefusedError` 携带的 code 而非另起炉灶。
- **D3（workspaceId 头暂无页内消费方）**：本票页面消费的唯一端点是列表（契约规定其不读选择头）。`client.ts` 的 `workspaceId` 是选择对的传输半边，供既有 `channels` 面与后续范围读票使用；接口已冻结（同源纪律与 tenantId 完全一致并有测试），接线按签名即可——与 MT079 D1（seam 先行、装配后接）同一判例。
- **D4（选择持久化的双源）**：URL 为权威（深链/新标签页，A10），localStorage 只在 URL 完全静默时兜底、且只记录用户显式完成的选择。这是「选择持久化」与「绝不自动选择」的交点解：无 URL 且无存储 = 无选择（ready 态占位），绝不恢复出一个用户未曾做过的选择。localStorage 写失败静默吞掉（URL 仍持有选择，镜像属 best-effort）——如实说明，非静默范围回退。
- **D5（未做变异轮）**：如 §5——取舍理由如上；GREEN-1 的 5 个真实断言失败提供了「测试能抓实现/断言偏差」的直接证据。
- **D6（routeTree.gen.ts 的改动归属）**：生成物由 vite 插件在 build 时重写，本票以 `git diff` 核验为**纯追加 21 行**（新路由注册），无其他漂移（`changes.diff`）。
- **D7（全量套件 4 个既有 fail）**：与本票无关的证据链见 §4 第 5 条（隔离单跑全过 + stash 基线同 4 fail + 账目吻合）。未顺手修复：不属本票 Scope，且该 3 文件与其他票并行面无授权。
