## 1. 设计要点

### 1.1 键派生 seam（新文件 `server/src/enterprise/tenancy/scoped-keys.ts`，纯新增）

四种作用域键 + 一个共享入口，全部纯函数、深冻结输出为 string、绝不读进程环境：

| 入口 | 键形（v1） | 用途 |
| --- | --- | --- |
| `scopedCacheKey(ownership, domain, logicalKey)` | `scoped-cache/v1/t=<tenant>/w=<workspace>/c=<company>/o=<override\|->/<domain>/<digest40>` | 缓存键 |
| `scopedEventChannel(ownership, domain, logicalKey)` | `event-channel/v1/…同上…/<digest40>` | 事件通道名 |
| `scopedObjectPrefix(ownership, domain)` | `object-prefix/v1/…/<domain>/`（目录形，尾随 `/`） | 对象存储前缀 |
| `scopedVectorNamespace(ownership, domain)` | `vn-<digest40>` | 向量命名空间（受限字符集摘要形，与 tenant-storage 的 schema 名派生同款；归属/版本/域全部进摘要输入） |
| `sharedInfrastructureKey(domain)` | `shared/v1/<domain>` | 连接池/模板/静态目录等部署级形态——**类型上就不接受归属参数**，「共享」是显式入口而非遗漏（验收 4） |

结构上的硬性规则（模块头注钉死）：

1. **键对身份单射**：归属与配置版本（MT014 runtime-config 的 `revisions: {company, override}`）原样进入键；绝不静默 trim/归一化——归一化会把两个身份折叠进同一个键（跨范围污染）。空白/越界/携带键形语法字符（`/`、`=`、控制字符、非 ASCII、`.`、`..`、129 长度等）一律响亮拒绝：`TENANT_REQUIRED`/`WORKSPACE_REQUIRED`（与 MT005/MT014 同码）+ `SCOPED_KEY_INVALID_TENANT_ID`/`…_WORKSPACE_ID`/`…_CONFIG_VERSION`/`…_DOMAIN`/`…_LOGICAL_KEY`。
2. **键只做寻址，不做保险箱**（Spec §6「路径前缀/ID 编码只用于寻址」）：归属 ID 是系统标识符，原样入键供运维寻址；而调用方提供的逻辑键段内容不受本模块控制、可能意外携带机密——因此逻辑段只以单向摘要（SHA-256 截断 40 hex，`JSON.stringify([logicalKey])` 为摘要输入）入键：明文不出现、不可反推（验收 3）。派生 API 的输入形状里根本没有凭据字段。kind 前缀互不相同 → 同域同参跨 kind 不碰撞；共享键形与所有作用域键形不相交。
3. **配置版本注入**：`scopedKeyOwnership(resolved)` 适配器从 MT014 解析产物（`Pick<ResolvedRuntimeConfig, "scope" | "revisions">`）提取归属事实，公司/团队覆盖 revision 变化 → 键变化 → 旧条目在新键下结构性不可达（验收 2）。runtime-config.ts 本体零改动（只读消费其导出类型）。
4. **拒绝零回显**：所有拒绝消息只含代码 + 规则文本，绝不回显任何输入值（canary 验证）。

## 6. 诚实披露

- **D1（index.ts / config.ts 零改动，决策而非遗漏）**：本票交付的是键派生 seam 与其验证；缓存/通道/对象前缀/向量库的**消费方装配**（谁调用 `scopedCacheKey` 等）属后续各业务票（票面备注：客户端侧缓存与在途响应在 MT083/MT104/MT105）。在本票往 index.ts 追加一个无人读取的实例是死代码，且 brief 的 Ownership 明示「新文件优先」、未授权 index.ts 装配段之外的动作，故不装配。接口已冻结，消费方按签名接入即可。
- **D2（测试文件名）**：brief 未指定文件名；Issue #58 的 Verification 命令点名 `cache-keys.test.ts`，故按票改名对齐（实现模块名 `scoped-keys.ts` 为本票命名，票面未约束）；改名后聚焦/全量/变异复核全部在终字节重跑留档。
- **D3（fresh-DB 首跑基线不稳）**：容器首跑全量出现 19 个失败，逐条为各套件 beforeAll 迁移在空 journal 上的竞态（一次性；无业务断言失败）；第二、三次运行 458/0 全绿。与 MT010 记录的同一现象；基线证据取稳定绿跑，首跑原始输出存档。
- **D4（假跑与无效突变体）**：MUT5 首跑为假跑（runner 先还原后运行，exit 0 无意义）；MUT1 首次未应用、MUT2 首次语法非法（模块加载崩溃被计 0 pass/1 fail——崩溃不是捕获）。三者全部识别、修正、重跑，README 留档——与 MT014 D5 / MT112 §7.5 同款操作事故披露。
- **D5（票号修正）**：模块/测试头注最初把票号误写为 #168（凭记忆猜测，未核实）；开工中途 `gh issue view 58` 核实真实票号后更正为 #58。该更正仅动两行注释，与变异靶向区域无关，但仍在终字节上复核 MUT3 捕获以自证。
- **D6（共享键无部署纪元）**：`shared/v1/<domain>` 不携带部署级 epoch/版本——票面与 Spec 的共享形态（连接池/模板/静态目录）按部署全局复用，未要求失效语义；若未来需要部署级失效，属新票的键形扩展（v2 前缀位已留）。
- **D7（逻辑段摘要的可运维性取舍）**：逻辑键段单向摘要意味着无法从键反查业务含义——这是「键中不含明文凭据、不可反推」的结构性代价（验收 3 的实现面）；归属/域/版本保持可读以保留运维寻址。已在模块头注钉死为设计决定。
- **D8（keyed-cache 是测试脚手架）**：`createKeyedMemoryCache` 只存在于 `support/`（测试专用），不进生产——票面交付物是键而非缓存实现；命中/未命中演示证明的是键的可达性边界，不是缓存产品。
