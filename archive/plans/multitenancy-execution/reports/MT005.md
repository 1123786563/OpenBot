## 1. 设计要点

### 1.1 签发入口（issuance，`createScopeResolver.resolve`）

落点完全遵从 `reports/seam-identification-mt005.md`：真实租户 seam 是 `server/src/enterprise/tenancy/store.ts` 的 `createScopeResolver`。在其目录事务内**纯追加**两段：

1. **选择子拆分**：原 `if (!tenantId || !workspaceId) throw TENANT_REQUIRED`（双义）拆为 `!tenantId → TENANT_REQUIRED`、`!workspaceId → WORKSPACE_REQUIRED`（seam 报告 §6-5 与 T02 契约；fixture 的错误表早已预留 `WORKSPACE_REQUIRED→400`）。
2. **团队资格判定**：公司成员校验通过后，同一目录事务内查 `enterprise_workspace_memberships`（`(tenant, workspace, principal)` 必须存在且 `status='active'`）。行缺失、行 suspended、workspace 不存在三种情况统一抛 `WORKSPACE_FORBIDDEN` —— 不泄露存在性。`set_config` 追加 `app.workspace_id`（事务本地）。

签发信任机制未动：`issuedScopes = WeakSet` + `Object.freeze` + `assertTrustedScope`（进程内信任边界）。`PlatformScope` 形状未改（MT004 契约）。

### 1.2 业务事务半边（`createWorkspaceGate`，新文件 `tenancy/scope-gate.ts`）

完全复刻 `conversations/store.ts` 事务形状（seam 报告 §2.2「标准形状」）：

```
assertTrustedScope
→ data.transaction
→ set transaction isolation level read committed / lock_timeout 2s / statement_timeout 5s
→ set_config('app.tenant_id'|'app.principal_id'|'app.user_id'|'app.workspace_id', …, true)   -- 全部事务本地，提交即清除（RLS 纵深防御）
→ advisory 共享锁：tenant → principal → membership → workspace-membership                     -- 顺序 = 既有两处 + 新键插在 membership 后
→ 公司成员重验：memberStatus/principalStatus/tenantStatus 全 active 且 epoch === scope.memberEpoch，principal.user_id = scope.actorId → 否则 SCOPE_REVOKED
→ 团队成员重验：行存在且 status='active' → 否则 WORKSPACE_REVOKED（operation 不执行）
→ operation(tx)
```

新 advisory 键型 `["enterprise","workspace-membership",tenant,workspace,principal]`，与离线管理写路径（本 fixture 的 suspend/remove/epoch-bump）的**排他锁**同键：闸门事务持共享锁期间撤权写被串行化（测试用 `lock_timeout` 探针确定性证明），撤权提交后同键下一事务立即拒绝。裁决 #2 遵守：不引入任何策略版本常量，无 `conversations-v1`。

## 5. 诚实披露

- **D1（MT002 交付文件的两处集成）**：`support/fixture.ts` 纯追加三块（头注释更新、向真实 MT004 表插入按计划矩阵的团队成员行——经受限 operator 角色、RLS 校验；`ROUTE_ERROR_STATUS` 追加 `WORKSPACE_FORBIDDEN→403`、`WORKSPACE_REVOKED→403`）；`fixtures.test.ts` 仅改 2 处断言（跨团队读取、company-admin 读取：404 `RESOURCE_NOT_FOUND` → 403 `WORKSPACE_FORBIDDEN`）。这是票面契约的直接结果——MT002 时代「团队资格=per-team grant」是 MT004 前的临时事实（fixture 头注释自述），MT005 后资格=真实团队成员行。不集成则回归 0-fail 要求无法满足；其余 19 个 MT002 断言未动。
- **D2（`resolveForThread` 未扩展）**：遗留线程发现路径不改——MT004 之前存在的会话没有团队行，扩展会让既有语义静默收紧（违反 expand-only）。gate 的判定面 = `resolve()` + 业务事务，与票面「集中入口 + 同事务重验」一致；线程路径的团队判定属后续接线任务。
- **D3（团队 epoch 未入 scope）**：`PlatformScope` 形状 MT004 已定（memberEpoch 为公司成员 epoch），团队成员 epoch 无法在不改形状的前提下钉入 scope。团队级重验 = 行存在 + active，覆盖移除（行删）与停用（status）；公司级 epoch 等值已钉死并被变异测试捕获（M4）。团队 epoch 一致性（如「重授予后旧 scope 仍过 gate 直至下一次 resolve」）需 MT008 级别的 scope 形状决策，现由「gate 每次业务事务重验 + 锁串行化 + 下一次 resolve 重新签发」缓解。
- **D4（管理写路径的替身）**：fixture 的 suspend/remove/epoch-bump 走专用测试 setup 连接（超级用户）。原因：operator 角色对该表无 DELETE policy、UPDATE policy 需要 `app.operator_principal_id` 上下文而生产尚无团队管理写路径（MT004 只交付 schema）。超级用户绕 RLS 是该离线通道的诚实替身；排他 advisory 锁纪律与生产一致。测试证据不受影响——**判定侧**（resolver/gate）全部经受限 directory/data 角色真实 RLS 得出。
- **D5（存量 lint）**：index.ts/store.ts 的 7 处 biome 发现为 HEAD 存量（快照比对证据在会话记录），不在本票范围，未动。
- **D6（skip 不是通过）**：唯 1 个 skip 是 MT003 assigned-db 集成用例，缺 `MT003_ASSIGNED_TEST_DATABASE_URL`，原因写入用例名。
