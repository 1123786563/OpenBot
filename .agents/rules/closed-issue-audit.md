# 已关闭 Issue 的 Agent 验证与待人审标签

用户要求审计 `1123786563/OpenBot` 中已关闭且带 `ready-for-agent` 的 Issue，或核对、添加 `agent:ready-for-review` 标签时读取。此规则用于回溯验证；不把 `closed`、PR merged、历史测试通过或已有标签当作当前交付证据。`agent:ready-for-review` 的含义是“已由 Agent 验收通过，待人审”，不表示人工批准。经 Orca 派发审计或修复时，Agent 选择以 [Orca Agent 选择](orchestration-agents.md)为准。

## 1. 冻结范围和代码版本

1. 分开冻结两个集合并逐集合分页、排除 PR：新审集合 N 为 `state=closed` 且带 `ready-for-agent` 的全部 Issue（含首次遇到的 completed、not_planned、作废和关闭原因不明票）；标签对账集合 R 为任意状态下带 `agent:ready-for-review` 的全部 Issue，加共享 Ledger 的待标签写入/纠正对象。R 不以 closed 或 ready-for-agent 为过滤条件，重新打开、移除资格标签的票仍可触达。保存查询起止时间、条件、页数/游标、数量、编号/URL、去重结果和完整性；搜索上限须拆分查询核对，缺页/无权/转移读取不全记 `intake_incomplete`。本轮冻结全集为 N∪R；结束前重新对账新增、移除和状态变化，新增项登记下轮队列及发现时间，不暗中扩大本轮容量。
2. 先对账已有 Run、报告、标签回执、Git 和活跃工作区。已有结论只能在其需求、目标代码、环境及证据仍然一致时复用；记录每项“复用、重验、失效”的依据，不重复派发已有效完成的审计。
3. 按 [delivery-gates.md](delivery-gates.md)固定原 Issue 约定交付目标（默认 origin/main）的完整 SHA、子模块 SHA、环境和工作区基线。审计与测试使用该版本的字节一致隔离树；代码或服务已漂移时重建环境。记录共享数据库、端口、容器和测试产物的归属，按 [验证与测试资源](testing.md)隔离或串行使用。

## 2. 逐票摄取和验收

每票按[Issue 摄取](issue-delivery.md)的只读规则读取正文、验收、评论中的已确认决定、关闭原因、正式子 Issue、依赖和相关 PR/提交；每种集合分别处理分页、去重、读取时间及完整性，递归子项也不能只取首屏。按 [设计与事实源](design.md)核对有效批准版本及 `CONTEXT.md`。区分 `contains` 与 `depends_on`，普通引用需核实关系。建立 `Issue → 每条验收 → 目标 SHA 中的实现/交付物 → 验证方法 → 证据` 映射；只读摄取不授权实施。

- `completed` 票进入交付验收。`not_planned`、作废、撤回、转移或关闭原因不明的票先核实需求是否仍有效、是否另有明确的交付完成决定；没有该决定时记 `unproven`，不贴标。
- 父 Issue 递归读取正式子项，逐项保留独立结论；每日容量及跨日 aggregate_pending 按 [每日规则](closed-issue-daily-run.md)执行；父票另验自身独有要求和组合行为。子票不因父票未通过而自动失败。
- 需求冲突、子项读取缺失或验收无法定义时保留经脱敏的来源证据、受控原文引用与缺口；不以未知代替“无要求”。

非 Orca 也须由与本票实现者及当前主控不同的独立审核者，以新会话/Brief 执行行为验收和代码审查；历史实现身份不可核实时记录独立性缺口，不能默认满足。主控只核对证据并裁决，不以自审代替独立性；审计者不得接手本票修复。Orca 身份按其 Agent 规则核验。

单票按以下顺序验证：

1. 将每条验收写为可观察结果，选择正常、拒绝、边界及适用的权限、并发、持久化、回滚场景。设计或文档票核对批准的交付物与决策验收。
2. 追溯当前 SHA 中的代码、配置、迁移和实际装配调用链，检查关闭后的变更是否撤销或改变行为。独立审查正确性、安全、兼容性和回归；跨票缺陷若使本票行为不可达，也计入本票结论。
3. 实际运行适用的最小相关测试、类型检查、Lint、构建和真实 API/UI/服务验收。运行前读取 [验证与测试资源](testing.md) 及其指定 ADR；保存命令、退出码、实际执行/失败/跳过数、脱敏日志、受控原文引用与环境。静态阅读只支持代码判断，不能充当行为验收。
4. 主控按 [review.md](review.md)对验收映射中的实际实现/装配范围执行 OCR，保存输入清单、覆盖对账和裁决；通用非 Orca 审计也不能省略此项。
5. 按 [目录与产物归处](artifacts.md) 保存单票报告和原始证据，记录目标 SHA、时间、输入、预期与实际结果、代码位置、文件哈希及本轮资源清理复查。主控独立核对报告、原始日志、哈希和目标 SHA。

## 3. 裁决和贴标

每条验收标记 `verified / failed / blocked / unproven / not_applicable`；`not_applicable` 附事实源依据。单票仅在所有适用条款 `verified`、实际运行所需依赖成立、目标 SHA 的 Required Checks/标准 CI 有效、无有效 critical/high/medium finding、独立审查与完整 OCR 及主控证据对账通过时为 `verified`。父票还须通过聚合验收。环境无法运行记 `blocked`，仅有推断记 `unproven`；任一失败或缺口均不能折算通过。

当本轮请求授权 GitHub 贴标时，主控对 `verified` 票执行以下写入门禁：

1. 按 [delivery-gates.md](delivery-gates.md)核对交付目标、需求批准权限、CI 和人审可访问证据，持久保存含需求指纹、目标 SHA 和预期资格/状态的写入意图。已有标签也须核验。
2. 添加标签并保留 `ready-for-agent`；写后按共同协议完整 rescan，只有意图条件仍成立才算有效。API/回读不明为 `label_pending`；失配为 stale，并按授权纠正，否则 `label_correction_pending`。操作者、时间、URL、前后版本、证据索引及回执均留档。
3. 对 `failed / blocked / unproven / intake_incomplete` 不添加标签。重新打开、移除 ready-for-agent、无交付完成决定的 not_planned 或证据过期等使已有标签无效时，进入 R 的纠正分支；按现有移除授权只移除该待人审标签并复核，不改其他标签。无授权或回执不明保留 `label_correction_pending`，不报告纠正成功。
4. 验证结论与交付/标签动作分列，状态契约和仅标签恢复见 [每日规则](closed-issue-daily-run.md)。有效证据未变且只剩贴标/回读/移除时，只做标签对账和必要 rescan；不重跑整票验收。若需求、目标树或 CI 失效则转重验，不能用标签重试复活旧 verified。

审计只读代码和测试源文件；修复缺陷另立范围，修复后重验受影响条款。本规则不扩大 GitHub 写入、提交、关闭 Issue 或清理资源的授权。

## 4. 完成和记录

按 [目录与产物归处](artifacts.md) 在 `.archive/runs/<run-key>/` 保存完整候选清单、逐票事实源和验收矩阵、Ledger、报告、验证日志、finding 裁决及标签回执。最终报告列候选数、已摄取数、各结论数、已贴标与 `label_pending` 数、已有标签复核/移除数、`label_correction_pending` 数、未审编号、结束前新增待下轮清单和每票可访问证据入口。仅在冻结 N∪R 逐票有结论、父票聚合已完成且所有授权动作通过写后条件复核时，报告“冻结范围审计完成（截至时间/清单哈希）”；分批结束时只报告该批确切范围，未授权或失败的纠正明确列为待处理。
