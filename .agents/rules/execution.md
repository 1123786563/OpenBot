# 实施、派发与上下文

编写实施计划、实现、修复、派发或恢复任务时读取。以 Issue 为依据时先完成[只读摄取](issue-delivery.md)，实施权限以当前用户授权为准。

## 先分档

开工时说明范围、风险和所选档位；已知事实足够时直接执行，不为选择档位增加确认轮次。按实际影响选择最高适用档位，不能用文件数或代码行数降低风险。

| 档位 | 适用条件 | 最低流程 |
| --- | --- | --- |
| 轻量 | 范围明确、单模块、可逆的局部修复或小改动；沿用已确认行为，不改变公开接口、跨模块合同或下列高风险边界；纯文档排版/错字也适用 | 当前 Agent 实施 → 最小相关验证 → diff 自查 → 说明结果和限制 |
| 标准 | 不属于高风险的一般功能、跨文件行为修改或接口调整 | 简要计划 → 实施 → 相关验证 → 一次独立 Spec/质量 Review |
| 完整 | 身份权限、租户/沙箱隔离、计费与支付、持久化写入/事务/迁移/事实所有权、部署发布、关键运行链路或运行依赖变更；改变授权、验证、审查、交付门禁的规则/配置；Orca 多 Agent 编排 | 完整计划与必要隔离 → 实施 → 独立行为验证与 Review → 集成验收及适用 OCR |

轻量不要求另建 Issue、方案文件、DAG、Run、Worktree 或子 Agent；标准计划可放在消息或已有 Ticket 中，写清步骤、文件和验收即可。跨会话/多人接力时再持久化计划和进度。完整计划使用 `writing-plans` 或下述等价流程，存 `docs/plans/`，包含事实源、约束、编号 Task、依赖、接口、文件所有权、验收和失败处理。

风险不明时先定向核验；执行中触及更高档边界时升级流程并补齐缺项。各档均保留授权、他人改动、测试隔离和真实验收要求；额外的用户要求及批准 Spec/ADR 门禁继续适用。[Orca 编排](orchestration.md)、[已关闭 Issue 审计](closed-issue-audit.md)和[每日自动化](closed-issue-daily-run.md)采用其专用强约束，不以本表降低。新规则不自动改写活跃 Run 的既有契约，恢复时核对策略变化和证据影响。

## 工作区、技能与计划

1. 先核对 Git 基线、已有改动和相关事实源；领域、架构规则按实际改动加载。适合的当前工作区可直接复用。多写入者、跨分支集成或用户要求隔离时再建 Worktree，Orca 工作区按 [worktrees.md](worktrees.md)操作。
2. 只检查当前路径实际需要的技能和工具。系统/开发者或用户明确要求的技能按其约束执行；仓库默认技能缺失时，记录缺口并采用等价步骤，不重复请求许可或编造调用回执。
3. 完整流程的等价步骤是：有验收的编号计划、必要隔离、范围明确的实施、独立验证/Review、可还原检查点、适用 OCR 和保全后收尾。独立性、真实验证、授权及适用 OCR 不由自查替代。所需能力确实不可用时只阻塞受影响阶段，继续可独立完成的工作。
4. 单 Agent 可按计划直接实施；多任务派发使用当前可用的 SDD，Orca 用其监督式 Task/Dispatch，一个阶段只用一个派发器。主控可完成已授权的局部修复，不为每个 finding 另起完整方案；专用编排内仍走原任务的修复路径。

用户已要求实施时，展示必要计划后继续执行。仅计划/仅 Review 不启动代码修改。提交、推送、合并、发布和 GitHub 写入依当前授权，不由计划或工作区创建推导。

## 验证与审核

实现者负责适用的 RED → GREEN → REFACTOR、针对性检查和自查；测试按 [testing.md](testing.md)选择相关范围。标准流程由一次独立 Review 检查 Spec compliance 与 code quality；完整流程增加独立行为验收，验证者与 reviewer 可为同一独立会话，报告分列行为、Spec、质量结论，无需为角色名另开会话。多任务集成须验证实际组合结果，完整终审的触发与证据承接按 [review.md](review.md)。

独立会话须不同于被审内容的实现会话，以必要事实源和冻结范围启动，不参与该范围的实现。验证者只读业务代码和测试源文件，可写指定缓存/报告。实现者自测不冒充独立验证。平台支持时选用可用专业角色；不支持时以 Brief 明确职责，记录真实会话身份和可核实配置，不制造 agent_type 或猜测模型。模型选择遵从当前可用能力与已有授权，不在通用规则固化型号。

有效 finding 的阈值、修复轮次、无进展处理和 OCR 统一见 [review.md](review.md)。

## 派发与恢复（仅需多 Agent 或跨会话时）

- 每个 Worker 接收单个自足 Brief：目标/验收、必要事实源、工作区及前置检查点、owned_files、接口、提交策略、验证和报告路径。干净会话启动；Worker 不再派发，主控统一安排审核。
- 默认串行实施。并行实现沿用已有明确用户授权，并满足接口、写权限、资源隔离和集成顺序；使用 Orca 或设并发上限本身不授予并行权限。
- 仅在跨 Run、共享资源或专用自动化场景加载[共享协调状态](coordination-state.md)。独占的本地临时目录和已证明隔离的测试资源不为登记而引入每日调度协议；归属或隔离不明时先核验，不视为空闲。
- 长日志、原始报告和执行状态归 [artifacts.md](artifacts.md)规定位置；消息只传新结果、阻碍和证据入口。保留唯一活动 Ledger，恢复先核对它、Git 和实际在途工作，避免重派已完成任务。
- 只有需要固定审查版本、转移或恢复内容时加载 [checkpoints.md](checkpoints.md)。无提交授权使用完整的未提交范围，不以空 BASE..HEAD 代替审查；下游必须取得全部前置内容。
