## 1. 结论

v0.1 不适合直接成为实施依据。共记录 **8 项问题：4 项 high、4 项 medium**。主要原因是遗漏了 OpenMuse 完整产品规格及对应 ADR，将早期移动端方案的抽象带入产品主规格，造成私有 Bot、双决策类型、两条记忆路径、五类任务及账号恢复等合同不完整。

v0.2 已补回这些文档约束和验收条件；在该轮结束时，R01 的多公司/团队私有 Bot 映射仍须产品/架构裁定。其他七项在本稿内完成文档修订，不代表其运行行为通过验证。用户随后对 C01 的明确选择和 v0.3 修订见 §6，不追溯为当时已经关闭，也不自动批准其他产品建议。

## 3. Findings 与处理

### R01 · high · 缺少私有 Bot 合同及企业范围映射

定位：v0.1 §1.1–1.2、§4、§5；第 13、29、78、90 行。

依据：OpenMuse 完整规格第 24–27、67、69 行及 ADR 0004 要求首次进入幂等创建私有 Bot、受管理模板、隔离 Computer/工作目录；个人工具默认只授予私有 Bot。公司团队设计 §6 又要求公司、团队、个人之间不共享浏览器登录态或工作目录。

问题：v0.1 只定义逻辑入口和可用多个 Bot，没有明确保留私有 Bot，也没有说明原“一个用户一个 Bot/Computer”如何扩展至多公司/团队。实施者可能只做 Bot 聚合选择，或复用原全局私有 Bot 的环境，无法证明隔离。

处理：v0.2 §1.1–1.2、§5、D01 补回预配、模板及私有工具边界，新增 A28。§17 C01 明确列为待裁定：按范围分别预配私有 Bot，或通过显式范围隔离实际环境，须先确定映射、默认选择和迁移事实。

v0.2 审核状态：**部分修订，C01 未解决，阻断企业私有 Bot 预配合同冻结**。后续用户选择见 §6；保留此处原审核时点的结论。

### R02 · high · 通用“操作审批”掩盖 Reviewed 与 Policy 的不同合同

定位：v0.1 §3.2、§5、§8.3；第 70、93、176 行。

依据：OpenMuse 完整规格第 13、40、72、85 行规定 Reviewed action 与 Policy approval 分离；具体外部变更绑定目标版本、账号、连接 generation、到期及原子 claim，具有回执和未知结果处理。

问题：v0.1 只定义通用审批和一次消费，没有保留双决策所有者，也未明确连接代次、目标版本及并发 claim。相同邮箱断开重连，或目标内容变更后，旧批准可能仍被错误解释为适用；“一次使用”的描述不足以约束双执行者竞争。

处理：v0.2 §3.2、§5、§8.3 分开决策类型和执行领域，明确 generation、目标版本、原子 claim，以及外部效果发生但回执写入失败时不可重发的核对语义，新增 A29。

状态：**本稿文档修订完成**；原领域合同及实际并发/供应商行为仍需验证。

### R03 · high · 未区分 Hindsight 与 OpenMuse 精确 ID 私有记忆

定位：v0.1 §10.2；第 210–216 行。

依据：Hindsight 设计 §目标与范围明确排除 OpenMuse 精确 ID 私有记忆；OpenMuse 完整规格第 54、69、76 行及 ADR 0007 将个人上下文默认限定本人私有 Bot，其他 Bot 需单独授权。

问题：v0.1 将“完整继承个人记忆设计”和同公司跨 Bot 使用放在统一章节，没有区分被排除的存储。可访问其他 Bot 可能被误认为同时取得全部个人上下文，或将精确 ID 记忆自动迁入 Hindsight。

处理：v0.2 §3.1、§10.2 明确保留两路径及 Goals/Ideas 的私有 Bot 授权，禁止自动合并/迁移和互相降级绕过，新增 A30；§17 C02 记录跨规格边界。

状态：**本稿文档修订完成**；接口路由和界面类别仍须在领域合同中落实。

### R04 · medium · 五类 Task 与 Routine/Responsibility 边界不足

定位：v0.1 §2、§3.2、§9 T07；第 44、64、200 行。

依据：OpenMuse 完整规格第 75、86 行及 ADR 0006 规定独立 Task 模块拥有 `agent/document/finance/plan/monitor`，Responsibility 保留事件订阅职责；Monitor 有自己的条件、游标、观测去重和退避。

问题：v0.1 只列通用任务及三类验收场景，并写“复用 Routines 间隔、上限及连续失败保护”，未限制适用对象。可能漏验任务类型，或把 Monitor 的调度规则当成 Routine 的规则。

处理：v0.2 §2、§9 明确保留五类 Task、唯一所有者及 Monitor 专属语义；Routine 的限制不自动套入其他领域，新增 A31。

状态：**本稿文档修订完成**。

### R05 · high · 混用公司离职、全局删除与单条遗忘

定位：v0.1 §6、§12；第 110、113、250 行。

依据：OpenMuse 完整规格第 57–58、77 行及 ADR 0008 规定全局账号删除立即停用工作、30 天恢复及之后最终清理；公司团队设计 §6 规定公司定向资格变更不得删除其他公司资格；Hindsight 设计另规定单条遗忘及恢复后的删除重放。

问题：v0.1 没有全局账号删除的独立流程和固定 30 天合同，也未区分“撤销会话”属于公司业务访问还是全局登录。统一删除措辞还可能让单条遗忘被账号恢复机制复活。原文将“更正”与删除同列，也会误导为更正时删除全部历史。

处理：v0.2 §6 区分公司离职、全局删除、更正/遗忘，保留 30 天恢复、受限管理员恢复、来源重验及不复活遗忘/外部写操作，新增 A32。

状态：**本稿文档修订完成**；各存储清理和恢复的运行证据不在本轮范围。

### R06 · medium · 完整集成、连接器和文档/财务合同覆盖不足

定位：v0.1 §3.1、§10.4、A26；第 52、226、285 行。

依据：OpenMuse 完整规格第 65、70、73–75、78、87、90 行明确唯一 OpenBot 业务后端、Google 经 OpenConnector、持久 Files、PDF 新副本且保留原件、服务端 finance CSV 计算及完整切换验收。

问题：v0.1 把这些要求留给笼统的“各领域规格”，但主要来源没有列出完整产品合同，且缺少对应验收。三类核心场景通过后仍可能遗漏 Files、PDF、finance 或保留第二套业务后端。

处理：v0.2 §3.1、§10.4–10.5 补回合同，新增 A33–A34；明确 Microsoft 范围保留但供应商路径尚待原企业合同冻结，不能将 Google 决定扩写为 Microsoft 决定。

状态：**本稿文档修订完成**；Microsoft 原有开放问题保持可见。

### R07 · medium · 将已有参考容量一并推迟为待定

定位：v0.1 §14；第 300 行。

依据：OpenMuse 完整规格第 9、60、99 行及私有 Bot ADR 明确首个自托管部署约 1–20 活跃用户；OpenMuse v4 规划修订另有可凭证据调整的资源规划基线。

问题：v0.1 只要求未来签署容量配置，未保留已有参考规模。这样既可漏掉现有容量验收，也可能误把自托管单部署 20 人当成整个企业共享平台的容量上限。

处理：v0.2 §14 保留 1–20 参考规模并区分企业共享部署容量，A34 增加三端、双用户/Google 账号及资源实测验收。未把规划基线宣称为测得能力。

状态：**本稿文档修订完成**；企业总容量、SLO 和质量阈值仍待有责主体确认。

### R08 · medium · 团队资格的通用交集遗漏显式分享例外

定位：v0.1 §6、§7.1；第 109、127 行。

依据：公司团队设计 §5.1 明确同公司跨团队分享为显式例外，检查公司成员、受众、资源动作和撤销，不要求接收者因此自动加入来源团队。

问题：v0.1 §4 允许显式跨团队分享，但通用公式和退出团队后的内容处理又绝对要求来源团队资格。实现者可能按照公式误拒独立有效分享，或按照分享泛化为整个来源团队权限。

处理：v0.2 §7.1 区分普通团队资格与显式分享两条路径，§6 对退出团队后的授权重新分类，新增 A35 验证允许及拒绝边界；分享不授予原团队执行、凭据和全部引用权。

状态：**本稿文档修订完成**。

## 4. 保持不变的已确认约束

- 公司工作台使用公司余额，外部个人模型授权使用个人余额，预留/结算/尾差跟随固定付款账户，不自动切换。
- Hindsight 后台处理由平台承担；未审核候选不可跨会话使用；启用仍遵守全功能隔离门槛，不改成公司试点发布。
- 管理身份不提供员工私人内容读取权；账号恢复权限不等于内容读取或员工代入权限。
- 全功能多租户验收后统一开放；单一界面或协议测试通过不等于企业产品完成。

## 7. 用户指出的长期任务缺口与 v0.4（2026-10-16）

用户指出跨几天、几个月的任务尚缺设计。静态核对确认原有持久 Task、Plan、输入/审核等待、Monitor 及企业持久编排方向构成部分基础，但不能据此认定具有完整跨月生命周期。现有 Task runner 的约 300 秒是逐轮执行期限，Plan 的任意阶段等待也尚不能由现有类型或注释证明完整实现；单纯扩大超时不能补足目标、等待、续期与累计预算合同。

补充[长任务生命周期专项草案](../specs/2026-10-16-long-running-task-lifecycle-spec.md)，主规格更新为 v0.4：增加 §9.1、D09/C06 和 A42–A47，专项定义 LT01–LT16 与 L01–L12。推荐保留五类 Task，以同一任务、多轮有界执行、持久等待/唤醒和可恢复工作记录推进，分别约束业务期限、租约、委托及审批有效期；覆盖跨月预算、来源更新、版本迁移、停滞、取消和结项。

本补充尚未批准；未新增 accepted ADR 或根领域术语，也未修改现有队列/runner 或选择新的编排产品。后续须冻结状态转换、等待生产者、可靠唤醒、检查点、续期及编排所有者合同。原有容量/单轮时限及权限保证不因提出长期任务而自动放宽，业务验收没有在本次文档补充中执行。
