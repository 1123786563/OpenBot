**派生键布局（R06 修复 T06-F3 后）**：`cacheKey`/`jobKey`/`exportKey` 的每个组件（含 `scope.key`、name、parts、exportId）统一经 `injectiveKey` 长度前缀编码（`<len>:<component>` 以 `|` 连接），与 `scopeKey` 同一纪律；`scopeKey` 输出不变。修复前裸 `|` join 导致同 scope 内 `cacheKey(s,'runs','page|2')` == `cacheKey(s,'runs','page','2')` == `cacheKey(s,'runs|page','2')`，`jobKey` 同型碰撞——`jobKey` 是计费评测运行的幂等身份，碰撞属计费缺陷（见 findings register T06-F3）。

**#17（游标消费方）的失效义务（补记 T06-F2）**：`bindCursor`/`readCursor` 把游标 MAC 绑定到 `(scope.key, 进程内 CURSOR_KEY)`，`CURSOR_KEY` 每次启动随机生成。#17 集成时必须：把 `readCursor` 的 `OWNERSHIP_REQUIRED` 403 当作授权失败终止——不得当作空页，也不得静默从第一页重开；游标不得跨 epoch bump 或跨进程重启持久化复用（重启使在途游标全部失效是设计的安全失败，不是缺陷）；读取时重新派生 scope，不信任请求携带的任何 scope 字段。

## 偏差与现场决策

1. **`resolveStorageLocator` 的 fingerprint 修复（对计划实现代码的唯一实质偏差）**：计划原文 `fingerprint = String(scope.key.length)`，但计划自己的测试要求两个 scope（`user-a`/`user-b`，等长 key，同 botId 同 epoch）的 locator **必须不同**——等长 key 的长度指纹相同，导致 `project`/`workspace` 撞名（Task 3 首跑 `33 pass / 1 fail` 实证）。修法：fingerprint = `${key.length}-${sha256(key).slice(0,8)}`。保持全部计划约束：确定性派生自 scope.key、workspace 仍含 key 长度（静态测试 `toContain(key.length.toString())` 通过）、单向不可反推、两 scope 必不同。测试未放宽一行。
2. **import 合并**：计划的 Task 3 追加代码自带独立的 `from "./contracts"` import，与 Task 2 已有 import 重复；合并进现有 import 块（`createHash` 一并加入 `node:crypto`），语义不变。
3. **基线文档与实测的出入（记录，不修）**：基线文档 GREEN gates 记录 `cd server && bun run typecheck` exit 0，但我在我的 base `ef58d946` 上（独立 detached worktree + 同一 node_modules）实测 exit 2，错误为 `src/craft/webapp-proxy.ts(417,7)` TS2322；整仓 biome lint/format 在基线同样红（74/132/29）。该文件不在我的 owned_scope，按约束不修。怀疑基线测量时用了主 checkout 的 node_modules（TS 版本差异），无法在本 worktree 内确证。
