## S3. Code quality findings

- [F1] **Important — no fence between claim expiry and an in-flight/late drive.** A winner that stalls longer than `claimTtlMs` (default 15 min, `continuation-store.ts:351`) before calling `receiptSink.started()` loses its claim to a takeover; its late `recordOperationStarted` is `onConflictDoNothing` (`continuation-store.ts:657-671`) so it cannot detect the loss, and it proceeds to `resumeStream` anyway (`resume-driver.ts:160-168`). Two drivers can then race the same suspended run; whether a second `resumeStream` on a run another process is driving fails safely is Mastra-engine behavior not verifiable from this workspace (see S5). Window requires a >TTL stall between claim and started (the production driver calls `started()` immediately after the gates, `resume-driver.ts:160`), and the receipt ledger closes every narrower variant. Required fix before the approvals-integration slice wires production drives: re-verify the claim (token hash / revision) immediately before `resumeStream`, or make `started()` fail when the receipt pre-exists. Not a blocker for ME06 (no production drive path is reachable today).
- [F2] **Important (integration hazard, not an implementation defect) — drizzle migration number collision with the main tree.** This tree correctly takes idx 164 (`server/drizzle/meta/_journal.json` tail, tag `0164_mastra_execution_continuations`; next free number at BASE bf64d0f2), but the main tree `/Users/wuyongjun/trea/OpenBot` already claims idx 164 for its own uncommitted `0164_usage_outbox_workspace.sql` + journal entry.
