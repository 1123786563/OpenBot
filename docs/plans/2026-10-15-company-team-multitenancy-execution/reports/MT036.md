## 1. 设计要点

主库（企业库，权威授权面）与 KB 库（内容面）是两个独立数据库；**一致性由调用时授权（主库注册表逐次求值，无缓存）+ 同步版本令牌（两侧可比对）保证**，绝不假装跨库外键。

### 1.1 主库侧权威（新文件 `server/src/enterprise/tenancy/kb-ownership.ts`，纯新增）

1. **KB 注册 = 主库 `enterprise_resources` 行（`kind='knowledge'`）**，与 MT009 依赖表的知识引用词汇同源。授权判定与 MT008 decide() 完全同构：`assertTrustedScope` → read committed + lock/statement timeout → 事务本地 `app.*` → advisory 共享锁（tenant → principal → membership → workspace-membership，`workspaceMembershipLockKey` 同键族）→ 受限 data 角色经真实 RLS 读事实 → **同一注册表**求值。deny 只有一种形状——`notFoundVerdict()` 的 canonical `RESOURCE_NOT_FOUND`：不存在、跨公司、跨团队、无授权、已删除、非 knowledge kind 对外不可区分。
2. **列表 = decide 的复数形态**（MT011 同款）：候选行按 scope 租户 + 团队 + kind 过滤一次受限读取（跨公司行由 RLS 隐藏），逐行经注册表求值只保留 allow；不可见库不进列表、不进计数。
3. **同步版本令牌** `kbSyncVersionOf(reg)`：确定性 `kb-sync/v1/w=<workspaceId>/r=<revision>/e=<aclEpoch>`，归属或版本任一成分变化都改变令牌。`compareKbOwnershipSnapshot`（纯函数、冻结结果、零值回显）：镜像缺失/租户不符 → `KB_OWNERSHIP_MISSING`；团队不符 → `KB_OWNERSHIP_WORKSPACE_MISMATCH`；令牌落后 → `KB_SYNC_VERSION_STALE`。**一致性门只在授权放行之后执行**（请求者已被告知存在性，故给确定性可行动码而非不可见语义）。
4. **信任边界**：`assertTrustedScope` 只放行 seam 签发的 Scope。KB 内部服务身份（API-Key 的 tenantId+role+kbScope）没有 principal/团队事实，结构上进不了本模块；模块源码级无进程环境读取（测试钉死）。

### 1.2 KB 库侧归属镜像（新文件 `server/src/kb/db/ownership-schema.ts` + drizzle-kb 迁移 0001）

新表 `knowledge_base_ownership_states`（expand-only，不动 `knowledge_bases` 既有列）：`knowledge_base_id`（PK，FK→knowledge_bases cascade）、`tenant_id`、`workspace_id`、`sync_version`（主库令牌的逐字镜像）、`updated_at`；行形状 CHECK（归属列与令牌非空）+ 租户/团队索引。迁移经 `drizzle-kit generate` 生成 `drizzle-kb/0001_handy_katie_power.sql`（journal 纯追加，0000 快照零改动），由运行时迁移器（advisory lock 幂等）应用——KB 专用测试库以专用受限登录（`ent_mt036_kb`，NOSUPERUSER NOBYPASSRLS）属主通道跑迁移。

### 1.3 知识库侧受限查询入口（新文件 `server/src/kb/application/service/kb-restricted-query.ts`，纯新增）

三条铁律（模块头注钉死）：

1. **请求者类型只有受信 PlatformScope**：`assertRequester` 先做结构检查（无 `scope` 的一切形状——含内部 API-Key 身份——→ `KB_REQUESTER_INVALID`），再 `assertTrustedScope`（伪造 scope → `UNVERIFIED_SCOPE`）。入口源码不出现内部身份词汇（kbScope/APIKeyEntry，注释剥离后源码级断言钉死）——普通请求复用内部 Key 得到的是拒绝，不是公司全域视野。
2. **授权先于一切内容访问**：`getKnowledgeBase` deny → canonical 不可见（与不存在逐字节同形）；KB 库内容行缺失/软删 → 同一不可见语义（跨库内容缺失不泄露区别）。列表/计数只含授权且一致的库。
3. **跨库一致性逐次比对（调用时，无缓存）**：授权放行后读内容行 + 镜像行并比对——镜像缺失/团队不符/版本落后一律拒绝（`KB_OWNERSHIP_*`），不一致对象同时从列表「不浮现」（列表上下文的拒绝形态）且不进检索集合。归属迁移（workspace 变更）或版本推进未同步的库在下一次调用即消失。

**检索收窄** `narrowRetrievalScope(requester, kbIds)`：请求集合去重后只保留「授权 + 跨库一致」的 id（保持首次出现顺序，输入卫生：非数组/非串/空串/超 100 响亮拒绝 `KB_RETRIEVAL_INPUT_INVALID`）；未授权/不一致 id 静默排除、不携带原因——把集合交给检索器并在检索端限制返回范围是调用方契约（Spec §6 先定允许集合再检索端限制）。

## 6. 诚实披露

- **D1（主库零迁移；KB 侧迁移走 drizzle-kb 通道）**：brief 的「需迁移则 migrate-test.ts 注册任务」按企业测试库口径理解——主库复用既有对象（enterprise_resources kind 过滤 + MT009 依赖表 + MT008 注册表），无新表无新列，故 migrate-test.ts / migration-tool.test.ts 零改动（无任务注册、无 allowlist 窄例外）。KB 归属镜像表落在 KB 域自有数据库，其迁移机制是 KB 域的 drizzle-kb journal（`kb:db:generate`，运行时迁移器幂等应用）——该工具不作用于企业测试库，无法也不应承载 KB 库 DDL。这是两个独立数据库票面语义的直接推论，已在 PLAN.md 与本报告钉死。
- **D2（setup 通道 stand-in）**：归属迁移/版本推进/tenant policy_revision 翻转/kind 漂移制造经 setup（superuser）通道执行——operator 对 `enterprise_resources` 仅有 MT008 授予的 visibility **列级** UPDATE，整行 UPDATE（workspace_id/revision/kind）的管理写路径属后续管理票（MT008 D5 / MT011 D5 同款披露）。**判定侧从不使用**：全部被测查询经受限 `ob_ent_data` 角色 + 真实 RLS（事务本地上下文 + advisory 锁同键族）。
- **D3（KB 库无 RLS/企业角色矩阵）**：KB 域是独立数据库、own-login 单一属主访问模型（docker/kb-mastra/init-db.sql 既有先例），企业域 `ob_ent_*` 角色不跨库存在。本票 KB 侧隔离由受限查询入口的调用时授权 + 同步版本一致性门实现（应用层 seam，主库权威为唯一授权事实源）；KB 库表级 RLS 与专用受限角色硬化属后续 KB 域硬化票，不在本票 Scope boundary（归属字段与查询限制/跨库一致性/受限查询入口）内。
- **D4（单门变异存活）**：MUT4a/MUT4b 单门移除存活（0 fail）——信任边界在入口与权威模块各设一道，移除其一被另一道兜住；双门同移（MUT4b-full）捕获。与 MT008 MUT3a「冗余防线如实记录」先例一致。
