## 2. What was built

One call, `createIsolationFixture(domain)`, provisions the Spec §11 minimum identity matrix on the dedicated enterprise test PostgreSQL through the **real** offline provisioning factory (`provisionDeployment`) and returns a fixture that opens business transactions only under **real restricted roles**:

- Companies A and B; teams A1 (甲) and A2 (乙) in A, team B1 (丙) in B.
- Nine identities covering all eight §11 classes (see `SPEC_IDENTITY_MATRIX`): `a1-member`, `a2-member`, `a1a2-member`, `a1-other`, `b1-member`, `multi-company` (member of both companies), `company-admin` (`tenant_admin`, no content grants), `platform-operator` (machine identity on the `ob_ent_operator` capability), `worker` (machine identity running tenant/workspace-scoped `ob_ent_data` transactions without principal powers).
- `requestAs(identity, {method, path, body?, tenantId?, workspaceId?})` runs the real authorization chain: session seam → trusted-scope resolver (`createScopeResolver`, restricted directory role) → resource reader (`createResourceReader`, restricted data role). Status semantics per interfaces.md T02: 401 `AUTH_REQUIRED`, 400 `TENANT_REQUIRED`/`WORKSPACE_REQUIRED`, 403 `TENANT_FORBIDDEN`/`SCOPE_REVOKED`, 404 invisible objects, 503 storage unavailable; bodies carry the error code only (no raw DB errors, no counts, no existence leaks). The route surface today is `GET /resources/:id` (the only real enterprise business read that exists at BASE); anything else is 404.
- `queryRestricted(role, context | undefined, text, values)` opens a transaction on the verified directory/data/operator connection (each pool is deliberately `max: 1`, so consecutive calls provably reuse the same backend), sets business context transaction-locally (`set_config(..., true)`), runs the `$1..$n` query with bound parameters only, and returns rows. Commit and rollback both clear the context because nothing session-level is ever written.
- `externalEffects()` records the real provisioning/revocation receipts; `suspendCompanyMembership(identity, tenantId)` wraps the real `suspendMembership` (epoch bump + audit event); `dispose()` deletes every fixture row by its unique id prefix and closes all four connections, and is idempotent; a failed creation also cleans up its rows and connections.
- `scenarios.ts`: `registerIsolationDomain` / `runIsolationScenario` over the 26-domain union (`ISOLATION_DOMAINS`) from tasks.json. Unregistered domains, adapter exceptions, and skip-shaped observations are errors — never a preset success; re-registration and unknown domains are refused.
- URL resolution happens entirely before the first socket: `TEST_DATABASE_URL`/`ENTERPRISE_TEST_SETUP_DATABASE_URL` must name an `openbot_enterprise_*` loopback database, and all three `ENTERPRISE_TEST_*_DATABASE_URL` role logins must exist and point at the same instance. There is no path that falls back to `DATABASE_URL` or any development database.

## 6. Concerns and limitations

1. **Team membership is a fixture fact until MT004.** `enterprise_workspaces` exists but workspace-membership rows do not; the fixture materializes each identity's team membership through per-team resource grants created by the real factory and records it in `identities[*].companies[*].teams`. When MT004 lands its table, the fixture should insert real membership rows behind the same fact shape (that change belongs to MT004/MT005 with this ticket's files as shared seam — coordinate ownership through the coordinator).
2. **requestAs route surface is intentionally minimal**: only `GET /resources/:id` exists as a real business read at BASE. Downstream route tickets extend the routing inside `requestAs` (or register domain adapters) rather than re-deriving scope checks.
3. **Machine identities** (platform-operator, worker) have no user session by design; `requestAs` for them is 401 and their usable seam is `queryRestricted` — matching Spec §5.2/§6 machine-authentication separation.
4. The `ent_mt002_*` login credentials live only in the ephemeral container and `checkpoints/MT002/environment.md`; the coordinator may re-provision with `bun server/scripts/enterprise-test-db.ts provision` and different passwords without code changes (URLs come from env).
5. `parameterized()` reserves `$1..$n` placeholder syntax (documented in-code); values bind as parameters and `undefined` binds are refused loudly (drizzle would otherwise silently truncate the SQL — found and fixed during verification).
