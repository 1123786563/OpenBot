## 1. 设计要点

### 1.1 策略版本注册表与判定入口（新文件 `server/src/enterprise/tenancy/resource-policy.ts`）

三件事，全部纯追加：

1. **注册表**（`createResourcePolicyRegistry`）：显式注册、显式解析；空注册表对任何版本抛 `POLICY_REVISION_UNSUPPORTED`（与 authz/service.ts 既有语义一致）；重复 id 响亮拒绝。`tenancy-v1`（判定 = `createAuthz().check` 的等价复刻，可见性完全不参与）与 `workspace-v1`（= tenancy-v1 全部判定 ∪ 唯一新放行「visibility='workspace' 且同团队有效成员」，绝不更窄）作为两个独立版本对象注册；注册新版本不改变旧版本任何判定（对照测试逐例钉死）。
2. **判定入口**（`createResourcePolicyService.decide`）：受信 Scope（`assertTrustedScope`，只有 `createScopeResolver` 签发的 Scope 能进入）→ 数据事务（read committed + lock/statement timeout → `set_config('app.*', …, true)` 事务本地 → advisory 共享锁，键序/键形 = `store.readLockKeys ∪ scope-gate.workspaceMembershipLockKey` + resource 键）→ 受限 data 角色下经真实 RLS 读判定事实 → 注册表求值。deny 只有一种对外形状 `{ outcome: "deny", code: "RESOURCE_NOT_FOUND" }`：不存在、跨公司、跨团队、无授权、已删除对外不可区分。
3. **可见性解析**（`parseResourceVisibility`）：DB 值 → 类型；取值域外响亮拒绝。

裁决 #2（MT005）边界：workspace-v1 是 Issue #51 票面授权的新策略版本；tenancy-v1 语义不变（对照测试 + 生产 authz 等价性测试双重钉死）；本票未改 store.ts / scope-gate.ts 任何既有导出语义（两者哈希与 prereq manifest 一致）。

### 1.2 显式迁移入口（新文件 `server/src/enterprise/tenancy/resource-visibility.ts`）

验收 3 的「必须经显式动作」：入口只按显式清单（tenantId + resourceIds）执行；**无清单/空清单零写入**（结构性提前返回，一条 SQL 都发）；清单外资源绝不触碰；`'private'`（显式个人选择）绝不被清单翻转；跨租户 id 只以 notFound 入报告绝不写入。写入经受限 operator 角色与既有 UPDATE 行策略（`app.tenant_id` + `app.resource_id`）+ MT008 迁移授予的 visibility 列级 UPDATE 权限；每资源先取排他 advisory 锁（与判定入口共享锁同键族），读-判-写在锁内完成。方向唯一：NULL → 'workspace'；已是 'workspace' 幂等 no-op。

### 1.3 落库（expand-only）

`enterprise_resources` 追加可空列 `visibility`（NULL = 未标记/遗留：行为 = 既有 grant 语义，两个版本下都不变）+ 取值域 CHECK（`null | 'private' | 'workspace'`），经 migrate-test 的 **MT008 任务**（0001 列+CHECK、0002 operator 列级 GRANT）真实执行；套件 beforeAll 先 dry-run 后 --apply（fresh→applied / 已应用→up-to-date 收敛）。不修改任何既有列/约束/策略/授权（expand-only 断言 + 迁移语句正则钉死）。

## 2. 验收逐条证据映射（Issue #51 四条，测试 `server/tests/multitenancy/resource-policy.test.ts`，29 用例）

| 验收 | 测试证据 |
|---|---|
| **1** 资源具有 private/workspace 可见性；未标记保持既有行为 | DB 边界：'workspace'/'private'/null 标记经受限 operator 真实 UPDATE 行策略写入、data 角色读回；`'public'` → SQLSTATE 23514（`enterprise_resource_visibility`）。回归：未标记资源在 tenancy-v1 与 workspace-v1 下都只认 grant（grantee ALLOW / 无 grant 活跃成员 DENY——新版本不自动扩大范围）；suspended 成员失去团队公共路径但保留 grant 路径（见披露 D1 的修复说明）；'private' 同样只认 grant。 |
| **2** 新策略版本独立注册；旧版本判定升级前后完全一致 | 空注册表对 tenancy-v1 抛 POLICY_REVISION_UNSUPPORTED；只注册 tenancy-v1 时 workspace-v1 不可解析；**同一 15 例判定矩阵**在 workspace-v1 注册前后对 tenancy-v1 逐例断言相同 verdict；矩阵同时与生产 `createAuthz().check` 在等价输入上逐例等价；tenant 仍处 tenancy-v1（policy_revision 解析路径）时 visibility 完全不参与；未知版本 `POLICY_REVISION_UNSUPPORTED` 拒绝猜测。 |
| **3** 旧 public 资源迁团队公共必须经显式动作 | 无清单 → 零写入（updatesExecuted=0，预标记原样存活）；空清单 → 零写入；显式清单只迁移列出的资源（清单外原样 NULL）；已 'workspace' 幂等 no-op；'private' 绝不被翻转（privateKept + 落库仍 'private'）；跨租户 id 报 notFound 且其本租户行原样；迁移后资源在 workspace-v1 下团队公共而 tenancy-v1 仍 grant-only；清单解析拒绝垃圾形状。 |
| **4** 跨公司引用永远拒绝、不泄露存在性 | 策略层：workspace-v1 对跨公司 facts（即使有 grant、即使 workspace 标记）DENY；tenancy-v1 同样 DENY（不变）。服务层（真实 RLS）：B 公司成员读 A 公司资源（已发布到 A 团队）两版本都 DENY；「外部资源拒绝」与「不存在资源拒绝」verdict JSON 逐字节相同；同一多公司身份在自己公司 scope ALLOW、在另一公司 scope 对同一资源 DENY——scope 是权威。 |

另：「restricted roles were in play」钉死判定全程 `current_user = ob_ent_data`（非 superuser）。
