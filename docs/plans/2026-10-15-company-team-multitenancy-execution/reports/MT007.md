## 1. 设计要点

### 1.1 单一撤权判定入口（新文件 `server/src/enterprise/tenancy/revocation.ts`）

票面备注（下游复用基础、不散落各处）落为三件事：

1. **失效点清单**（`REVOCATION_CHECKPOINTS`）：票面命名的六点——`list`、`detail.read`、`download.issue`、`events.subscribe`、`task.sensitive`、`credentials.access`。封闭集合，`parseRevocationCheckpoint` 对未列名检查点响亮拒绝（`REVOCATION_CHECKPOINT_UNKNOWN`），杜绝下游拼错名字静默绕过。
2. **级联判定**（`createRevocationGuard`）：`decide(scope, checkpoint)` → 断言受信 Scope → **复用 MT005 `createWorkspaceGate().transaction`**（同一事务形状、同一锁序 tenant→principal→membership→workspace-membership、同一事实行）做两级重验：公司停用 → `{deny, SCOPE_REVOKED, level: company}`（一事实、全团队级联）；团队停用 → `{deny, WORKSPACE_REVOKED, level: team}`。**本文件零重复实现重验逻辑**——判定与 gate 语义不可能漂移。`assert` 为同判定的抛错形态。**无任何判定缓存**：每次调用读实时行，停用后恢复立即重新放行（AC3 的「不残留拒绝缓存」由结构保证，测试钉死）。基础设施故障原样上抛，绝不折叠成拒绝或放行。
3. **审计事件写入**（`recordRevocationAuditEvent`）：在调用方的 operator 事务内写一条 `enterprise_security_events`（既有表，**无 schema 变更**）：操作者（`actor_id`=操作者 principal，details 双记 principal/user）、对象（`target_principal_id`）、范围（`tenant_id`；团队事件带 `workspace_id`）、版本（`epoch`=变更后成员关系版本）、时间（`created_at`）。事件 id 兼作 operation id，经真实 RLS INSERT 策略（`app.tenant_id` + `app.operation_id` 钉）落库。

### 1.2 管理面扩展（`workspace-admin.ts`，纯追加 + 三处最小编辑）

- **新增动作**：`restoreTeamMember`（suspended→active，epoch+1）、`suspendCompanyMember` / `restoreCompanyMember`（公司级停用/恢复，epoch+1）。事务形状与既有动作完全一致（read committed + timeout + set_config 事务本地 + 排他 advisory 锁 tenant→membership(admin→target)，与 MT005 gate 共享锁同键串行化——lock_timeout 探针测试钉死）。公司级停用/恢复经 MT004 既有的 operator `UPDATE(status, epoch)` 列授权 + `app.operator_principal_id` pin 写入。
- **既有动作补审计**（AC4 要求「每次停用/恢复/撤权」）：`suspendTeamMember`→`workspace_member.suspended`、`removeTeamMember`→`workspace_member.removed`（版本=被删行最后 epoch，删除 returning 补带 epoch）、`addTeamMember` 重激活分支→`workspace_member.restored`（新建分支 `auditEventId: null`——新建成员不是停用/恢复/撤权）。全部动作返回 `auditEventId` 供回读验证。
- 错误语义与既有面一致：目标行状态不符/不存在统一 `TEAM_MEMBER_NOT_FOUND` / `COMPANY_MEMBER_NOT_FOUND`（不泄露存在性）。

## 5. 披露

- **D1（接入面勘察清单，下游票的 seam 参考）**：下载签发现位于 `craft/artifact-routes.ts`（产物下载）、`craft/directory-archive.ts`、`workshop/routes.ts`/`public-routes.ts`、`untrusted-content.ts`；任务敏感动作位于 `openmuse-tasks/`、`work/queue.ts`、`responsibilities/`、`routines/`；凭据取用位于 `credentials.ts`、`passwords/`、`host-access/`、`plugins/shared-use-*`。以上均无受信 PlatformScope 流入（多租户改造属其各自闭环票）；本票交付的 `download.issue` / `task.sensitive` / `credentials.access` 检查点 + `createRevocationGuard` 是它们的复用契约（Issue #50 备注）。
- **D2（既有 reader 形状）**：`store.ts createResourceReader` 对预签发 Scope 只重验公司级（MT005 前形状，MT005 报告 §1.4 已列「未触碰面」；store.ts 本票不得改）。请求路径（resolve）与业务事务路径（gate/guard）均已按两级判定拒绝；下游票把详情读路径迁入 gate/guard 时该形状自然收敛。
- **D3（事件接入的性能形状）**：wired replay 每次调用先跑一个 guard 事务（锁+重验）再跑 repository 事务——两个事务的串行成本换零侵入（不改 conversations/store.ts / runs repository）。默认轮询 200ms 下每订阅每秒约 5 次重验；如后续需要，可在下游票把团队事实检查折进 repository 事务（需 seam 授权）。
- **D4（测试支撑复用）**：测试经 MT006 `support/workspace-scope.ts` 夹具（含其 D1 披露的 operator DELETE 策略供给）+ 真实 resolver/gate/admin 面；本票未新增任何替身。审计读回经受限 operator 角色按事件 id + operation 钉（RLS 真实路径）。
- **D5（tests/enterprise 预存失败，非本票造成）**：`tests/enterprise/runner-{events,production,scope}.test.ts`、`run-{success-contract,active-lookup}.test.ts`、`runner-events.integration.test.ts` 在**前置态**（还原本票对 events.ts/runner.ts 的 16 行改动后）即为 63 pass / 51 fail（114 例）/integration 0-1——根因是 MT005 起 resolver 要求团队成员行而这些合成夹具未建行；本票改动前后失败数**完全一致**（63/51，integration 0/1），证据 `verification/enterprise-runs-suites-preexisting.txt`。本票基线（brief 指定）为 `tests/multitenancy/` 232→261 全绿 0 skip；预存失败按证上报，不在本票修复范围。
- **D6（subscribe 测试的安全中止）**：未接 guard 时 subscribe 会无限轮询——测试内置 3s 安全 abort，失败形态为明确断言失败而非挂起（首次 RED 期间即验证了该防护）。
