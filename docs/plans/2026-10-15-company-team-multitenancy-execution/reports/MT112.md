## 2. 勘察结论（开工前完成，全部基于真实代码，无臆造表名）

**部署身份（实际表/列）**

1. `deployment_packages`（`server/src/db/schema/core.ts:261`）：`tenant_id text NOT NULL UNIQUE`，启动时由 `synchronizeTenantPackage`（`src/tenant-package.ts:797`）从租户包 `brand.yaml` 的 `tenant.id`（`tenant-package.ts:619`）upsert——这是**数据库内持久化的部署身份**。
2. `config.deploymentId`（env `DEPLOYMENT_ID`，`src/config.ts:2787`，可选）：生效身份为 `config.deploymentId ?? tenantPackage.tenantId`（`src/index.ts:841/1274/1320/3720`）。**边界（诚实披露）**：迁移 SQL 只能看到持久化身份（`deployment_packages.tenant_id`）；env 覆盖场景下运行时派生键可能与迁移派生键不同，生产执行不在本 Ticket 范围（ticket 备注明示），此边界写入任务描述与下方设计。

**计费 Customer（实际表/列）**

3. `billing_customers`（`server/src/db/schema/billing.ts:18`）：`external_id text PRIMARY KEY`、`name`、`last_synced_at`；注释明示「keyed by the external ID this deployment generates locally (deployment identity)」。键值由 `deploymentExternalCustomerId(tenantId)`（`src/billing/service.ts:54`）**唯一定义点**派生：`openbot-deployment-${tenantId}`；customer 名称 `OpenBot deployment ${externalCustomerKey}`（`src/index.ts:3772`）。下游投影 `billing_subscriptions.external_customer_id`、`credit_grants/credit_ledger.external_customer_id` 均引用该键。

**映射落点决定**

4. 企业域既有表（`enterprise_tenants/principals/memberships/workspaces/resources/resource_grants/security_events/workspace_memberships`）中**不存在**部署身份 ↔ 租户的映射表（`enterprise_resource_grants` 是资源 ACL，形状不匹配）。按 brief 指引：**新增最小映射表 `enterprise_deployment_anchors`（纯追加进 MT112 任务 DDL）**。

## 3. 设计

**表 `enterprise_deployment_anchors`**（drizzle 导出 `enterpriseDeploymentAnchors`，schema 纯追加；TASKS 步骤 0001 建表、0002 RLS）：

- 列：`tenant_id`（PK，FK → `enterprise_tenants(id)` ON DELETE cascade）、`deployment_tenant_id`、`billing_external_customer_id`、`created_at`。
- 唯一性（两个方向）：唯一索引 `enterprise_deployment_anchor_identity (deployment_tenant_id)` 与 `enterprise_deployment_anchor_billing_customer (billing_external_customer_id)`——同一部署身份/同一计费 Customer 至多被一个锚点租户认领。
- **可核验性（自证）**：CHECK `enterprise_deployment_anchor_billing_derivation` 把派生规则焊进数据：`billing_external_customer_id = 'openbot-deployment-' || deployment_tenant_id`（与 `deploymentExternalCustomerId` 唯一定义点一致）。核验 = 两条 JOIN（→ `deployment_packages`、→ `billing_customers`）+ CHECK 保证的内部一致性。
- RLS 最小新增：REVOKE PUBLIC 与四角色 → ENABLE + FORCE → 1 条 `ob_ent_operator` 租户范围 SELECT 策略 + `GRANT SELECT`。**不授予任何受限角色 INSERT/UPDATE**——锚点行只能由本迁移写入（测试以 42501 证明）。

**数据创建（TASKS 步骤 0003 锚点行、0004 映射行；与 MT004 纯 DDL 的差异所在）**

- 「原有公司」租户行：固定 id `ent-legacy-original`、名称 `原有公司`（Spec §9.2 词汇）；`ON CONFLICT (id) DO NOTHING`。
- 「默认团队」workspace 行：`ent-legacy-default-team` / `默认团队`；`ON CONFLICT (tenant_id, id) DO NOTHING`。
- **成员锚点**：全库最早用户（`ORDER BY created_at ASC, id ASC LIMIT 1`，确定性规则、绝不先查后插）→ `enterprise_principals`（id = `entp-legacy-anchor-<user_id>`，`ON CONFLICT (id) DO NOTHING`）→ `tenant_admin` 成员资格（`ON CONFLICT (tenant_id, principal_id) DO NOTHING`）→ 默认团队 workspace 成员资格（MT004 表，`ON CONFLICT DO NOTHING`）。无用户时插入 0 行（不臆造用户）。已知边界：锚点用户的既有他租 principal（unique `user_id` 冲突）会响亮失败——MT112 的契约窗口（企业域刚建、尚无回填）内不会发生，如发生即人工审查信号，见 §7 披露。
- **映射行**：`loaded_at` 最早的 `deployment_packages` 行（历史部署的原始身份；brand 迁移可能累积多行，故显式确定性选取）+ 派生计费键；`ON CONFLICT (tenant_id) DO NOTHING`。不写 `billing_customers` 投影行（其权威写入方是 billing sync，迁移不越权）。

**expand-only**：三个既有文件 diff 均为纯追加（0 删除；`migration-tool.test.ts` 仅裁决授权的一处断言替换）；新表/新步骤/新数据全部纯追加；未改 MT001–MT004 任何语义（既有表策略计数逐一不变，测试断言）。
