## 5. 诚实披露（D1–D7）

- **D1（缺失 state 的安全事件归属边界）**：缺失/未知 state 无归属公司，`enterprise_security_events.tenant_id` NOT NULL 且禁止臆造租户（「不填虚假租户标识」）——默认只拒绝不落行；`consume` 的 `securityAttributionTenantId` 参数允许调用方在确有归属事实时显式供给（用例双路径钉死：无 attribution → securityEventId null；有 attribution → 事件落行、state 值仍不回显）。票面「缺失…记录安全事件」在此口径下满足；HTTP 装配（下游票）若无法提供归属，缺失拒绝只进部署日志。
- **D2（发起人存活重验超集）**：票面四拒绝外，consume 增加第五拒绝 `STATE_INITIATOR_INELIGIBLE`（回调时公司/团队成员资格必须仍 active，A5 停用面），带安全事件；恢复成员资格后同一流程仍可完成（不烧 state）。epoch 不比对（state 行是发起时快照，epoch 纪律属 MT005 scope-gate 域）。
- **D3（verifier 入行属设计延伸）**：票面未点名 PKCE；持久行保存发起时服务端生成的 PKCE verifier 并经 allow binding 返回——持久行因此是流程秘密材料的唯一事实源，下游不必双轨维护「sealed state + 持久归属」两套机制（「同一规则不写两份」）；verifier 永不进事件/响应/日志（canary 钉死）。S256 challenge 与 plugins/oauth.ts 的 challengeFor 同算法，模块独立实现（不 import verified 交付）。
- **D4（行读回走超户披露）**：state 表 RLS SELECT 只有 state 臂（含 operator 在内谁都无公司枚举权），行级断言（status/failed_reason/计数）走夹具披露的超户 stand-in；安全事件断言走受限 operator 真实 RLS。业务路径全程受限角色。
- **D5（17 号档案无效证据已重取）**：surfaceOf 死代码移除后的首跑误用了已销毁容器（连接失败，52 fail）——该档案作废并在 17-true-final.txt 原文保留背景说明；容器同参数重建、15 任务迁移重放后以 18-true-final2.txt 为准（26/0/0、796/0/0、typecheck 0、biome 0 新增）。教训：teardown 必须晚于最后一轮证据。
  - 勘误（修复轮，2026-10-17）：中途版（support 文件 sha256 86280a40…，仅见 after-hashes.txt 哈希条目）未存档、内容不可恢复、diff 不可执行——上方「单一归因=surfaceOf 死代码移除」表述撤回，52-fail 成因不可归因，不作补造。可观察痕迹仅剩：17 号档案 biome 段含 `tests/multitenancy/support/oauth-state.ts format` 诊断 → 03-biome-write 修复 → 18 号档案该诊断消失。另：17 号档案头部原背景自称保留 52-fail 现场亦失实（52-fail 证据不存在），已在 17-true-final.txt 头部追加勘误行更正时间线（17=重建容器后首次有效复跑、18=biome 修复后终态复跑）。
- **D6（变异 MUT-1 特殊性）**：消费原子臂的 `status='pending'` 条件是并发 TOCTOU 防线，单线程观测不到（消费预检与原子臂互为纵深）——为此套件新增双 operator 连接的真实重叠并发用例（MUT-1 由其杀灭）；MT027 D8 同类不变量本套件已尽可能钉死。
