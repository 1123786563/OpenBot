## 1. 设计要点

### 1.1 策略分层 seam（新文件 `server/src/enterprise/tenancy/routing-policy.ts`）

四件事，全部纯新增（MT014 runtime-config 同款范式：公司基线 + 团队收窄覆盖 + 版本化存储 + 受限角色读取 + 归属派生缓存键；**未扩展 runtime-config.ts**——brief 禁改条款下用新模块新表）：

1. **平台模板目录**（`PLATFORM_TEMPLATES`）：进程内深冻结封闭清单（3 个模板，`deepFreeze` 递归冻结）。平台模板是平台静态能力（MT075 分类与 MT001 清单同源、「平台模板目录可共享」Spec §8），**不落库**——公司/团队面对它没有任何写路径，「不回写平台模板」是结构性质而非约定。
2. **公司治理策略文档**（`parseCompanyGovernancePolicyDocument`）：`network`（egress mode ∈ 既有 `EGRESS_MODES` 四档 + 规则经真实 `parseEgressRules` 归一化）、`capabilities`（封闭能力集上**每个开关显式声明布尔**——公司基线无隐式默认）、`modelRouting`（allowedRoutes ≥1 + defaultRoute ∈ 开放面）。严格形状、未知键拒绝、消息只含代码/路径/索引（egress 解析器错误文本内嵌规则值，一律不透传）。
3. **团队收窄覆盖**（`parseTeamGovernanceOverridesDocument` + 纯函数 `resolveGovernancePolicy`）：只接受收窄字段——capability 覆盖值 `true` 一律 `CAPABILITY_OVERRIDE_WIDENS_POLICY`（**专门测试**：公司关掉的开关、公司已开的开关，`true` 都被拒——覆盖没有「打开开关」的表达）；network 覆盖 mode 强度不得低于公司（`NETWORK_OVERRIDE_WIDENS_POLICY`）、rules 必须是公司规则清单子集（canonical 比较，含索引不含值，canary 钉死）；路由覆盖必须 ⊆ 公司路由（`OVERRIDE_WIDENS_POLICY` 含索引）、默认路由必须落在有效面内；收窄到空路由被拒（`OVERRIDE_MODEL_ROUTING_EMPTY`，对齐 MT014 D6 语义）。输出深冻结。
4. **受限角色服务**：`createRoutingPolicyService`（data 通道：read committed + lock/statement timeout + 事务本地 `app.tenant_id` + FORCE RLS；缺公司行 = `GOVERNANCE_POLICY_NOT_FOUND`，跨公司不可见与不存在不可区分、无默认回退）；`createTemplateInstallReader`（data 通道，跨团队安装读为 null/空——存在性不可区分）；`createTemplateInstallWriter`（operator 通道：install 拷贝目录条目、`updateInstall` 按 (tenant, workspace, ref) 复合键 + **revision CAS** 乐观并发（丢失更新不可能）、`syncToCatalogRevision` 把陈旧安装副本刷新到当前目录版本；跨范围行按 `TEMPLATE_INSTALL_NOT_FOUND` 处理且字节不变）。cacheKey = `routing-policy/v1/t=…/w=…/c=<companyRev>/o=<overrideRev|->`——纯入参派生、无进程状态（MT014 已实现的缓存键规则，见 D1）。

## 6. 诚实披露

- **D1（「缓存键规则复用 MT015」的解释）**：MT015 未在本工作树实现（无报告、无代码）；树内已落地并经 MT014 验证的缓存键规则是「cacheKey 由实际归属 + 配置版本确定性派生、无进程状态」。本票按该规则实现 `routing-policy/v1/t=/w=/c=/o=` 并由验收 4 的 5 个用例钉死其全部性质（即时性、无污染、纯函数、双实例一致）。若 MT015 后续定义了不同规则，以其为准再对齐。
- **D2（窄例外，brief 预授权）**：3 处既有文件编辑均为纯追加（migrate-test.ts 任务注册、migration-tool.test.ts 穷举断言第 6 次裁决先例、schema barrel 1 行），逐字节重建证明 0 删除/0 既有行修改（`changes-summary.txt`）。
- **D3（capability 词表复用部署级模块）**：`routing-policy.ts` 只读 import `admin/capabilities.ts` 的封闭能力集（`CAPABILITIES`/`isCapability`），全部署一套能力词表、避免术语分叉；该文件零改动。部署层 organization/role/group 的「group 可放宽」语义与公司/团队层「覆盖只收窄」是**不同层**的两套规则（前者单租户部署内部、后者跨公司租户治理），本票不改部署层；两层的最终收敛（部署级模块的租户化/关闭）属 Spec §9 后续治理票。
- **D4（egress 解析器复用）**：网络策略规则形状与解析复用 `agent-computer/src/egress`（只读 import，公司策略与电脑执行面永不各自解释规则）；其错误文本内嵌规则值，故失败折叠为「路径 + 索引」拒绝、绝不透传（canary 用例钉死）。
- **D5（模板安装写路径是本票生产面）**：与 MT014「写 API 属管理票」不同——AC3 的 update 语义（只落本范围、CAS、不回写）必须存在于生产代码，故 `createTemplateInstallWriter` 交付为生产 seam（operator 通道 + RLS + 复合键 + CAS）。管理流授权（谁有权调用 writer，经 MT075 公司面判定）与 HTTP 面属后续管理票；测试写入经受限 operator 角色走真实 RLS 策略（非 superuser 旁路）。
- **D6（平台目录不落库）**：平台模板目录实现为进程内深冻结封闭清单（平台静态能力，同 `openmuse-template-store` 的 `OPENMUSE_TEMPLATE_REVISIONS` 形态）而非表——「不可回写」由结构保证（无表、无语句引用目录、深冻结），并由行为测试（快照逐字节 + push 抛错）与源级断言钉死。目录的动态管理（新增/修订目录条目）属平台面后续票，届时目录版本推进即安装副本 `syncToCatalogRevision` 的输入。
