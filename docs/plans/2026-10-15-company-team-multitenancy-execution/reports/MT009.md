## 1. 设计要点（第 1 任实现，第 2 任核对后如实转述）

### 1.1 动作规则模块（新文件 `server/src/enterprise/tenancy/team-public-rules.ts`）

1. **显式动作词表** `TEAM_PUBLIC_ACTION_IDS`（read/run/upload/write/delete/share/manage）；未知动作抛 `ACTION_UNSUPPORTED`，绝不映射成 deny。
2. **read 与管理动作分别判定**：read 的放行语义只有 MT008 注册表一处定义，原样委托 `createResourcePolicyService.decide`（默认按资源所属租户 policy_revision 解析，可显式覆盖）。
3. **其余动作走本模块判定事务**（受限 data 角色 + 真实 RLS；事务形状与 MT008 判定入口同族：read committed + lock/statement timeout → 事务本地 `app.*` → advisory 共享锁，键序/键形同族）。团队公共使用路径四个必要条件全部显式：生效版本 ∈ 团队公共能力集（workspace-v1）且注册表内可解析（缺失一律 `POLICY_REVISION_UNSUPPORTED`）；资源显式 `visibility='workspace'` 且 `status='active'`；scope 与资源同公司同团队 + 版本号健全；请求者持 active 成员关系。任一不成立 → `RESOURCE_NOT_FOUND`（与 MT008 同款唯一拒绝形状，不泄露存在性）。
4. **run 附加规则**：仅 bot 类可运行（read 放行绝不派生 run；grants 表 CHECK 本就只允许 'read' 授权，run 无逐人授权形态）；通过后校验 `enterprise_resource_dependencies`（MT009 迁移新增表）：每行须 `status='active'`，知识范围引用还须解析到同租户内活跃资源行。任一无效 → `DEPENDENCY_INVALID` 并指明 dependencyKind + dependencyRef（确定性排序、可解释、不静默降级）；该解释只发给已过可见性门的成员，非成员在门处即得 `RESOURCE_NOT_FOUND`。
5. **管理动作在团队公共路径上一律拒绝**：对已过门的成员拒绝形状 `TEAM_PUBLIC_ACTION_FORBIDDEN`（指明动作）；依赖校验不参与管理动作判定。
6. **纯门可独立测试**：`decideTeamPublicActionWithoutDependencies` 与数据库完全解耦，伪造事实层面逐条件钉死跨公司/跨团队防线（RED-2→GREEN-2 即为此增量）。

**诚实边界（模块头注释钉死）**：依赖有效性只回答「声明的依赖是否存活」，不做传递授权重判（知识范围引用的资源对运行者本人是否可见属后续票据语义）。

### 1.2 落库（expand-only，migrate-test MT009 任务）

新增 `enterprise_resource_dependencies`：复合主键 (tenant_id, resource_id, dependency_kind, dependency_ref)；CHECK 兜底 kind ∈ model/credential/knowledge、status ∈ active/invalid、ref 非空；复合外键指向 enterprise_resources ON DELETE cascade。最小 RLS：REVOKE PUBLIC、ENABLE+FORCE、data 租户范围读 / operator 租户范围读+插，**无 UPDATE/DELETE**（依赖失效以新状态行/软删除表达）。不改任何既有表/策略/授权。

### 1.3 装配（index.ts 纯追加段）

动作服务与全部企业消费者共享**同一**已验证 enterprise data channel（无第二连接池、无宽松替身）；装配一次、导出供使用面票据消费；挂路由非本票范围。

## 3. verification/01 的 1 fail 调查（接管说明第 2 项）

**现象**：01-full-suite-12-files.txt 仅存摘要「340 pass / 1 fail（8431 expect，17.36s）」，失败用例名、断言、堆栈均未存档——不可从工件直接定位。

**排除「已由 GREEN-2 解决」**：mtime 链证明 GREEN-2（22:38:29）**早于** 01（22:40:29），01 是在最后一次绿色聚焦运行之后产生的新失败，该解释不成立。

**排除「树内缺陷」**：
- 交付树哈希 = GREEN-2 态（§0.2），即产生 01 的代码与今天复跑的代码逐位相同；
- 期望数差值是**中止签名**：01 记录 8431 expect，当前树全绿运行 8436（+5）——某用例未跑完自己的 expect 即被中止，与瞬时中止（超时/资源类）一致；且当前树每次全量运行 341 个用例全部跑完全部 expect，不存在「部分路径从未被测到」的潜伏缺陷证据。

**复现实验（第 2 任，全量 9 次全绿）**：
- 空闲复跑 ×8：`bun test tests/multitenancy/` 全部 **341 pass / 0 fail / 0 skip**（存档 04 文件含 5 次全记录，17.6–21.8s）；
- **CPU 饱和复跑 ×1**：10 核 `yes` 饱和负载下复跑（模拟前任连跑 6 变异 + GREEN-2 后的热机状态）仍全绿（70.58s 与 26.50s 两次饱和记录）。

**候选机制分析（为何恰在 22:40 一次性出现）**：bun test 默认按核数并行跑文件（`--parallel` 默认 = CPU 核数，`--timeout` 默认 5000ms）。12 个文件并行共享一个 PostgreSQL；本票测试文件的 beforeAll 是全组最重（4 个前置任务迁移 + 本票 dry-run + apply ≈ 11 个迁移子进程调用 + 完整身份矩阵夹具 + 7 资源播种），前任 22:38–22:40 刚连跑 6 次变异 + GREEN-2。单次瞬时失败（如某用例/钩子撞上 5s 默认超时或资源竞争）与全部证据相容，且与「此后 9 次全绿（含饱和）」不相矛盾。

**结论**：01 的 1 fail 为**一次性瞬时运行时失败（环境/负载类），非未修缺陷，亦非 GREEN-2 所修**。诚实声明：失败用例身份不可考（摘要日志未存细节），以上是排除法结论；不影响交付——当前树在全量、聚焦、空闲、饱和四个条件下均确定性全绿。
