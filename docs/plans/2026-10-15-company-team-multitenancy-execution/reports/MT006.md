## 1. 设计要点

### 1.1 列出面（`createWorkspaceScopeLister`，新文件 `tenancy/workspace-admin.ts`）

登录用户列出其有资格的公司与团队。判定事实与 MT005 完全同源：目录事务按
self-read RLS（`app.user_id`）读取 `enterprise_memberships`（join principals/tenants，
全部 `active` 才入选）与 `enterprise_workspace_memberships`（`status='active'`）；
团队名按公司经 data 角色租户上下文补齐（`enterprise_workspace_tenant_scope` 策略，
SQL 侧仅限本人团队 id）。无资格 → `{ companies: [] }`（明确空状态）；公司无团队 →
`teams: []`。排序确定性（tenantId/workspaceId）。响应体不携带任何
current/selected/default/active 字段（用例钉死）——列出就是列出，选择永远经裁决 #1 头。

### 1.2 管理面（`createCompanyAdminAuthorizer` + `createWorkspaceAdminService`）——等价集中入口

MT005 的 `resolve()` 结构上要求有效团队成员行（`WORKSPACE_FORBIDDEN`），而 AC3 的
「创建团队」对象尚不存在、公司管理员（fixture 的 company-admin）按计划矩阵不属于
任何团队——团队 gate 无法覆盖管理操作。票面明示「经 MT005 的 scope gate **或等价
集中入口**执行」，本票交付该等价集中入口（gate 的管理面孪生）：

```
签发：authenticate → x-openbot-tenant 选择 → 目录事务重验（active×3）→
     role = tenant_admin → Object.freeze + WeakSet 登记（与 issuedScopes 同构）
操作：assertTrustedAdminContext（伪造/反序列化 → UNVERIFIED_ADMIN_CONTEXT）
     → operator 事务：read committed + lock_timeout 2s + statement_timeout 5s
     → set_config('app.tenant_id' + 'app.operator_principal_id'=操作者, …, true)（事务本地）
     → advisory 排他锁（键序 membership → workspace-membership，createTeam 另持 tenant）
     → 事务内重验：成员行 active + role=tenant_admin + epoch === context.memberEpoch
       + principal 行 active（经 principals operator_read 策略 pin）→ 否则 SCOPE_REVOKED
     → 写前 set_config 切换 operator_principal_id 至目标成员（MT004 update 策略收束行范围）
     → 经受限 operator 角色 + RLS 写入
```

与 MT005 gate 的串行化：同一 `["enterprise","workspace-membership",t,w,p]` 键，
gate 持共享、管理写持排他——锁探针用例证明 gate 事务持锁期间管理写以
`lock timeout` 失败、释放后立即生效。四个操作：
`createTeam`（重复 id → 409）、`addTeamMember`（非公司成员/未知 principal 一律 404
不泄露存在性；active 行 → 409；suspended 行 → 重新激活 epoch+1 → 200；新行 → 201）、
`suspendTeamMember`（无 active 行 → 404）、`removeTeamMember`（无行 → 404）。

### 1.3 路由挂接（`tenancy/workspace-scope-routes.ts` + index.ts 只追加路由注册段）

### 1.4 operator DELETE 策略（remove 的 RLS 前提）

MT004 交付的 `enterprise_workspace_memberships` operator 策略只有
read/insert/update——remove-as-DELETE 经受限 operator 角色需要 DELETE 策略。
本票**不**向 `migrate-test.ts` 注册新迁移任务：MT001-MT005 交付测试文件只读，
`migration-tool.test.ts` 把 `ALLOWED_TASK_IDS` 钉死为 `["MT000","MT004"]`，
注册表追加会破坏只读基线（诚实约束，见 §5 D1）。处理：策略 DDL +
`GRANT DELETE` 由本票**测试支撑文件**（`support/workspace-scope.ts`）经专用 setup
连接在测试库一次性供给（pg_policies 目录查重后创建）；生产写路径本身完全经
operator 角色 + 真实 RLS 策略执行（测试即证）。生产迁移生成属 schema 链后续票。

## 5. 诚实披露

- **D1（operator DELETE 策略的测试库供给）**：策略 DDL + GRANT DELETE 由测试支撑
  文件经 setup 连接创建；生产代码写路径经受限 operator 角色 + 真实 RLS 执行（测试
  即证）。不注册 migrate-test 新任务的原因是只读基线钉死 allowlist（§1.4）；
  生产迁移生成留给 schema 链后续票。移除操作的 RLS 语义与 MT004 update 策略同构
  （tenant + operator_principal_id pin 至目标成员）。
- **D2（降级 admin 的事实变更通道）**：operator 角色无法更新 role 列（MT004 列授权
  仅 status/epoch），降级经 setup 连接（超级用户）执行并在 finally 恢复——纯测试
  事实变更，与 MT005 D4 同类替身；被钉的判定面（revalidateAdmin）全部经 operator
  角色真实 RLS 得出。
- **D3（`resolveForThread` / conversations 事务未扩展）**：业务事务半边仍是 MT005
  的 `createWorkspaceGate`，本票未改动其语义（哈希不变）；线程路径团队判定属后续
  接线票。
- **D4（scope 未携带团队 epoch）**：沿用 MT005 D3 结论——团队级资格以「行存在 +
  active + gate 每事务重验」为界；本票管理写与 gate 同键排他/共享串行化，
  移除/停用经锁纪律立即可见。
- **D5（存量 lint）**：index.ts/app.ts/config.ts 的 biome 发现与 BASE 逐一对应
  （noConsole×4、noNonNull、app noUnusedFunctionParameters、organizeImports×2、
  format×3；9 errors + 2 warnings，行号平移），净新增 0。本票 index.ts 追加块刻意
  不含 console.error（server/src 为 noConsole:error 覆盖区；会话故障经 401、
  operator 通道故障经 admin 路由 503 显式呈现）。
- **D6（skip 不是通过）**：全量 0 skip——`MT003_ASSIGNED_TEST_DATABASE_URL` 指向
  专用第二库，MT003 real-apply 用例实跑通过。
- **D7（一处测试自我修正）**：fixture 的 a1-other 按计划矩阵本就是 team-a1 成员
  （same-team-other-person）；DTO 用例初稿误用其验证「新加入」，409 暴露后改用
  a2-member。生产代码无此错误。
