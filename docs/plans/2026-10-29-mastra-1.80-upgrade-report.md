# Mastra 升级报告：core 1.64.0 → 1.80.0（OpenBot 在途未提交改动）

> 证据来源：上游 `mastra-ai/mastra` 的 GitHub Releases（core 区间 16 个稳定版全覆盖）+ 各包 `CHANGELOG.md` 原文（memory / pg / hono / client-js / server / schema-compat）+ 本地已安装产物（`server/node_modules/@mastra/*` 已是新版本）+ 本仓代码面扫描。
> 采集日：2026-10-29。

## 0. 先厘清「1.8」

- `@mastra/core@1.8.0` 发布于 **2026-03-02**，是今年 3 月的老版本，与本次升级**无关**。它的内容是：supervisor 多智能体编排模式、`queryVector` 可选（仅 metadata 的向量查询）、`runEvals` 增加 `targetOptions`、工作区编辑后触发 LSP 诊断、新增 Blaxel 云沙箱 provider；上游明确标注该版**无破坏性变更**。
- 本仓语境里的「1.8」= **1.80**，即当前工作区这笔未提交的升级：`@mastra/core` 1.64.0 → **1.80.0**（1.80.0 发布于 2026-10-28，是当前最新稳定版）。
- 完整时间线：1.64.0（2026-09-04）→ 1.65.0（09-09）→ … → 1.79.0（10-21）→ **1.80.0（10-28）**，共 16 个 minor 版本、约 8 周。

## 2. 新增能力（按上游 release Highlights 归类）

**可观测性 / Trace（本次最大主题）**
- 1.65 高级 trace 查询（core 契约 + server 端点 + 各存储实现）；租户隔离的 trace 删除与级联清理。
- 1.66 trace 查询增强（span 字段、metadata、feedback、score 的富过滤）；observability 信号删除（feedback + scores）贯通 storage/server/client。
- 1.68 trace 查询拿到「真分页 + discovery + 增量轮询」（core/server/client + ClickHouse/DuckDB/PG）；durable agent 默认不再持久化 `running` checkpoint。
- 1.71–1.72 可观测性能力协商协议（storage ↔ server ↔ client）、基于 discovery 的过滤与能力声明、trace 聚合规划 API。
- 1.75 span 查询 API（跨 trace 列已完成 span）；trace 聚合带 token 与成本分析（覆盖各存储）。
- 1.78 trace 聚合 API（server + client + React）；trace 列表带 input/output/error 预览。
- 1.79 span 聚合 + 「Time to First Chunk」+ 更强的 trace/span 查询。
- 1.80 span 聚合 API + 存储支持（ClickHouse/Postgres/DuckDB）。

**Agent / 运行时**
- 1.65 Agent Channel Actions API（处理按钮点击 / 选择变更）；1.67 后台工具执行控制增强；1.69 分类器成一等原语 + `ClassifierProcessor` 策略执行（输入/输出/流式）+ `context.background.adopt()` 原生后台工具执行。
- 1.70 按请求的模型路由（`ModelSelectionProcessor`）；跨进程取消排队中的 thread 输入。
- 1.72 后台任务多 worker 安全（持久化 ownership lease）；agent/workflow 的durability 与恢复增强。
- 1.73 **默认 Agent 错误恢复**（repair-first + 安全重试）；新的 `tool-call-resumed` 流式 chunk；1.74 工具上下文可读完整会话（`agent.getMessages()`）。
- 1.75 session 每 thread 持久化一个活跃模型 + 可选「无初始 thread」；1.78 **Agent Scopes**（多租户身份 + 更安全的 memory/thread 路由）；`queueSignal` 类型化信号排队。
- 1.79 Agent Controller 会话改为 sessionId 键（每 resource 多会话）；沙箱获得原生文件系统 API。

**Memory / 工作记忆**
- 1.68 基于 token 预算的会话历史裁剪（`messageHistory`）；1.74 OM 历史检索（过滤/排序/记录查找）、语义召回可分页浏览命中点附近的观察组。
- 1.75 自嵌入向量存储（语义召回无需客户端 embedder）。
- memory 1.31 `messageHistory` 选项、1.34 recall 工具附件处理、1.37 PG 上并发的 schema 工作记忆更新不再互相覆盖（行锁事务内深合并）、1.39 OM 的 `'auto'` 模型可按实际可用凭据选择 provider。

**平台 / 集成**
- 1.65–1.80 持续扩张沙箱与工作区能力（bulk upload、权限、LSP、可配置二进制解析、本地符号链接挂载）；新增 `@mastra/connect`（1.67 首发，1.75 升到 1.0）、Discord 与 Microsoft Teams channel、MCP v2 架构（1.68）、MCP Events（1.79）、Sandbox 原生文件系统（1.79）。
- 1.79/1.80 端用户级（per-resource）连接与「请求连接」交互提示。

**流与可靠性**
- 1.66 首 chunk 超时 + 降低 tracing 开销；1.72 thread 流式与 PubSub 保留策略改进（更快重连、更少重放）；1.73/1.77 durable/evented 执行可靠性与规模修复；1.80 统一持久化的 provider 错误分类（重试与 UX 更好）。

## 3. 破坏性变更（上游明确列出的，按与本仓相关性排序）

上游 16 个 core 版本**每个都带 Breaking Changes 段落**，但绝大多数集中在 `@mastra/factory` 与 `@mastra/playground-ui`——**这两个包本仓都没用**，因此大部分与 OpenBot 无关。真正需要看的是 core 契约级与 `@mastra/server` / `@mastra/client-js` / `@mastra/memory` 的部分：

| 版本 | 破坏性变更 | 本仓是否命中 |
|---|---|---|
| 1.67 | `subscribeQueuedMessages({resourceId,threadId}, listener)` → 改为 `subscribeThreadEvents(...)`，listener 收类型化事件 | **否**（本仓无调用） |
| 1.68 | Agent Controller 流式消息事件改为「一个完整 `message_start` + 按 ID 寻址的 `message_update` 增量」，`message_end` 只含消息 ID | **否**（本仓走 AG-UI 桥的 `text-delta/tool-call/tool-result/step-finish/finish`，不消费 controller 事件） |
| 1.68 | `@mastra/mcp@2.0.0` 大改写：仅支持 MCP 2026-07-28，移除旧握手，suspend/resume 取代 elicitation | **否**（本仓未直接依赖 @mastra/mcp） |
| 1.72 | `session.respondToToolApproval(...)` 现在**必须带 `toolCallId`**；审批门禁按 thread/run 键控 | **部分命中**：本仓审批走 `agent.resumeStream(data, { runId, toolCallId })`，路径不同，不调用该 API |
| 1.73 | durable stream 在 output processor 阻断时**不再发出独立的 `tripwire` chunk**，改用 `finishReason === 'tripwire'` 与 `output.tripwire` | **命中但已合规**：`server/src/mastra/stream-events.ts:555` 的 `case "tripwire"` 正是走 finishReason 分支，符合新契约 |
| 1.76 | Observational Memory 默认模型从 `google/gemini-2.5-flash` 改为 `'auto'` | **否**（本仓未启用 OM；`gemini-2.5-flash` 仅出现在 `server/tests/catalog-model-ref.test.ts` 的模型目录夹具里，与 OM 无关） |
| 1.77 | `@mastra/server` 的 workflow HTTP 路由**不再允许启动/恢复内部 workflow**（返回 404），durable agent 必须走 agent 路由 | **否**（本仓 Hono 只做 `/api/agents` 探活，见 `compatibility.ts:213-215`） |
| 1.79 | Agent controller 会话以 `sessionId` 为键（**移除 `scope` 参数**），core/controller/server 路由与 client-js 的 `controller.session()`/`session.create()` 签名同步变更 | **否**（本仓未用 Agent Controller / client-js 会话 API） |
| 1.79 | `querySpans()` 契约变更：移除 `model`/`provider` 过滤，响应去掉 `cost`/`inputTruncated`/`outputTruncated`/`errorTruncated`，**存储适配器需同步更新** | **否**（本仓无 `querySpans` 调用） |
| 1.79 | thread 行查询契约变更：改用 `timeRange.traces`/`timeRange.threads` 而非 `traces.timeRange` | **否** |
| 1.79 | Channel 的 `resolveResourceId`/`resolveThreadId` 上下文**必须传 `requestContext`** | **否**（本仓未用 channel resolver） |
| 1.80 | `queryTraceThreads()` 的 thread 行不再含 `model`/`provider`；**`page.limit` 上限 100（默认 25）**，超限校验失败 | **否** |
| 1.80 | `@mastra/connect` 建会话返回 `launchUrl` 而非 `connectUrl` | **否**（未用 connect） |
| 1.78 | `buildInputPreview()` / `INPUT_PREVIEW_MAX_LENGTH` 弃用，改用 `buildPreview()` / `PREVIEW_MAX_LENGTH` | **否**（本仓无引用） |

配套包侧与本仓相关的少数几条：
- **client-js 1.56**：`controller.session()` 改为接收 session id，resource 移到 `create()`，**移除 `scope` 参数**——本仓未用。
- **client-js 1.52**：AgentController `switchModel` 移除 options 参数——本仓未用。
- **client-js 1.57 / core 1.80**：`queryTraceThreads()` thread 行移除 `model`/`provider`——本仓未用。
- **memory 1.33**：Observational Memory 的 `scope: 'resource'` 标记 `@deprecated`（thread scope 明显更好）——本仓未启用 OM。
- **memory 1.30 / core / client-js / server 1.67**：新增 `Memory.updateThreadResourceId({threadId, resourceId})`，纯新增。
- **schema-compat 1.3.14**：Standard Schema 做输入转换时，tool `execute` 收到的是**转换后的输出类型**而非 input|output 联合类型——影响类型推断，运行时不变。

## 4. 依赖与底层变化（bun.lock 实测 diff）

- **AI SDK 大版本推进**：`@ai-sdk/provider-utils` 4.0.40→4.0.61 / 5.0.13→5.0.62，`@ai-sdk/provider` 2.0.3→2.0.5 / 3.0.14→3.0.19 / 4.0.4→4.0.29。同一上游 major 内的小版本推进，未跨 major。
- **core 新增直接依赖**：`hono` 4.13.13、`hono-openapi` 1.5.0、`re2js` 2.9.0、`yaml` 2.9.1。

## 5. 对 OpenBot 仓库的影响与需要关注的事

本仓真实使用面很小（排除 node_modules 后只有 `server/src/mastra/`、`server/tests/`、`agent-mastra/src/`）：`@mastra/core/agent`（`Agent`、`MastraDBMessage`、`convertMessages`）、`@mastra/core/mastra`（`Mastra`）、`@mastra/core/tools`（`createTool`、`Tool`）、`@mastra/core/workflows`（`createStep`、`createWorkflow`）、`@mastra/core/storage`（`InMemoryStore`）、`@mastra/core/schema`（`toStandardSchema`）、`@mastra/memory`（`Memory`）、`@mastra/pg`（`PostgresStore`）、`@mastra/hono`（`MastraServer`）。

需要关注的具体动作/风险：

1. **`server/tests/enterprise/mastra-compatibility.test.ts:51` 的 pin 已同步为 `1.80.0`**（本次未提交改动已改），`server/src/copilot.ts:4322` 的注释也从 1.43.0 同步到 1.57.0——这两处是本次升级的既有适配。
2. **双 peer 变体问题仍在**：`server/src/copilot.ts` 的注释说明本仓跑 zod 4 而 `@ag-ui/mastra` 依赖 zod 3，包管理器因此解析出两份 `@mastra/client-js`（现均为 1.57.0，代码相同但类型私有字段不同），跨接处靠一次 `as never` 强转。`@ag-ui/mastra@1.1.6` 的 peer 范围是 `@mastra/core >=1.29.0 <2.0.0-0`，**1.80.0 在范围内**，但桥接层本身仍是 1.1.6、未随上游跟进，是升级链上最脆的一环。
3. **审批恢复路径未受影响但需回归**：`server/src/mastra/resume-driver.ts:262` 走 `agent.resumeStream(data, { runId, toolCallId })`，与 1.72 改动的 `session.respondToToolApproval` 是不同 API；但 1.73 的默认错误恢复（repair-first + 安全重试）会改变失败重试行为，**审批失败重试路径需实测**。
4. **`stream-events.ts` 的 `tripwire` 分支已是新契约**（`finishReason === 'tripwire'`），与 1.73 的 chunk 语义变更一致；但 `server/src/mastra/stream-events.ts` 的 chunk 白名单（`text-delta`/`tool-call`/`tool-result`/`step-finish`/`finish`）在 1.68 之后上游 chunk 形状有增补（`tool-call-resumed` 等），**建议确认未知 chunk 不会走到 `UnknownMastraChunkError`**。
5. **PG 侧并发工作记忆修复对本仓是净收益**：memory 1.37 + pg 1.31 的「行锁事务内深合并」修复了 `scope: 'resource'` 下并发更新互相覆盖的问题——本仓 `PostgresStore` + 多进程部署正处在这个场景。
6. **`@mastra/hono` 1.7.22 的 FGA 授权绕过修复属于安全升级项**，若本仓部署了 Hono 自定义路由且启用 FGA，应作为升级动机而非顺带带过。
7. **未验证项**：本次未跑本仓测试套件（`server/tests/mastra-*.test.ts` 约 20 个文件、依赖 `openbot-test-pg` 容器 :5433），上游 release 原文与本仓代码面比对已完成，但**运行时行为未实测**。

## 附 2：@ag-ui/mastra 2.0.1 升级与 jose 归一（2026-10-30 追加）

**@ag-ui/mastra 1.1.6 → 2.0.1 已落地**（`server/package.json:19` + `bun.lock`）。验证：peer 全满足；2.0.0 移除的 API（`emitInterruptOutcome`/`forwardedProps.command`/`registerCopilotKit`/legacy binary part）本仓零使用；桥接面仅 `getRemoteAgents`/`getLocalAgents`/`MastraAgent` 三入口；typecheck 与 1.1.6 同错集；全量 mastra 套件 325 测试两版本 profile 逐项一致；审批挂起→恢复路径（resume-process）在 2.0.1 下全绿——正是 2.0.0「单中断 + 严格审批应答」破坏性变更的正面对抗面。注：2.0.1 仍依赖 zod 3，双 `@mastra/client-js` 副本强转（`copilot.ts`）不消除也不恶化。

**better-auth 双副本 typecheck 错已从根上修复**：根因是 mastra 升级带来的 `@mastra/client-js@1.57.0` 要 jose `^6.2.12` → 6.2.14，而 better-auth 生态停在 6.2.10，`@better-auth/core@1.7.1` 因此分裂成两个 peer 变体（唯一差异 = jose peer 版本），`auth/index.ts:1049` 的插件数组 TS2322。修法 = `bun update jose` 把 6.x 统一到 6.2.14（`@segment/analytics-node` 的 jose 5.10.0 独立嵌套不受影响）。回归：typecheck 0 错；mastra 全量 profile 不变；auth 单测（node 侧）40/40。CI 全新安装不再踩此坑。`auth/index.ts:884` 处另一会话加的 `as BetterAuthPlugin[]` 强转在根因修复后已冗余（可留可删）。

better-auth island 测试组（47 组）需 5 个 `BA_TEST_*` 库 URL 才运行，未配置时整组跳过（blocked）——环境门禁，与本升级无关。
