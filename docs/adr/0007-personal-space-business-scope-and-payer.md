# 以独立个人空间承载个人业务，并固定个人任务付款账户

用户确认产品面向个人和小型企业，并要求将本轮建议纳入规划。现有完整业务 Scope 依赖公司/团队，而个人模型授权只解决外部模型调用，不能直接承担完整个人 Agent 的工具、数据及运行权限。本 ADR 提出具体模型，**尚未获用户对书面架构方案的确认**；它不覆盖已接受的 ADR 0004/0006 或现有付款合同。

推荐增加本人拥有的 Personal Space（个人空间），与公司 Tenant、团队 Workspace 分开表达。个人执行范围绑定本人、个人空间和逻辑私有 Bot；公司执行范围继续使用公司、团队、本人和 Bot。范围类别、身份与对象归属均由服务端解析和验证，个人入口不是无 Scope 的公司入口，也不通过虚构公司获得权限。稳定的逻辑私有 Bot 复用身份，其环境、工具、连接、上下文及业务状态保持范围隔离。

推荐个人工作台的新业务调用固定消费已有个人 PayerRef；公司工作台仍固定公司 PayerRef，外部 Bot 的个人模型授权保持原路由。每笔调用在准入时固定付款事实，余额不足不切换账户；个人虚拟 Key 不提供业务工具授权。加入公司新增独立成员关系，不自动移动个人资料、连接、记忆、任务或余额；需要交付的有权正式产物通过明确目标授权处理。

此选择避免把“公司租户”悄悄改成个人身份，也避免让个人用户先设置一家虚构公司。代价是资源授权、数据库隔离、个人记忆映射、执行环境、付款准入及旧入口需要显式支持两类业务范围，不能把空 tenant、全局 owner 或同名 ID 当作安全边界。已有公司记忆不得迁为通用个人记忆，旧个人数据仅在归属可证时绑定；未知范围受控隔离。

未选“个人自动建一家公司并沿用全部组织语义”：上手可以隐藏界面，但会混淆公司成员、个人资产及公司/个人付款。未选“个人模式关闭租户检查”：会成为公司入口和后台任务的旁路。物理表结构、API 选择器、路由、迁移及代码接口由后续实施设计确定，不在本决策预先固定。

产品行为及验收见[产品规划 G01、X01–X02、X07、X19](../specs/2026-10-16-personal-smb-product-roadmap.md)及主规格 C07。确认此 ADR 之前，相关文字是可评审方案，不表示个人模式已经实现、原 Tenant 语义已修改或生产数据可迁移。
