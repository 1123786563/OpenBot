# Deploy the external OpenBot observability pipeline

Use this handoff with the [OpenBot configuration runbook](openobserve-runbook.md) and the [Collector Contrib sample](examples/openobserve-collector.yaml). The platform team operates the Collector, OpenObserve, identity gateway, and storage. Run the acceptance procedure in an isolated environment before enabling production ingestion.

## Provision OpenObserve

1. Create a dedicated OpenObserve organization for OpenBot and pre-create both streams as **Logs**. In Streams → Stream Details → Configuration, set `openbot_runtime` to **30 days** and `openbot_audit` to **90 days**. Turn off original-data storage and indexing. Leave extended retention unset. Read the saved settings back for both streams. The [stream settings API](https://openobserve.ai/docs/reference/api/stream/setting/) also supports `PUT /api/<org>/streams/<stream>/settings?type=logs` with `{"data_retention":30,"store_original_data":false,"index_original_data":false}` or the corresponding 90-day value.
2. Give the Collector an ingestion credential per stream through the platform secret store. Put the complete authorization header value in each secret, using the scheme generated by your OpenObserve installation. Use ingestion-only tokens where supported. Give platform administrators a separate identity through the platform OIDC gateway or OpenObserve SSO and RBAC. OpenBot sessions confer no access. Use the [OpenObserve ingestion guide](https://openobserve.ai/docs/ingestion/logs/otlp/) and [service account guide](https://openobserve.ai/docs/user-guide/account-administration/identity-and-access-management/service-accounts/) for the installed edition.
3. Route the browser UI and all query API paths through the administrator group check. For a gateway-based setup, bind the upstream privately and prevent direct queries to it. Expose a separate private ingestion route that accepts only a Collector identity, `POST /api/<org>/v1/logs`, and the exact stream name associated with that identity. Block direct access to other upstream paths and ports from ingestion clients. For an edition without scoped ingestion credentials, keep the upstream credential at that private gateway and inject it only after these path, method, and stream checks. Keep any bootstrap or break-glass credentials in the platform vault.
4. From the relevant client networks, exercise the query UI and its query API as a platform administrator, workspace member, unauthenticated caller, and ingest identity. Expect only the platform administrator to query. Exercise both ingestion identities against their own stream and the other stream. Verify that the public query URL and the internal ingestion URL enforce their respective controls. Hand the browser URL to the owner of the optional OpenBot administrator entry.

## Install the Collector

Use Collector Contrib 0.139.0 for the sample and revalidate the configuration and fixture when upgrading. Set these values before starting it.

| Variable | Example or source |
| --- | --- |
| `OPENBOT_DEPLOYMENT_ID` | A stable, unique identifier such as `production-east`, matching OpenBot's `DEPLOYMENT_ID` exactly. Use letters, digits, hyphens or underscores. |
| `OPENBOT_RUNTIME_LOG_GLOB` | Pod log paths matching only this OpenBot deployment, such as `/var/log/pods/openbot-prod_openbot-server-*_*/server/*.log`. Use explicit include entries for the API, worker, migration and routine workloads that actually exist. Retention diagnostics may share the API container. |
| `OPENOBSERVE_OTLP_LOGS_URL` | The full private logs URI, such as `https://observe-ingest.example.internal/api/openbot/v1/logs`. |
| `OPENOBSERVE_RUNTIME_AUTHORIZATION` | Runtime ingestion authorization header from Secret. |
| `OPENOBSERVE_AUDIT_AUTHORIZATION` | Audit ingestion authorization header from Secret. |

For Kubernetes, use a node-local DaemonSet with the container log directory mounted read-only. Confirm the actual namespace, pod and container names against the rendered releases. Select the complete API, worker, migration, retention and routine log sources, then verify that sidecar and other tenant logs are excluded. For a host deployment, use a receiver for its actual stdout/stderr framing and pass the application JSON line as the log body to the same runtime processors. For Docker JSON log files, mount the relevant log directory read-only and replace the sample's CRI framing check with one for Docker JSON before the container parser. Confirm the runtime receiver against the deployed logging driver before rollout.

Expose port 4318 through an internal Collector service for the audit route. Terminate TLS and validate the OpenBot producer identity at a private ingress or add TLS and client authentication to the OTLP receiver. Restrict access to that receiver to the authorized OpenBot API deployment, including access from elsewhere in the cluster. The sample binds HTTP inside the Collector and relies on this platform boundary. Use the Helm/Compose settings in the [OpenBot runbook](openobserve-runbook.md#openbot-configuration) to send audit OTLP to the Collector. The OpenBot-to-Collector credential and the Collector-to-OpenObserve credentials serve separate connections.

Validate with the intended environment values and run the synthetic fixture:

```sh
otelcol-contrib validate --config docs/examples/openobserve-collector.yaml
python3 docs/examples/check-openobserve-collector.py
```

### Privacy and delivery

Runtime and audit have independent receivers, processors, queues and exporters. Both pipelines rebuild from explicit field allowlists before buffering and export. They remove raw log bodies, free-text diagnostics, resource and scope attributes, and unknown fields. Messages, prompts, tool parameters and results, file contents, credentials, authorization headers and arbitrary objects are excluded. The runtime pipeline accepts version-1 structured events and catalogue-backed `legacy_unstructured` notices. It drops arbitrary legacy lines and unknown legacy event identifiers, and strips measurements and correlation IDs from legacy notices. The audit pipeline accepts the version-1 OpenBot audit envelope, keeps fixed scalar fields and applies event-specific, typed facet filters. For unknown or failed projections, only common fields survive. The Collector emits unprefixed audit attribute names and names approved facets `facet_<name>`. Confirm the stored column names with a sample query after ingestion.

Identifier fields assume the authenticated OpenBot producer and trusted workload log paths. Validate that these fields are populated from product identifiers before adding an event or field to the allowlist. Never enable Collector debug logging or an unfiltered exporter on deployment traffic. The local fixture uses synthetic data and substitutes file exporters after the privacy processors.

Queues are bounded and in-memory. Small ordering differences, retries, duplicates and loss after an outage are expected. Filter queries by `deployment_id` and use `occurred_at` for event chronology. Count each `audit_event_id` once within its deployment, for example with `COUNT(DISTINCT audit_event_id)` after applying the deployment filter. If copies for the same audit ID disagree, verify the event in PostgreSQL. With `start_at: end` and no checkpoint store, runtime collection starts at new lines. OpenBot emits new audit replicas after recent PostgreSQL inserts and does not replay the table. Bounded in-flight retries can deliver older records after recovery. Historical backfill and outage replay are outside the pipeline contract.

## Store and recover

Use encrypted storage with private, scoped access. For a clustered OpenObserve deployment, provision a dedicated object bucket or prefix for stream data and a dedicated PostgreSQL metadata store. For a single-node local installation, put the complete OpenObserve data directory, including SQLite metadata and local stream data, on durable storage. If local mode uses object storage, include the bucket in the recovery plan as well as the data directory. Follow the [OpenObserve storage guide](https://openobserve.ai/docs/administration/maintenance/storage-management/storage/) for the chosen topology.

Define a recovery point objective, recovery time objective, backup schedule and expiration before rollout. For a consistent offline recovery point, pause ingestion at the gateway, complete the platform's flush/quiesce procedure and stop OpenObserve writers and compactors. Take a matched backup of the metadata and object data or a consistent snapshot of the stopped local data directory. Record the OpenObserve version, UTC recovery point, backup identifiers, configuration and key references. Resume service and verify fresh ingestion. Use an equivalent coordinated online backup only when the platform can demonstrate metadata and object data consistency. Local files and unflushed ingest state require coverage if the chosen recovery procedure depends on them.

Restore into an isolated instance at the recorded version, with private networking and side effects such as alerts disabled. Restore matching metadata and stream data, apply the recorded configuration and restricted access, and verify both stream policies, deployment IDs, representative audit IDs and a fresh ingest/query. Expire backup copies and old object versions according to the platform's approved privacy and recovery policy. Document the snapshot retention separately from the live 30/90-day policy. Keep storage lifecycle rules compatible with OpenObserve's file references and retention compaction.

## Drill continuity and recovery

1. Record the deployment ID and UTC test window. Trigger a synthetic routine or Bot run, confirm its Activity and completion, and perform a benign auditable change. Record the audit UUID from PostgreSQL `audit_events` or OpenBot's administrator audit view. Confirm both streams receive the expected records and that sentinel content from privacy fixtures is absent.
2. Stop all Collector instances serving this test deployment, keeping the OpenBot API, workers, PostgreSQL and OpenObserve running. Confirm the audit receiver and runtime readers are down. Repeat the auditable change and run, including a normal model or harmless tool call when supported. Confirm business requests complete, the new audit row persists, and Activity and the run are visible. Record the outage duration, requests, run IDs, audit IDs and any delivery-error metrics.
3. Restart the Collector, confirm readiness, then perform a fresh run and auditable change. Check both streams for post-recovery events and inspect any duplicates with the deployment-scoped audit ID. In-flight records may arrive late. A gap after the retry window is expected. Confirm that the restart did not initiate a PostgreSQL scan or historical runtime import.
4. Restore the normal deployment, query settings and exporter health. Separately test the OpenObserve exporter failure path in staging by temporarily blocking the Collector's upstream or denying its ingestion requests. Confirm queues stay bounded and the same business checks still pass. Monitor failed receives/exports, queue saturation, OpenObserve write errors and post-recovery ingestion.

## Evidence to hand over

| Item | Record |
| --- | --- |
| Deployment | `DEPLOYMENT_ID`, environment, workload selectors, OpenBot revision |
| Collector | Version/image digest, config revision, private endpoint and allowed producer identity |
| OpenObserve | Version, organization, administrator browser URL, private OTLP URL |
| Streams | `openbot_runtime` / 30 days, `openbot_audit` / 90 days, saved settings and verification date |
| Access | Administrator IdP group, ingestion and query identity verification, secret references and rotation owner |
| Storage | Location, backup schedule and expiry, RPO/RTO, restore date and results |
| Acceptance | Fixture output, outage window, run IDs, audit UUIDs and evidence links |

PostgreSQL `audit_events` is authoritative for audit actions and has its own retention. OpenBot Activity and the underlying product ledgers are authoritative for product-visible history. Opik is the execution and model trace source when configured. OpenObserve holds the derived audit copy and searchable service diagnostics. Investigate gaps using the canonical source for the affected event.
