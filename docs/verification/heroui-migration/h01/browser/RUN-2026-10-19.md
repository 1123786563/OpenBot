## 已证伪（红，须修复后才能关闭 H01/H03 的 AC）

**ESC 级联关闭（H03 `dialog.tsx` 缺陷，2 次复现）**

- 步骤：打开 Dialog → 打开 Select → 按 Escape。
- 期望：仅关闭 Select 弹层，Dialog 保留，焦点回 trigger。
- 实际（无守卫版，run #1）：`afterSelectEsc = {dialogs: 0, optionsLeft: 0, focusOn: "BODY"}`
  —— Select 弹层与整个 Dialog **一起**关闭，焦点丢失到 body。
- 修复尝试 A（document capture 阶段对 popup 内 ESC 做 stopImmediatePropagation）：
  弹层与 Dialog 全都不关（`optionsLeft: 3, dialogs: 2`）——React 合成事件委托在根容器，
  document 捕获拦截会同时杀掉弹层自身的关闭。已回退。
- 修复尝试 B（记录 popup-ESC 时间戳，在 onOpenChange 里丢弃 200ms 内的关闭请求）：
  `afterSelectEsc = {dialogs: 2, optionsLeft: 3}` —— 弹层没收到自己的 ESC（焦点在 trigger 时
  弹层不消费），而 Modal 的 ESC 关闭也未被放行；`close-modal` 后 `dialogs` 仍为 2、焦点未恢复。
  已回退。
- 结论：两条拦截路径都不成立，需要在**弹层消费 ESC 后终止传播**的层面解决（候选：给
  Select/ComboBox 弹层容器加 bubble 阶段 Escape 监听，在 RAC 关闭弹层的同一处理器里
  `stopPropagation`，使事件不再到达 Modal 的处理器；或 Modal 侧改用 RAC 的
  `CloseTrigger`/受控 close 而非全局 ESC）。此项为 **H03 的 Critical 交互缺陷**（影响所有
  Dialog+Select/ComboBox 组合页面），H01 AC3/AC4 与 H03 AC4/AC5 未过，不得放行下游。
- 复现命令：`cd app && bunx vite --config vite.spike.config.ts --port 5199`，浏览器开
  `/spike.html`，控制台执行 `window.__runH01()`；红点在 `afterSelectEsc`。

## 2026-10-19 修复轮（真实键盘输入，browser-use press_key = 可信 CDP 输入）

前置：此前合成 `dispatchEvent` 事件不带 `isTrusted`，焦点管理路径不可信；本轮改用
`browser-use click/press_key`（CDP 真实输入）复跑。

**守卫最终形态**（`app/src/components/ui/dialog.tsx`，已过 typecheck 与 25/25 dialog 相关测试）：

1. document 捕获阶段监听 Escape：**仅当 `[role=listbox]`/`[role=menu]` 真实存在**且事件目标在
   popup/trigger 数据槽内时，把时间戳记入 `lastPopupEscapeAt`；
2. `Dialog` 包装 `onOpenChange`：200ms 内的"关闭"请求若来自 popup 已消费的 ESC 则丢弃
   （弹层自己关闭并把焦点还给 trigger）；
3. 关闭时把焦点还给打开前的元素：双 rAF 后、且仅当当前焦点是 body 或仍在退场 overlay 内
   （HeroUI 在退场动画后才拆 overlay，其清理会打断过早的 restore）。

**真实键盘证据（spike.html，Modal + Select 数值 ID）：**

- 打开 Dialog → 打开 Select → 点选 Gamma → 按 ESC：
  `{dialogs:1, options:0, focusOn:'modal-select-trigger', triggerText:'303'}` ✅ 只关弹层，
  焦点回 trigger，数值保留。
- 再按 ESC：`{dialogs:0}` ✅ 弹层已关时 ESC 正常关闭 Dialog。

**遗留（未解决，计 H03 缺陷单）**：

- ESC 焦点在**选项上**时（未点选、键盘导航进弹层），行为不稳定：一次复现弹层+Dialog 都未关
  （focus 停在 option `…-202`）。该路径待单独定位（RAC ListBoxItem 的 ESC 处理 vs 我的 stamp
  竞争），修复验收同上。
- 受控 render-prop 触发器的焦点返还：在 v8 一轮中 ESC#2 后焦点落在 BODY；加双 rAF restore 后
  v10 一轮因上面选项路径卡死未跑到该断言。焦点返还逻辑保留（有明确注释与守卫条件），验收
  待选项路径修复后一并跑。
- `triggerRole` 依旧无 `role="combobox"`（有 `aria-haspopup=listbox`，无障碍命名由 Dialog
  heading 关联）；是否必须补 role 由 H03 复审裁决。

## 2026-10-19 收口轮：两条遗留关闭 + 新边缘（快速连按 ESC）修复

**环境切换**：本轮 Qoder in-app Browser 视口不可用（0x0/hidden），改用独立 CDP harness：
`puppeteer-core@23 + 本机 Chrome headless`（/tmp/cdp-harness/{repro,matrix,probe-c,probe-d}.mjs）。
CDP `Input.dispatchKeyEvent`/click 产生 `isTrusted=true` 事件，与 browser-use press_key 同级可信，
且脚本化可重复。spike 服务器 http://localhost:5199/spike.html 不变。

**场景矩阵（动画开启，与 in-app browser 环境一致，7 项断言）**：

| 场景 | 断言 | 结果 |
| --- | --- | --- |
| A. trigger 焦点按 ESC | 弹层独关（dialogs:1,options:0,focus→trigger） | PASS |
| A. 再按 ESC | Dialog 关 + 焦点返还 `open-modal` | PASS |
| B. **选项焦点按 ESC（遗留 1）** | 弹层独关、焦点回 trigger；再按关 Dialog+焦点返还 | PASS |
| C. 弹层开着快速连按两次 ESC | Dialog 关、焦点返还 | PASS |
| D. 选项焦点 + 快速连按两次 ESC | Dialog 关、焦点返还 | PASS |
| E. Footer Close 按钮 | Dialog 关 + 焦点返还 `open-modal`（遗留 2） | PASS |

**结论：遗留 1（选项焦点 ESC）与遗留 2（受控 render-prop 触发器焦点返还）在最终守卫代码下
均为绿，本轮回路关闭。**

**新发现与修复：快速连按 ESC（间隔 < 弹层退场动画时长）**

- 复现：弹层开着时 ~10ms 间隔连按两次 ESC，Dialog 不关（3 轮复现）。
- 定位（probe）：`aria-expanded` 在 ESC#1 派发内同步翻转；ESC#2 时守卫并未拦截——是退场中的
  弹层把 ESC#2 吞掉（焦点困在 option 上约 200ms 才回 trigger），事件从未到达 Dialog；
  probe-c 的「ESC#2 未关」读数是立即采样撞上退场动画的假象，250ms 间隔（probe-d）正常关。
- 修复（`dialog.tsx` 守卫 v2）：
  1. **活弹层**（`aria-haspopup=listbox|menu` 且 `aria-expanded=true` + 焦点在弹层上下文）：
     盖**任务域 burst 标记**（`setTimeout 0` 过期），包装 `onOpenChange` 丢弃同一 task 内的
     关闭请求；时间戳 200ms 窗口整个删除（它是 C 失败的根因之一）。
  2. **垂死弹层**（无 expanded 层 + 焦点困在 `option/menuitem` 上）：document 捕获阶段
     `stopImmediatePropagation` 消费该 ESC，并经 `onOpenChangeRef` 代偿调用 `onOpenChange(false)`
     关闭 Dialog（仅受控 Dialog；非受控保持 RAC 自身行为）。
