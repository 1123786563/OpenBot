# Domain context

本仓库使用**单一领域上下文**，位于根目录 `CONTEXT.md`（AGENTS.md 引用的就是这个文件；本路径此前缺失，2026-10-18 由 #419 补齐）。没有按模块拆分的第二份术语表，也不要为某个子系统另起一份 `CONTEXT.md`。

## 各事实源的分工

- `CONTEXT.md`：**词汇**。`## Language` 下按主题分小节（用户与模型访问、公司与团队、个人记忆、计费与积分、计费准入），每个术语一条定义。它刻意不记实现，所以不要把流程、字段或接口形状写进去。
- `docs/specs/`：已批准需求、行为、范围、非目标与验收标准。
- `docs/adr/`：架构决策与约束，按 `NNNN-标题.md` 递增编号。
- `docs/plans/`：实施计划与执行证据。
- `docs/tickets/`：派发给实现者的 Ticket。

冲突时的优先级写在根 `AGENTS.md`：已批准 Spec 高于实施 Plan；实现与 ADR 或批准需求冲突要升级处理，不在实现阶段静默重新设计。

## 使用规则

1. 开工任何模块前，先在 `CONTEXT.md` 里查该模块的既有术语，用既有词命名与书写；查不到且这个词会反复出现，才补条目。
2. 改术语含义就是改领域模型：同一次变更里更新 `CONTEXT.md`，必要时补 ADR，不要只把新含义留在代码或聊天记录里。
3. 引用领域概念时带上出处（Spec 文件名、ADR 编号或 `CONTEXT.md` 小节），让读者能核对，而不是让读者相信你的复述。
4. `CONTEXT.md` 只增不删地堆积会失去作用：发现定义与批准需求漂移时，以需求为准修正定义，并在 ADR 或 Spec 里留下依据。
