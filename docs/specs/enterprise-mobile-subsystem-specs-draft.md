## 2. Cross-domain public contract

### 2.1 Version, identity, scope, schema

- Mobile public API prefix: `/api/enterprise/v1`. The path version is `v1`; every input/output has a strict runtime schema (Zod on the TypeScript side) and an explicit versioned contract artifact. No shared import of service-private types across repositories. Mobile DTO fields use `camelCase`; internal Go/TS wire contracts use strict `snake_case` and `schema_version: "v1"` as specified in enterprise master §4.2. Internal wire payloads and credentials never appear in client DTOs or AG-UI state.
- Identity proof is the current Better Auth user session. The server resolves a Directory principal and active membership. `x-openbot-tenant` is only a tenant selector; it is not proof, Scope, authorization, or authority. Client input cannot claim `tenantId` as trusted Scope, `principalId`, `userId`, `actorId`, role, permission, policy, approval, signature, lease, fencing token, capability, or receipt.
- Proposed public identity reads: `GET /api/enterprise/v1/me`, `GET /api/enterprise/v1/tenants`. Tenant listing precedes tenant selection; protected business requests require the selector. Selecting a tenant re-resolves active membership server-side. A cached `/scope` result is not a later credential.
- The established enterprise type names that may be exposed only where appropriate are `TenantSummary {id,name,role}`, `ScopeView {tenantId,principalId,role}`, `ResourceView {id,workspaceId,kind,revision}`, with `TenantRole = "tenant_admin" | "member" | "auditor"`. Do not expose membership epochs or database snapshots to mobile as authorizing capabilities.
- Contract DTO anchors from approved plan §5.1: `PersonalSession {channelId,botId,threadId,mode:"single"}`, `SubmitMessage {clientMessageId,text,attachmentIds}`, `Submission {messageId,runId,accepted:true}`, `PublicRunEvent {eventId,runId,seq,type,payload}`, `OperationReceipt {operationId,status,receiptRef,reconciliationRequired}` where status is exactly `not_submitted | submitted | succeeded | failed | unknown`. `payload: unknown` is only a placeholder in the planning sketch; C02 must replace it with a discriminated, strict event union before consumers treat it as typed.

### 2.2 Shared HTTP/error, pagination, trace and redaction

- Approved mobile-plan §5.2 proposes `{error:{code,message,requestId,retryable}}`, with meanings 401 unauthenticated/expired; 400 missing/invalid selector; 403 unauthorized; 404 restricted/not visible; 409 idempotency/revision conflict; 413 size; 415 type; 422 content; 429 quota; 503 unavailable. Tenancy plan §4.3 instead specifies `{error:{code,request_id,retryable,summary}}` and 500 for unknown program errors. This is a **source conflict** (camel vs snake request ID, message vs summary, and the latter's 500 behavior); C02 must obtain and record an explicit shared-public-error decision before schema acceptance. Internal enterprise errors must not be accidentally copied to mobile. Do not return raw database, provider, parser, or runtime errors.
- Cursor pagination is required by channel/history and C17/C23 domain plans, with stable ordering, but the authorities do not freeze cursor field names, page-size limits, or cursor binding. Exact pagination schema and tamper/stale-cursor behavior are an unresolved C02 gate; no offset or opaque cursor format is assumed here.
- Server generates a per-request correlation ID and returns it in the agreed error/header contract; do not trust or reflect a client-supplied request ID as authoritative. Keep business dedupe IDs (`clientMessageId`, `clientRequestId`, `operationId`, provider event/state identifiers) distinct from trace IDs. Trace context propagation/format across Runtime and provider requests remains to be frozen. Logs/audit use server-generated correlation and stable reason codes; never log session/OAuth/Computer tokens, authorization headers, raw message/document/provider content, signed capabilities, or private Computer addresses. Redact DTOs, errors, analytics, crash reports and URLs consistently.
- On every tenant switch/account switch/logout, cancel old requests, dispose Runtime/socket subscriptions, advance tenant/cache generation, remove old tenant/user cache visibility and reject late responses. Offline is read-only for previously authorized cached content and unsent drafts only. Reconnect reauthenticates/reselects tenant and rechecks current access; unknown writes are reconciled before user-confirmed resubmission. Never auto-replay an external or business write.

### 2.3 Single-writer, domain and audit conventions

- One authoritative writer per domain. Hono/Bun TypeScript control plane owns identity mapping, Scope, authorization, business ledgers and public routes. Go is a replaceable execution adapter, has no business DB access, and does not own the Run ledger. Node orchestration owns Temporal history only and advances work through internal commands. No OpenMuse PGlite/worker/Computer mirror is authoritative for enterprise data.
- Runtime/TS run domain owns Run/event/checkpoint; TS tool domain owns operation/receipt. Runtime workers propose events; TS validates, deduplicates and assigns durable sequence. Business-domain services own their records; the provider/Computer/parser is an executor, not a second business writer. DB domain ownership and event/audit ownership must be enforced rather than documented only.
- Security membership/ACL changes and their security audit record commit atomically under T1-C operation/lock rules. Runtime lifecycle, operation/receipt, approval, Computer control and PDF job audits must be owned by their respective authoritative domain. Mail/Calendar provider effects also retain TS operation receipts; provider acceptance is not replaced by an optimistic local “success.” Audit retention and read-access policy are unresolved across domains and block production acceptance.

### 2.4 Resource/action matrix (proposed minimum; not a grant)

`✓` means the action is separately representable and must be checked; it does not assert that every member has it. `—` means no implicit grant. `TBD / deny until specified` is a blocker: no inheritance from `read`, SSO, tenant selection, tenant role label, platform-admin role, or Bot ID.

## 3. Subsystem drafts

### 3.1 Identity and tenant

1. **Scope/endpoints/version.** Documented existing behavior: legacy `/api/me` and Better Auth/OAuth/SSO are described by the mobile integration source; that source also notes Native cookie storage, callback and cross-origin proof remain. Proposed enterprise public endpoints are `/api/enterprise/v1/me` and `/api/enterprise/v1/tenants`; protected feature routes use `x-openbot-tenant`. Better Auth auth paths are exact allowlisted methods/paths, not wildcard business routes. DTOs are strict and versioned under the common rules; a successful SSO session is not membership.
2. **Single writer.** Better Auth owns authentication session; enterprise identity/Directory/T1 tenancy service and PostgreSQL own `userId↔principalId`, tenant membership/role/status/epoch and ACL. Explicit provisioning owns membership changes. No OpenMuse identity mirror, self-enrollment, email-domain autojoin, or platform-admin content bypass.
3. **Linearization/idempotency.** Each request resolves fresh Scope; T2-B's sole authorized-resource read is one short `READ COMMITTED` transaction, setting local DB context and verifying current tenant/principal/member epoch and role under ordered advisory locks. Membership suspension commits epoch/state and security event atomically; replays use the stable `operationId` and identical complete payload or conflict. A change committed after an already-authorized response begins cannot retract bytes already sent; subsequent protected operations deny. No write operation for “select tenant” is implied.
4. **Auth/revocation.** User Session, active Directory principal, active tenant and active membership all required. `x-openbot-tenant` only selects among memberships; nonmembership/suspended is 403, inaccessible resource is 404 without existence leak, unavailable/corrupt auth state fails closed (503 per T2). Membership epoch is rechecked in short transactions. A long-lived stream/socket must independently reauthorize and terminate on revocation (Runtime/Computer gates below).
5. **Failure, audit, offline.** No silent fallback to shared admin/single-user or legacy API. Session expiry is 401; forbidden is not translated to “sign in”; tenant/caches are segregated by deployment/user/tenant/resource. Provisioning/grant/revoke/security events are recorded by T1 security-event owner atomically. Offline only displays previously authorized cache and drafts; no tenant change or business mutation until online revalidation.
6. **Evidence and gates.** Positive: two real test tenants/principals, authorized resource read, re-login/session restore and tenant list. Negative/security: unprovisioned SSO user, inactive/suspended tenant/principal/member, platform admin with no membership, forged selector/role/principal, A→B connection pool reuse and cache race, revoked session/membership/ACL. Failure: DB loss, lock timeout, stale epoch, broken session provider, audit write failure all fail closed. Needs isolated PostgreSQL with RLS roles/connection reuse and real test identity/SSO callback environment plus DBA/security/backend evidence. G0-T and F01/T1–T3 are not demonstrated by this draft; no database/IdP test resources were accessed.

### 3.2 Runtime, Runs and Events

1. **Scope/endpoints/version.** Proposed mobile endpoints: `POST /api/enterprise/v1/channels/:channelId/messages`; `GET .../submissions/:clientMessageId`; `GET .../history`; version-frozen compatible Runtime routes under `/api/enterprise/v1/runtime`; `GET /api/enterprise/v1/runs/:runId`; `GET .../events` with `afterSeq`; `POST .../cancel`. These names follow approved plan §5.2/C07/C10 and are proposed, not existing routes. Run/Connect/Stop/history must match C01's exact RN SDK discovery/transport sample; do not treat `/api/copilotkit` output as raw SSE or connect directly to a Bot AG-UI endpoint. Mobile DTOs include Submission/PublicRunEvent/OperationReceipt; strict versioned AG-UI union and event payloads, event ID and seq are required.
2. **Single writer.** MessageService owns user-message acceptance; TS enterprise Run service is sole writer of business Run, attempts, durable lifecycle/events/checkpoints; TS tool domain owns operation receipt. Node writes orchestration history only; Go execution state is rebuildable. Runtime facade calls same MessageService/Run service as nonstreaming submission and is not a second run path.
3. **Linearization/idempotency.** Message, business Run, budget reservation and Outbox commit in one transaction. Deduplication key is `(tenant, principal, channel, clientMessageId)`; same key/same body returns the same message/run; same key/different body is 409. Conversation creation uses `clientRequestId`; same key with different Bot is 409. Source events deduplicate on `(tenant_id,run_id,attempt_id,source_event_id)`; same key/different payload rejects; TS assigns monotonic `seq` after persistence and before publication/ACK. Tool operation deduplicates `(tenant_id,run_id,tool_call_id)` and binds step/target/args digest/installation version. `accepted:true`/HTTP 202 means accepted only.
4. **Auth/revocation.** Session + active tenant Scope + channel/Bot relation and separate read/run/cancel/tool/approve permissions are checked on submission, history, Runtime Run/Connect/Stop, event subscription, reconnect and every consequential tool operation. Runtime invocation internal wire follows master §4.2: strict `schema_version, tenant_id, principal_id, actor_id, initiator_kind, run_id, attempt_id, turn_id, thread_id, expert_version, input_digest, model_route_ref, budget_reservation_id, lease_id, fencing_token, expires_at`, plus `delegation_ref` for scheduled work; Go service identity/capability is not client DTO. Current membership, delegation, lease/fencing revalidated; revocation closes active subscription and prevents later operations. A client event cursor is not authorization.
5. **Failure, audit, offline.** Outbox/workflow start reconciles stable workflow ID after crash; no second Run. Reconnect replays by seq without restarting; duplicate historical/live overlap ignored by event ID/seq. Stop is `cancel_requested`, not `cancelled`; only confirmed worker exit establishes terminal cancel. Submitted/unknown side effect freezes automatic retries, is looked up by operation receipt or manually reconciled; never change ID to retry. Run/operation ledger owns audit/receipt. Offline history/cache read-only and drafts remain local; user re-confirms a reconciled submission after online auth.
6. **Evidence and gates.** Positive: C07 same-key submit yields one message/run/outbox; C10 fixed SDK run/connect/stop/history, persisted replay and sequence; cross-platform same channel. Negative/security: no session, wrong tenant/channel/Bot, mismatched SDK user, stale lease/fencing, forged events/tool results/system instructions, unauthorized history or cancel, duplicate/different-body submissions. Failure: commit followed by response loss, outbox redelivery, worker/runtime/API restart, duplicate event ACK loss, tool unknown/receipt ACK loss, cancel race, revoked live stream; prove no duplicate side effect. Requires C01 golden SDK/Native auth samples, F01 tenancy test DB and F02 persistent Run/Tool service. Runtime G0-R/G1a and G1b evidence per master §6 remains unclaimed; Go candidate does not authorize tenant load or real tools.

### 3.3 Computer

1. **Scope/endpoints/version.** Proposed enterprise namespace is `/api/enterprise/v1/computers/:botId/*`, adapting legacy status/screenshot/stream/snapshot/navigate/click/type/key/scroll/files and control request/take/release concepts. Exact route methods, schemas, WS subprotocol/auth transport, limits and operation receipt binding remain to be frozen in C02/C14; the old `/api/computers/:botId/*` route is not enterprise authorization. DTO must expose neither private Computer/supervisor URLs nor tokens. `snapshotId` scopes opaque refs; handover uses service-issued `requestId`.
2. **Single writer.** Enterprise TS Computer gateway owns tenant/Bot authorization, ActionPolicy, approval checks, control ownership and audit/operation intent. The Bot Computer service owns actual desktop/browser process and screen state. Tool ledger owns consequential external operation/receipt; no Mobile/OpenMuse Computer, direct private port, or second sandbox can write these effects.
3. **Linearization/idempotency.** A control request/take/release must linearize in a durable control lease/request state; each action validates current tenant/Bot grant, exact snapshot ID, action and target, then persists operation intent before forwarding to Computer. `requestId` and `snapshotId` are documented stable references. The authorities do not specify operation-ID/idempotency scope or atomic lease-vs-action protocol; exact key, lease generation/fencing, and external effect linearization are blocking C02/C14 design decisions. Do not pretend HTTP request arrival is transaction commit or successful desktop effect.
4. **Auth/revocation.** Require session+tenant Scope, Bot-specific permissions, action-specific Policy and current control lease. WS upgrade receives equivalent auth/tenant/resource/action checks as HTTP; no long-lived token in URL. Active stream closes on revoke. Human holds control ⇒ Bot writes denied; stale snapshot refs rejected. `read` does not authorize navigate/click/type/file write/exec or control transfer. Platform administrator/Bot ID possession grants nothing.
5. **Failure, audit, offline.** Control request/lease, policy decision and operation receipt audit belong to TS control/tool domains. Ambiguous screen or action outcomes display uncertain and reconcile by receipt; no automatic repeat. Human input is not queued for offline execution. Screenshots may be explicit degradation for stream, not evidence of control. Offline can show cached prior frame with stale indicator only; all action calls are online and current-authorized.
6. **Evidence and gates.** Positive: authorized status/screenshot and stream, snapshot-bound click, request→take→act→release, resume. Negative/security: cross-tenant WS upgrade, revoked membership/Bot grant, stale snapshot/ref, fake request ID, absent control lease, token/private URL leakage, Bot action during human control. Failure: WS revoke/close, expired lease, API restart, response loss after click/write, stale fencing, takeover race; prove no unsafe duplicate. Requires isolated Computer/Bot deployment, disposable test site and real user test session; approval/policy/receipt backend and operations owner. C14 plus F01/F02; no private endpoint, external target, or live account used, and this draft cannot close the missing lease/idempotency protocol.

### 3.4 Goals and Milestones

1. **Scope/endpoints/version.** C21 plans a new persisted Goal/Milestone domain because OpenBot has no exact equivalent. Proposed enterprise resources are `/api/enterprise/v1/goals` and Goal-scoped Milestone resources; exact methods/path shapes and schemas are not specified in approved plan §5.2/C21 and remain to freeze before coding. Use Goal status exactly `active | paused | completed`; Milestone completion is explicit boolean and revision; Goal/Milestone writes carry optimistic `revision`. Do not equate Goal with Task or Routine.
2. **Single writer.** Enterprise Goals service/schema owns Goal, Milestone and, subject to explicit ownership decision, the Goal↔Task link record. Task service owns Task instance/result; Routine/scheduler owns routine and scheduling. No OpenMuse/PGlite mirror, automatic migration from old Goals, or cross-domain direct row updates. The cross-domain link owner is unresolved: C02 must assign it before acceptance; proposed safe boundary is command routed to its named owner and explicit association, with neither service mutating the other's aggregate.
3. **Linearization/idempotency.** Goal/Milestone mutation commits in the Goals domain transaction with revision compare-and-swap; stale revision returns 409. The Goal↔Task relationship must be protected by a tenant-composite foreign key, and both Task and Goal tenant/ACL must also be validated in the controlled association operation. The foreign key is a required database integrity invariant, not a substitute for authorization. Exact cross-domain consistency/transaction or outbox protocol is unspecified and blocks link acceptance, but does not weaken or defer the composite-FK requirement. No idempotency key is defined for Goal creation or repeated milestone actions; C02 must freeze stable mutation identity/replay semantics before supporting retries.
4. **Auth/revocation.** Distinct list/read/create/update/reorder/complete/delete/link/unlink permissions; cannot infer completion/edit from read. Every request rechecks active tenant membership and Goal/resource ACL. Revocation after screen load blocks next write; no optimistic saved UI until server confirms. Goal completion does not cancel Task; Goal pause does not pause Routine. Sharing is out of scope pending explicit design.
5. **Failure, audit, offline.** Goal service owns Goal/Milestone audit/change history; Task and Routine owner retain their own execution audit. Conflict reloads authorized latest state and asks user; ambiguous mutations query by frozen idempotency/version before user-confirmed retry. Offline cached Goals read-only; local draft can be retained but cannot claim saved.
6. **Evidence and gates.** Positive: create/edit/status transitions, add/remove/order/complete milestones, restart durability and explainable task association. Negative/security: cross-tenant/wrong Task link, unauthorized action, stale revision, deleted/revoked Goal, stale loaded UI. Failure: concurrent updates, transaction loss/response lost, store restart, partial link update; verify rollback/reconcile. Needs isolated DB/migrations test, tenancy ACL fixtures, product/domain decisions on delete/history/link owner, and explicit operation keys. C21 depends on C17; no Goal data model/API was tested or introduced here.

### 3.5 Google/Microsoft connections and Mail/Calendar

1. **Scope/endpoints/version.** Proposed `/api/enterprise/v1/connections`, `/mail`, and `/calendar` families. C22/C23 specify capabilities but do not enumerate frozen HTTP method/route schemas; route inventory, paging/cursor, provider IDs and error mapping are blocking C02 decisions. Google Gmail/Calendar and Microsoft 365 Mail/Calendar both required; normalized ViewModel retains provider plus opaque provider resource ID. Connection lifecycle: user-delegated OAuth with PKCE/state, fixed callback, minimal read scopes; write scopes require separate consent. Mail: list/detail/thread/attachment reference/draft/approved send. Calendar: range/events/timezone display and approved create/update/cancel. Define provider-safe semantics for timezone and DST transitions, all-day events, recurring events, and operations on a single occurrence; disable unsupported complex recurrence edits explicitly rather than guessing.
2. **Single writer.** Enterprise Connections service owns connection status, provider/account/tenant/principal binding, generation and encrypted secret reference. Approved Secrets broker owns token material; it is never stored in mobile/cache/logs and no second plaintext token store is added. Mail/Calendar service owns local operation intent/receipt and normalized metadata; Google/Microsoft remain authoritative for provider messages/events and actual external effect. Provider connector performs I/O but cannot write another domain's ledger. SSO does not grant provider access.
3. **Linearization/idempotency.** OAuth `state` is bound to initiating user, tenant, provider and connection generation; only validated callback commits connection state; replay/late callback after disconnect or generation change rejected. Writes use prepare→preview→approval digest→recheck current membership/connection generation/permissions→execute via TS tool receipt. Approval digest binds mail recipient/body/attachment or calendar target/time/timezone; any change requires a new approval. Provider acknowledgment is external effect boundary. Retry only when provider idempotency or a verified query proves safe; otherwise lost response = `unknown` and reconcile/manual review. Google/Microsoft idempotency tokens and write version keys are not specified and must be frozen per provider/API before acceptance.
4. **Auth/revocation.** Require member Scope plus explicit connection-read/manage/connect/disconnect and provider-specific read/write/send/calendar action grants; no shared mailbox or application-wide Graph authority in this scope. Recheck active member, connection status+generation, provider grant, object ACL, action Policy, approval and budget at execute, not only OAuth completion. Revoke/disconnect invalidates future actions and late refresh/callback; in-flight operation outcome remains unknown until reconciled. Do not expand permission based on tenant admin, SSO, or a provider connection to unrelated resources.
5. **Failure, audit, offline.** Connections service records connect/refresh/disconnect/consent state; Tool operation ledger owns prepare/execute/receipt; domain audit references provider but redacts content and token. Refresh single-flight; revoked/expired connection blocks writes. Provider 429/503 is not success; respect safe retry guidance only for read/idempotent requests. Unknown send/event write remains frozen, is queried or escalated to human reconciliation, never resent automatically. Mail attachments must flow through the C20 asset-permission chain; a provider attachment reference alone does not authorize reading, downloading, caching, or sharing its content. Sanitize rendered message content and block remote tracking content (including remote image/resource loads); do not execute email HTML. Offline may show authorized cached metadata read-only and retain draft only; sending/saving provider writes requires network, current consent and user approval.
6. **Evidence and gates.** Positive: Google and Microsoft test accounts each complete consent, reconnect/refresh, disconnect/revoke, authorized reads, approved sandbox send, event create/update/cancel, and provider-safe timezone/DST, all-day, recurrence, and single-occurrence behavior. Negative/security: wrong tenant/principal callback, state replay/mismatch, stale generation after disconnect, missing read/write scope, approval body/recipient/timezone change, forbidden shared mailbox/app scope, secret leakage, attachment access bypassing C20 asset ACL, unauthorized attachment download/cache/share, unsanitized message content, and remote tracking loads. Failure: refresh race, provider 401/429/5xx, response lost after send/event write, callback after disconnect, duplicate approve, revoked attachment access, and blocked/failed content sanitization; prove reconciliation without duplicate external write or unauthorized content access. Requires isolated provider app registrations, sandbox/test user accounts, consent/admin policy, approved sandbox recipients/calendars, Secrets broker, C20 asset-permission and content-sanitization implementation, and write approval owner. C22 depends on C19/F02; C23 depends on C22/C13. No provider accounts/resources accessed; neither provider nor G1b/G2 acceptance claimed.

### 3.6 PDF

1. **Scope/endpoints/version.** Proposed `/api/enterprise/v1/files` upload/asset contract (owned by C20) and `/api/enterprise/v1/pdf-jobs` import/inspect/fill/job/receipt contract (C24); exact routes and DTOs are not frozen. PDF is not admitted by simply loosening chat MIME types. Plan's documented OpenMuse behavior/limits: max `10 * 1024 * 1024` bytes and 500 pages; reject over-limit with 413/422, and explicitly fail malformed, encrypted, malicious or non-fillable input. These are planned inherited limits, not independently measured results. Schemas must bind source asset reference/hash, job/status, preview, output asset reference and receipt; details/fields must be frozen before implementation.
2. **Single writer.** C20 Files service owns uploaded source/output asset metadata, object keys, scan state and access; PDF service owns PDF job lifecycle and result/receipt; isolated parser worker processes but does not own business state. Tool/approval domain owns consequential operation and approval receipt. Output is a new asset; original is never overwritten. No OpenMuse Worker/store or API-process unbounded parser as another writer.
3. **Linearization/idempotency.** Upload acceptance commits authorized asset metadata, then job and Outbox commit as one durable intent before parser execution. Preview binds source hash, field set and operation parameters; approval binds same digest; output creation is keyed by stable operation and source digest so recovery does not create duplicate outputs. C24 requires idempotent operation/artifact association but does not name the job-create key, transaction schema, parser receipt or output uniqueness constraint. Freeze them in C02/C24; do not claim exact-once processing before then.
4. **Auth/revocation.** Upload/import, source read, inspect, approve/fill, output read/download/share are distinct actions under current tenant Scope and asset ACL. Recheck permission on job execution and each output/download, not just upload-time. Revoked access blocks new reads/downloads and processing steps before effect; already-started parser outcome is reconciled. Source hash/reference cannot authorize access by possession. Mail attachment export remains C23 approval path.
