# 计费支付：账户归属、收款交付与异常处置设计

状态：已批准。用户于 2026-10-15 确认本书面方案；公司既可在线购买，也可由授权管理员发放积分。本次确认以本文件为后续实施计划的需求依据，不表示已批准实施、迁移、提交或发布。

## 目标与事实源

每笔订单、支付、订阅周期、积分发放和模型消费均能确定付款账户、受益账户、发起人、资金或用量事实、当前处理状态及处置证据。已收款未交付不能被表示为完成；未知费用不能被表示为免费。

沿用 `docs/specs/2026-10-14-company-team-multitenancy-design.md`、`docs/adr/0004-company-team-tenancy.md` 的公司工作台公司付款、外部授权 Bot 个人付款决定，以及 `docs/specs/2026-10-14-bifrost-github-spec.md` 的个人授权和严格预留要求。复用现有支付事实、Lago 订阅投影、CreditWriter 和 Credit Ledger；不创建第二套积分账本。

本方案的以下明确规则覆盖旧计费可靠性设计中相冲突的局部规则：严格计费的未决预留一直占用容量；订单归属必须表示付款账户，`created_by` 仅表示发起人；公司在线购买可进入公司账户。旧文档对过期 hold 重新放出容量、订单只有个人创建人归属的描述不可作为新路径的实施依据。现有代码仍需迁移，文档决定不代表功能已交付。

## 范围

- 个人与公司在线购买套餐；公司还可由授权管理员直接发放额度。两种公司额度进入同一公司积分账户，各自保留来源。
- 支付确认、订阅首期和续期、周期积分发放、重复或迟到收款、退款或人工处置、只读对账和账务展示。
- 公司工作台和外部个人 Bot 的用量、预留、结算及尾差按原付款账户隔离。

不在本设计中定义新的套餐价格、折扣、税务发票格式、自动退款政策或新的支付渠道。正式发票如需提供，另立产品和合规规格；现有订单视图称为支付记录。

## 领域身份与授权

`PayerRef = { type: personal | company, id }` 是账户归属的不可变业务标识。个人 `id` 是稳定用户 ID；公司 `id` 是稳定 Tenant ID。两类 ID 的唯一键和幂等域均包含 `type`，不能因字符串相同发生混用。一个 PayerRef 对应一个明确的本地积分账户及外部计费 Customer 映射；多团队共享公司的一个余额。

`OrderActor` 是发起购买的登录用户；`PayerRef` 是购买和后续积分归属。支付渠道回调只能通过服务器保存的订单找到 PayerRef，不读取回调、客户端 body/header 或当前选中的团队来更改它。个人购买要求 actor 等于个人付款账户；公司购买要求 actor 对该公司具有明确的采购权限。公司管理员直接发放要求独立的发放权限和原因，不能复用普通采购权限。权限失效阻止新订单或发放，不改写已有资金、订阅和待结算归属。

个人订单由本人查看；公司订单由创建人及获授权的公司财务人员查看。公司成员身份本身不授予财务可见性。付款二维码等 checkout 材料只向创建人或明确可继续处理该订单的授权财务人员返回。跨账户读取统一返回不暴露对象存在性的结果。后台任务以订单保存的 PayerRef 工作，不以执行任务时的登录用户或公司选择器推断归属。

## 订单、收款与交付

订单创建时锁定 PayerRef、发起人、套餐版本、金额最小货币单位、币种、购买周期、预计积分、渠道和有效期。目录变更不重定价既有订单。订单 ID 全局唯一；一笔渠道交易在同一渠道内只能成为一笔收款事实，唯一键包含渠道及交易 ID。数据库在 PayerRef 范围内约束并发待支付购买；不同个人或公司可以同时购买。是否允许同一账户的套餐更换，以现有订阅权益规则判定，不能用部署级锁互相阻塞。

支付渠道验签后，对渠道权威交易查单并核对订单号、交易 ID、金额、币种、渠道状态。确认收款事实和本地订单收款状态在一个事务中提交；存储失败返回可重试响应。回调重复投递必须读回同一事实，不重复交付。金额、币种、订单或交易归属不符时记录异常，阻止自动权益交付；未经证据不能把它写成正常已支付。

收款状态与交付状态独立。交付状态至少区分 `pending`、`processing`、`delivered`、`needs_resolution`；每次失败保留原因和下一次重试时间。收款已确认但交付未完成时，对用户显示“已付款，权益处理中”，并对运营告警。订阅激活与积分发放分别具有稳定幂等键；其中一步成功、另一步失败时只重试未完成项。交付完成的判断必须同时核对订阅权益和本期应发积分，不依赖一次函数调用返回成功。

每次渠道实际收款均保留独立资金事实。重复、迟到或落在已被另一订单覆盖的权益周期的收款不得再次发放同一权益，进入 `needs_resolution`。该状态不能永远只靠无限重试：运营必须能查看证据、执行授权处置并留下最终结果。自动退款不在本期范围内。

## 订阅周期与积分发放

订阅在创建时从订单继承不可变 PayerRef。每个周期有稳定的外部周期标识、起止时间、套餐版本、收款依据、应发积分、Grant ID 和交付状态。首期和续期使用同一套周期处理规则。周期积分发放幂等键由订阅 ID 与稳定周期标识组成；通知 ID 仅用于投递去重，不能替代周期身份。相同周期重复通知只返回已有 Grant；不同周期不能共用键。

续期成功且对应收款依据已确认，才创建该周期 Grant。续期失败或费用未知时不预发积分。补缴、周期时间修正或迟到通知先查权威订阅与收款事实，再判断是否补发、保持原周期或进入异常；不得根据回调到达日期自行生成周期。取消订阅阻止未来周期续期，既有已付款周期按锁定权益规则保留至结束；渠道退款是否撤销尚未消费的积分需在退款个案中依据已消费、已预留和有效期核算，不能直接删除 Grant 或历史 Ledger。

Grant 来源明确区分 `plan_purchase`、`plan_renewal`、`admin_company`、既有奖励及其他已批准来源。管理员公司发放不创建虚假的支付订单或收款事实；它记录公司 PayerRef、发放人、理由、额度、有效期和审计关联。所有额度使用同一账户并发预留规则，团队用量只作归属统计，不复制余额。

## 严格消费与未知结果

对启用严格计费的账户，可用容量 = 尚有效且未消费的 Grant 容量 − 所有仍未解决的预留 − 应计尾差容量。预留的技术期限只触发调查和告警；结果未知时即使期限已过，也不得重新放出容量。已有旧逻辑的 expired hold lazy reclaim 不可用于严格路径。已准入调用在 Grant 过期后仍从原分配结算，释放的过期剩余额度不再次可用。

每次提供商尝试或可独立计费单元都有稳定身份及可强制费用上限。没有完整价格、可靠用量或强制上限的能力拒绝执行，并在购买前的能力说明中显示不可用原因。异常实际费用超过已证明上限时冻结受影响能力、保留用量证据并告警，不能以负余额或静默免单掩盖保证失效。

## 异常处置与对账

异常记录关联订单、渠道交易、订阅周期、Grant、预留或消费尝试，并保存证据、发现时间、责任账户、处理状态和操作审计。至少覆盖已收款未交付、重复或迟到收款、金额/币种不符、续期周期冲突、未知消费、超上限费用及账本漂移。异常不改变原始事实。

对账是只读检查：逐账户比较支付交易与订单、已付款订单与周期交付、周期与 Grant、Grant 与 Ledger、预留与结算，以及本地用量与供应商用量。报告包含个体交易 ID 和归属账户，不能只用汇总数掩盖相互抵消的差异。

处置是单独的授权动作：确认交付、确认无费用后释放、依据可靠费用结算、补发、发起渠道退款，或记录平台承担损失。每个动作记录操作者、证据、金额/单位、理由及幂等键；退款必须先核对渠道可退金额与已有退款，且不能通过直接删除积分记录“回滚”。无法确定资金或用量事实时保持未决并持续告警。具体退款时限、手续费承担、通知文案和税务处理在上线退款能力前另行批准；在此之前只允许有证据的人工渠道处置并在系统内登记结果。

## 页面与账务语义

支付记录显示订单金额、币种、渠道、收款时间、付款账户、交付进度及异常处置进度；订阅页显示周期与权益；积分页显示可用、预留/待结算、已消费、过期及来源；用量页显示按同一账户结算的费用依据、积分与未结算状态。Lago 估算或供应商美元成本不得标为人民币实付金额。个人与公司账户必须有清晰标识，用户切换团队不能让同一公司余额被显示为不同钱包。没有正式发票事实时，界面不把本地订单视图称为正式发票。

## 验收场景

1. 用户甲与公司 A 同时购买：各自订单、订阅及 Grant 归属正确；用户乙、公司 B 不能读写或领取；公司 A 有财务权限者能查看公司订单，普通成员不能。
2. 公司 A 两个团队并发消费同一余额，只允许总额内的预留；外部 Bot 个人 Key 只消费个人余额，余额不足不改扣公司余额。
3. 公司财务在线购买与管理员直接发放同时发生，两个来源记录可区分，余额正确相加；管理员发放没有虚构支付事实。
4. 同一渠道交易重复回调、两笔不同交易落到同一订单、过期订单迟到付款，资金事实不丢失且同一期权益只交付一次；异常进入可处置队列。
5. 收款后 Lago 不可用或积分写入失败，页面显示权益处理中；服务恢复后只补齐缺项，最终订阅与 Grant 都到位。
6. 同一续期周期的重复和乱序通知只发一次；下一周期独立发放；失败续期不预发；补缴和周期更正依据权威事实核定。
7. 未知费用预留跨技术期限仍占余额；确认费用后结算，确认无费用后释放；Grant 中途过期时结算与释放遵守原分配和过期规则。
8. 对账能识别单边缺失、双边相互抵消及跨账户错配；处置保持原始资金与 Ledger 事实，并有权限、证据和幂等验证。
9. 购买前可见所购能力的实际可用状态；不可计费或无强制上限的能力不会在支付后被误表示为可用。

## 实施切片与迁移边界

按纵向业务切片规划：账户与授权化购买；收款及交付闭环；订阅续期与公司管理员发放；异常处置及对账；账务展示与端到端验收。每个切片必须同时覆盖必要的存储约束、接口、授权、后台恢复及可观察行为。具体文件、迁移、回退和依赖留待实施计划在检查现有数据与代码后确定。

迁移前必须盘点部署级 Customer、订单、订阅、Grant、预留及在途支付。能由证据确定归属的历史记录才迁移到对应 PayerRef；不明归属隔离调查，不猜测、不复制余额到个人和公司两处。迁移期间避免新旧路径同时对同一账户计算可用容量。公司历史账务及个人账务均保留必要事实，测试数据清理须另按已批准精确范围执行。
