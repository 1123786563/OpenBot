# 公司与团队多租户整改设计

状态：书面设计已获用户批准（2026-10-14），作为实施计划的需求依据；尚未批准具体实施计划或执行方法。公司工作台采用公司余额；外部 Bot 直连 Bifrost 保留个人余额，见 §7、§10。相关架构决定记录在 `docs/adr/0004-company-team-tenancy.md`，状态为 accepted。

日期：2026-10-14。证据来源：本次用户确认、本地代码与文档静态读取；未运行部署、测试或性能评估。本次不执行迁移、发布或生产代码修改。

## 1. 目标与已确认需求

以最少必要架构调整，将现有系统整改为服务多家公司、每家公司多个团队的系统。全部现有功能完成隔离并通过验收后统一开放多租户，不以只开放部分功能作为交付。

| 编号 | 用户确认的需求 |
| --- | --- |
| R1 | 一个平台服务多家公司，每家公司内支持多个团队。 |
| R2 | 公司之间隔离；同公司团队之间默认互不可见。 |
| R3 | 员工可以加入同一家公司的多个团队。 |
| R4 | 加入团队后自动获得团队公共 Bot、公共知识库使用权；个人会话、文件和凭据保留个人权限。 |
| R5 | 所有现有功能完成隔离后统一上线。实施允许分批，开放门槛统一。 |
| R6 | 公司工作台采用公司统一余额，团队分别统计用量。 |
| R7 | 外部 Bot 直连 Bifrost 保留已有个人余额机制，个人模型授权及独立撤销规则保留。 |

R6 与 R7 是两类明确的付款账户；用户最新“保留”按保留既有 Bifrost 个人计费决定处理。不得因两个入口属于同一个产品而合并余额或自动切换付款方。

## 3. 路线选择与范围控制

推荐共享应用、共享 PostgreSQL，沿现有业务模块补齐隔离。保留 TypeScript/Hono/Bun 控制平面、现有 Worker、运行协议及前端；本整改不要求迁移技术栈或建设新的权限服务。

替代方案：每公司独立部署最少改业务代码，但不满足本次共享平台目标；每公司独立数据库增加连接路由、全库迁移和运营复杂度，当前没有独立数据库需求，不选。

最小改动指复用权威存储和已有授权/执行链路，不指减少安全校验或测试。不得承诺固定文件数、工期或性能收益；当前未完成逐文件工作量评估。

首期团队平级，每家公司可有默认 Workspace。部门树、上下级权限继承、跨公司分享、团队独立钱包均不纳入本设计。保留现有分享能力时，受众限制为同公司且明确授权；默认不跨团队公开。

## 4. 身份、团队与数据归属

### 4.1 身份与成员

User/Principal 是全局身份，Tenant 是公司，Workspace 是公司内团队。公司成员关系及团队成员关系都支持多对多。

新增 Workspace Membership，唯一成员关系为 `(tenant_id, workspace_id, principal_id)`，包含 active/suspended 状态及授权变更版本。复合关联必须同时证明 Workspace 属于该公司、Principal 是该公司成员。公司成员暂停后，其全部团队权限失效。

角色复用现有公司角色；团队管理使用明确、有限的管理权限。管理权限与内容访问分别判断：公司管理身份不默认拥有所有个人内容或非成员团队内容。团队管理者也不因此读取其他成员的个人凭据或会话。

### 4.2 归属规则

| 数据类别 | 归属与处理 |
| --- | --- |
| 全局身份、会话认证、平台静态公共目录 | 保留全局归属，独立授权，不填虚假租户标识。 |
| 公司成员、SSO/SCIM 配置、公司余额、订单与公司配置 | tenant_id；团队报表按工作范围限制，不能用公司余额共用推导内容共用。 |
| 团队 Bot、知识库、团队策略、团队发布资源 | tenant_id + workspace_id。 |
| 个人会话、业务记忆、个人文件、个人连接凭据 | 在所属公司/团队范围内进一步限制个人权限，禁止只用全局 user_id 将不同公司的业务数据混在一起。 |
| 根对象的子记录 | 包含 tenant_id 并通过复合关联保持公司一致；团队可以沿受约束父对象确定，避免无约束地重复 workspace_id。 |
| 业务运行、用量、任务、产物及事件 | 固定记录或受约束关联公司、团队、发起主体及业务对象，关联不得跨公司或跨团队漂移。 |

适用的业务对象接入现有 Resource/Grant 注册。纯关系、全局身份、账务事实不为套用通用授权而强行变成内容资源。

保留旧业务表为其业务对象的唯一权威存储；已有 Enterprise 对象保留自己的权威存储。不能通过“新旧各写一份”完成迁移。需要调整的唯一约束与外键按真实业务归属扩展，UUID 或全局唯一 ID 本身不是授权依据。

## 5. 授权与 Interface

### 5.1 新授权规则

团队公共资源读取/使用要求：有效公司成员资格、有效资源所属团队成员资格、资源明确发布为团队公共、对应动作允许、资源及相关依赖有效。

个人资源要求：有效公司成员资格、有效团队成员资格、现有个人所有权或明确资源授权、对应动作允许。团队成员资格不开放个人文件、会话、连接账号和凭据。

read 不自动授予 run、write、delete、share、manage。团队公共 Bot 可使用不等于可编辑配置；团队公共知识库可检索不等于可上传或删除。不同公司不可通过内容 Grant 绕过公司隔离。同公司跨团队分享是显式例外，必须同时验证有效公司成员、受众、资源动作和分享撤销，不复用默认团队公共规则偷放行。

资源授权规则通过新版本引入。旧 tenancy-v1/conversations-v1 的语义不被静默修改；资源暴露范围必须迁移或明确选择，不能把旧 public 自动变成全公司/全平台公开。

### 5.2 Module 与调用接口

沿现有 authorization seam 增加团队事实检查，由授权 Module 集中处理公司资格、团队资格、资源归属、动作、个人权限和策略版本。业务调用者不自行拼装多套“可见性”判断。

保留现有可信公司 Scope。创建、列表及团队设置等操作必须传入经过验证的目标 Workspace；按 ID 操作可从对象归属确定 Workspace，再授权，不强制仅凭客户端当前团队决定对象归属。

一个业务事务中完成成员重验、团队重验、资源授权和实际读写。团队成员移除、公共发布撤销或授权撤销后，后续操作失效；已发出的外部动作不能声称被撤回，长任务在后续敏感动作处重验并支持取消。

缺公司/团队上下文时明确拒绝，不能回退默认公司或第一个团队。跨范围及无权对象按不可见方式处理，不通过错误文本、计数、存在性检查泄露数据。登录、健康检查等全局端点显式列入例外。

### 5.3 数据库兜底

租户域表启用适用的 RLS 与受限业务数据库角色，业务事务设置本地公司和必要的主体/团队上下文。事务提交或回滚后清除上下文，连接池复用不能沿用上一次请求的范围。

团队公共访问、个人所有权和显式分享的数据库策略必须与应用规则一致。公司范围机器读权限仅供明确平台任务，不可提供给普通业务接口。禁止应用使用可绕过 RLS 的角色作为普通数据访问入口。

## 6. 配置、运行及外部系统

部署级基础设施继续共享；公司/团队模型选择、Bot 配置、连接器凭据、政策、知识范围通过作用域解析。缓存键含实际归属及配置版本，不能将客户业务状态保存在单份可变全局配置中。

租户包加载从单个部署默认扩展为公司配置装配，明确团队配置覆盖规则。公司提供可用能力，团队选择其中已开放能力；团队覆盖不能扩大公司安全限制。个人凭据不通过覆盖规则升级为团队凭据。

机器认证与业务身份分开。任务保存原始公司/团队归属及受限执行身份，Worker 根据服务器持久化记录验证执行资格，不能信任队列消息中任意 tenant_id，也不能把序列化 Scope 当可信 Scope。平台扫描可发现所有公司的到期任务，但每个任务的执行、产物和费用回到自己的作用域。

模型、AG-UI、MCP、电脑、代码沙箱及 Go Runtime 的调用都绑定业务归属、动作和受限凭据。公司/团队/个人之间不共享浏览器登录态或个人工作目录。共享基础运行池可以保留，但分配、复用和回收必须防止状态残留；状态化公共 Bot 的使用还须区分调用人的会话和个人凭据。

知识检索先确定允许的 KB/文档集合，再在检索端限制返回范围；不能在内容已进入模型或重排之后过滤。当前 KB 的公司范围 Key 只可作为受控内部能力，普通请求不能获得无限公司知识范围。

对象存储、外部线程、学习容器、向量检索命名空间、缓存、事件通道按实际业务归属隔离。路径前缀/ID 编码只用于寻址，签名 URL、下载接口和代理端点仍要授权。分享链接属于明确授权，校验归属、受众、有效期与撤销状态。

OAuth/SSO 回调通过服务器持有的状态绑定发起公司、团队、用户和目标连接，不读取回调时用户当前选中的团队作为归属。SCIM 只变更关联公司的成员关系，不能删除用户在其他公司的资格。

## 7. 公司余额与团队用量

公司工作台的一个 Tenant 对应一个明确映射的计费 Customer。各团队共用公司余额，不为每个团队复制可用额度。现有积分 Grant、Reservation、Ledger、Settlement 和订单事实继续为权威。

每次被计费执行固定公司、团队、使用人、Bot/授权及稳定的调用标识。预扣、释放、结算、退款或调整均可追溯到同一公司账户；外部 provider 回调从已记录订单/调用关系解析公司，不接受客户端任意指定付款账户。

公司内不同团队并发调用必须从同一余额原子预留，不能“各团队各读一次余额”后独立扣费。团队用量按确定事实汇总，公司总计与可归属的团队用量及明确公司级项目一致；无团队的公司级发放/调整要保留真实归属，不能虚构团队。

余额共用不改变账单可见性为全员可读。付款人继续拥有其订单可见性；明确授予公司财务管理权限的主体可查看公司账务，团队用量只向授权主体开放。旧按个人 created_by 限制的订单读取不被直接放宽为全公司成员读取。

保留现有金额单位、幂等、预扣上界与结算保证，不引入新的积分精度或宽松准入。价格和计费规则调整不属于本次隔离整改。Bifrost 个人直连路径保留 ADR 0003 的独立准入要求，不能因为公司工作台有 Credit Gate 就认定个人直连路径已覆盖。

### 7.1 公司与个人付款账户路由

| 调用来源 | 付款账户 | 用量归属 |
| --- | --- | --- |
| 公司工作台中的团队业务、公司定时任务及其受控执行 | 固定公司 Tenant 的余额 | 公司、团队、使用人、Bot/运行。 |
| 已授权外部 Bot 通过个人模型授权直连 Bifrost | 该个人授权绑定的 OpenBot 用户余额 | 个人、Bot 授权及调用；不计入公司的已扣积分。 |

付款账户由服务端依据业务对象或已签发授权固定，持久化到调用、预扣与结算事实。客户不能通过 body/header 随意指定账户；余额不足时拒绝对应调用，不自动消费另一类余额。事件、客户映射和幂等标识要能区分个人与公司，避免标识冲突或重放到另一账户。

多公司用户的公司任务不会因切换公司/团队而改变付款方。个人虚拟 Key 继续绑定个人及 Bot 授权，不自动改成公司 Key，也不授予任何公司内容、团队资源或业务工具权限。个人调用与公司调用的账单、对账、尾差分别归属各自付款账户；公司团队用量统计不把个人消费算作公司支出。

已有按部署客户归属的历史积分迁移到原有公司账户；不得把同一历史余额复制到公司账户和个人账户。既有个人余额如果已经存在则保留个人归属。无法判断历史账户类型的记录先受控隔离再核验，不按用户身份猜测付款方。

## 9. 迁移、错误与统一上线

1. 固化当前版本、全部入口与数据归属清单，记录共享基础设施和平台例外。建立全功能覆盖映射。
2. 创建原有公司及默认团队，给历史对象建立归属；保持现有个人权限。无法唯一归属的历史对象进入受控隔离清单，不按猜测分配。
3. 以兼容方式增加字段和约束并完成回填；并行版本的写入必须有明确归属。迁移时暂停相关写入或提供受控兼容写入，不能由新旧默认值造成跨公司数据。
4. 按业务闭环接入授权、数据库策略、配置和执行身份；完成外部线程、文件、检索集合、浏览器状态等迁移或受控隔离。每个对象只有一个权威写入方。
5. 在候选环境覆盖所有功能和客户端；关闭开发单用户绕过及不合格旧入口，验证后台机器入口与租户数据读取分别授权。
6. 全部验收通过后统一开放多租户。上线前做备份与恢复演练，确认故障时的安全退路。

错误处理：身份/作用域缺失明确拒绝；对象不可见按 not-found 处理；授权存储或配置不可用时关闭相关操作；不能以错误时回退默认租户恢复服务。

回退规则：存在多公司数据后，不能直接回退到不懂 tenant_id 的旧版本。安全回退须使用仍支持隔离的版本，或先停止全部业务入口和任务执行后恢复经核验的备份。停机窗口与数据量属于实施前必须实测的部署输入，不在本设计承诺零停机。

## 10. 现有设计冲突及处理要求

### C1：Bifrost 的个人余额与本次公司余额——已解决

`docs/adr/0002-per-user-bot-model-access.md` 与 `docs/adr/0003-bifrost-openbot-credit-admission.md` 已 accepted；Bifrost 设计及 `CONTEXT.md` 规定用户个人余额、个人治理 Customer、按用户累计费用尾差。用户在明确提出该冲突后回复“保留”，本设计按保留既有个人直连路径处理；公司工作台使用公司余额。

旧 ADR、个人积分术语和 Bifrost 访谈记录保留。本次不实现公司 Key 替换个人 Key，也不把 Bifrost 原生周期预算当作公司或个人积分。两类付款账户遵守 §7.1 的固定路由，无余额回退、无重复额度，业务内容权限与个人模型调用资格分别校验。

### C2：旧 Enterprise 显式 Grant 与团队公共授权

`docs/specs/superpowers/2026-10-09-enterprise-ai-platform-design.md` 与现有策略强调显式个人资源 Grant、不隐式继承 Workspace 权限。本次 R4 选择团队公共资源访问，是明确新增行为。

本文件批准后，通过新策略版本和资源发布属性实现；旧版本不放宽。后续 ADR 应记录这项有限演进：仅团队明确公共资源采用团队资格，个人内容及内容管理动作不继承。

### C3：订单可见性

旧计费可靠性设计明确按 created_by 限制用户订单。本次公司共用余额不自动替换该限制；公司财务管理是明确管理动作授权，普通公司成员不能查看其他人的付款资料。后续实施若调整旧文档，应明确哪些管理读取新增授权。

### 文档证据限制

根 AGENTS 的规范入口位于 `.agents/rules/domain.md` 与 `.agents/rules/issue-tracker.md`。本次仅设计，不自动创建 Issue；不得声称已核验远端 Issue 或完整需求树。

## 11. 验收条件

| 编号 | 验收 | 对应需求 |
| --- | --- | --- |
| A1 | 同一用户加入多公司，直接使用另一公司的资源 ID、凭据 ID、任务 ID 或签名流程，未经授权均无法读取或操作。 | R1/R2 |
| A2 | 同公司非团队成员无法通过列表、详情、检索、下载、事件、直接运行或管理接口访问团队资源；错误与计数不泄露其存在性。 | R2/R5 |
| A3 | 多团队成员分别使用自己加入团队的公共资源；跨团队默认不可见，显式分享仅在规定动作与受众内有效。 | R2/R3 |
| A4 | 新团队成员无需逐人 Grant 即可使用明确公共 Bot 和公共 KB；无法编辑它们，也无法读取同团队其他人的个人资源。 | R4 |
| A5 | 公司/团队成员停用及资源授权撤销影响后续 HTTP 请求、下载签发、订阅、任务敏感动作及凭据获取；其他公司资格不被误删。 | R2/R3/R5 |
| A6 | 缺少上下文、伪造 Scope、连接池复用、授权依赖失败均不回退默认公司或团队。实际受限数据库角色下跨范围查询/关联被拒绝。 | R1/R2/R5 |
| A7 | OAuth/SSO/SCIM、支付与运行回调按服务器持久状态归属，不能借客户端 selector 改写公司或团队。 | R1/R2/R5/R6 |
| A8 | 所有后台扫描、重试、取消、恢复与外部执行保持原公司/团队归属；浏览器、文件、线程、缓存及检索没有客户状态串用。 | R2/R5 |
| A9 | 各团队并发消费共享同一公司余额并原子预扣；公司 A 不能消费公司 B 余额。用量可按团队/用户汇总，重试不重复结算。 | R6 |
| A10 | Web/移动/桌面切换公司和团队后不显示旧范围的在途响应或缓存；新标签页与长连接遵守相同规则。 | R1/R3/R5 |
| A11 | §8 每个现有业务闭环以及明细清单中的全部入口均有针对性正向与越权证据；适用测试、静态检查和独立 Review 通过后统一开放。 | R5 |
| A12 | 历史迁移保持个人权限、账务事实和关联一致性；无未归属交付数据；完成可恢复且不会丢失隔离的上线/回退演练。 | R2/R4/R5/R6 |
| A13 | 公司调用与个人 Bifrost 直连分别使用固定付款账户，余额不足不切换账户；重试、回调、团队切换与 Key 重放不改变付款方。个人消费不计入公司支出，个人 Key 不开放公司内容；历史余额不重复迁移。 | R6/R7 |

最低测试身份：公司 A 的团队甲/乙、公司 B 的团队丙；至少包含仅属甲、仅属乙、甲乙双成员、同团队另一人、跨公司用户、公司管理员、平台操作身份及受限 Worker 身份。

正向业务回归与越权检查必须同时完成。只有越权测试通过但功能不可用，不满足“所有现有功能完成隔离”。外部服务证据缺失、未分类路由或未归属数据都阻断统一上线。
