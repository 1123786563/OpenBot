## 现场决策与偏差记录

1. **计划测试桩笔误修正（Task 2）**：计划的 `rejectingUser` 中间件写的是 `await context.json({...}, 401);`（无 return）——响应被丢弃，Hono 报 "Context is not finalized"，任何正确实现都只能得到 500。真实 guard（`guards.ts` 的 `createRequireUser`）是 `return context.json(..., 401)` 短路。已改为 return 写法，断言强度不变（仍断言 401 且先于业务逻辑）。这是测试桩内部修正，不触碰任何 produced 接口。
2. **`requireUser` 装配适配（Task 3 Step 4，计划预留的现场核对项）**：index.ts 没有名为 `requireUser` 的变量；仓库自己的约定是 `createDeploymentRequireUser(config, auth, roleRepository)`（`app.ts` 导出，其 docblock 明说"the one construction both createApp and index.ts's seams mount"）。已按该约定构造。计划中 `agentStore.get` 按实际名 `agentProfileStore.get(actor, botId)` 使用，语义与计划一致（读到 profile → `canManageAgent` 判定 → 否则 null；绝无 `canAccessAgent`）。
3. **app.ts 字段位置**：按计划逐字放在 `opsSignals?:` 之后——该处在 `openMuseSeams` 命名对象内，符合仓库"named object 而非 trailing positional"的既定方向；一个字段 + 一行解构 + 一行挂载，未动其他代码。
