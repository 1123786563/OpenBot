# Rehearse billing recovery and API rollback

Run the #108 rehearsal from the repository root with Bun, Docker Compose, and the worktree's `.env.test` link in place.

```sh
bun install --frozen-lockfile
scripts/billing-recovery/rehearse.sh /tmp/openbot-108-evidence
```

Choose a new output directory for each run. The script creates a private Postgres 17 container with a random loopback port, applies the current migrations, and removes the container on exit. It writes the custom-format `ledger.dump` and the assertion results in `result.json`. All channel records, model traces, and responses are fixtures.

## Recover the ledger

1. Check that the snapshot contains a paid order, a confirmed refund, and a paid operation still awaiting settlement.
2. After the snapshot, record a new payment, confirm a refund for an order already in the snapshot, and settle a newly dispatched operation in the source database.
3. Restore the snapshot into a second database. Activate the restore hold before opening any billing path. The rehearsal verifies that new orders and reservations are denied.
4. Check each account's payment and refund records against the channel evidence. Retain the order, entitlement, and refund IDs. Recover a missing dispatch from its retained checkpoint, including its frozen route, original funding allocations, and supplier hold. Pass the original usage evidence to current settlement.
5. Replay the evidence a second time. Compare the ledger IDs, balance, Lago event ID, route supplier exposure, and shared pilot exposure to the source database. Resume the verified account after those checks pass. Leave the account with the channel amount discrepancy paused.

The replay code is part of the local fixture. It uses a retained ledger journal and a dispatch checkpoint in addition to channel and usage evidence. The existing `billing-paths.ts restore resume` command records the operator's decision, so keep a discrepant account on hold and leave the restore active while any account still needs reconciliation.

## Roll back the API version

1. Withdraw the affected route before the rollback and confirm that a reservation made before withdrawal can no longer dispatch.
2. Run the legacy billing API from commit `cf466ae4948c803227a530c7e24452c941d98713` against the retained schema. The rehearsal gives it read-only HTTP ingress. Its receipt presents a Paid Credit reservation as Test Credit, and its quote endpoint rejects the current catalog.
3. Keep the current settlement code active on the same database. Complete the two in-flight operations with fixture usage. Check the frozen price and route, Paid Credit allocation, and supplier cost. Seven tokens debit seven microcredits even though the replacement route prices the same input at seventy.
4. After the pending operation count reaches zero, stop current settlement work and start the legacy API with a catalog generated by that revision. Keep the schema and the billing write hold. Confirm that the legacy quote succeeds and the settled receipt remains readable.
